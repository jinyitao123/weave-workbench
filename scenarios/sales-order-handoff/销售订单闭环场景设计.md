# 销售订单闭环场景设计

## 当前边界

2026-10-03，本批范围已确定为销售订单闭环，顺序为合同负责人确认结构化付款条件、独立签署登记、必要的预收登记与独立确认、合同转订单、提交及原生订单审批，再由各员工正常桌面办理后的独立 Forge 读回收尾。**Forge 已正式发布，桌面新包已完成销售本人登录与待办只读打开；本场景完整业务验收尚未完成。** 本机组件结果、部署实物和真实桌面观察分别记录，不互相代替。项目立项、生产发货、交付验收、开票核销和最终回款后置，不用本批结果代表完整订单到回款通过。

本页是这一场景的唯一主文档。系统边界依据[智能体团队设计](../../docs/architecture/智能体团队设计.md)和[系统架构](../../docs/architecture/系统架构设计.md)；个人动作、调用范围、回执与事项字段只维护在[共享契约](../../contracts/v1/README.md#员工本人业务动作)。当前工作队列见[项目状态](../../docs/项目状态.md)，实际部署、桌面产物和工程门禁见[联调环境当前基线](../../docs/environments/开发联调环境.md#当前销售订单联调运行基线)。

本批不新建签署团队、转订单团队或订单审批团队。员工与 Pi 在本人会话中办理明确业务动作；Forge 校验规则、权限和版本，并由原生审批与有效任职决定办理人。Weave 保留既有团队能力，但不承接本批这些个人决定，也不能凭旧合同运行的任务令牌执行它们。

## 起点与材料

复用合成合同 `TEST-CONTRACT-20261002-001`。其 R2 正文与技术协议已完成双方本人内部复核，销售完成通知续看、最终下载及历史原件读取已有证据，准确字节和摘要见[合同场景当前联调](../sales-contract-handoff/合同场景设计.md#当前联调)。这只构成本场景的上游基线，不代表签署、预收或订单已经完成。

该基线最后独立读回为“内部复核通过”，签署字段为空，关联订单和项目均为零。开始本场景时仍须以本人权限重新读回，确认没有其他会话改变状态；不能为重测删除已有单据，或覆盖此前退回、修改和批准的历史。

签署凭证须由登记员工明确选择并按本人权限上传，保留与获批 R2 的来源关系。合成测试材料需标明用途；不能把内部复核通过、签署空白页或模型文字当作客户签署事实。签订日期、签署来源、订单名称、计划交货日期、付款方式和下单资金条件均取员工明确输入，不自动填今天、猜账号或推算未确认金额。

下单资金条件单独以结构化业务字段确认。若本轮采用预付款 6,000 元作为下单条件，应由合同负责人明确保存这一数值，再核对同合同实际登记并独立确认的到账事实；不得从付款条款中的“30%”自行计算并认定已满足，也不得把本页样例当作已到账记录。

| 签署归档员工 | 核对准确合同及获批版本，登记本人选定的签署凭证、日期与说明 | 凭证归属与原件核验仍执行；不得覆盖已有不同签署版本。 |
| 收款登记员工 | 对准确合同登记实际到账、账户、日期、金额及流水依据 | 登记与独立确认分开；未确认或不匹配的记录不满足下单门。 |
| 独立财务确认员工 | 核对原生收款流水与合同预收记录后确认 | 不确认本人登记，不能以口头说明替代权威到账数据。 |
| 订单经办员工 | 读取下单条件与合同明细，创建订单并提交原生审批 | 明细、数量、税率、价格、额度由 Forge 校验，不让模型重写整张清单。 |
| 独立订单复核员工 | 打开本人原生审批，核对来源、数量、金额和条件，作出同意或拒绝 | 按原生有效任职及审批请求确定资格，不审批本人经办订单；拒绝取消该单，不进入合同材料返修。 |
| 团队开发者 | 仅维护获授权的团队定义或查看能力元数据 | 不因开发身份读取本合同、办理个人动作或将 `employee_only` 绑定给团队。 |

多人或无人任职时，Forge 使用已有明确且有效的负责人，或保留待分配状态；不能选择查询结果第一人、把同一事项派给所有候选或让 Pi 猜人。非审批事项从业务状态派生，原生审批继续由审批服务承载，通知只负责提醒。

## 正常验收路线

以下是完整验收路线；当前只走到第一步的本人待办只读打开，准确材料与独立页面仍须重新核对，其余业务办理均待执行。每个正式决定从对应员工的正常桌面会话发起；接口和数据库只辅助定位、取证，不替代点击、办理和业务页面读回。

| 顺序 | 员工正常入口与操作 | Forge 应形成的权威结果 | 独立核对 |
| --- | --- | --- | --- |
| 1 | 合同负责人从真实完成通知或本人业务记录交 Pi 查看 | 只读取得当前内部复核结果、准确 R2 和未签署／未下单事实 | 当前记录、原件与合同场景基线吻合；零写入。 |
| 2 | 合同负责人从本人条件确认事项明确保存下单付款条件 | 结构化规则与明确金额，未确认不按零或无需预付款处理 | 独立页面读回规则，条件事项按权威状态退出；签署前确认，不事后静默降低条件。 |
| 3 | 独立签署归档员工从本人事项打开合同，选定凭证并明确要求登记 | 一份准确签署登记及可追溯原件，日期、登记人和说明正确 | Forge 本人详情重开；原件下载摘要相符；旧 R1/R2 历史不变。 |
| 4 | 如规则要求预付款，收款登记员工从本人事项登记到账 | 复用原生收款流水及客户预收台账，绑定同合同、同客户，等待独立确认 | 金额、账户、日期、流水及归属准确；此时不得提前满足下单条件。 |
| 5 | 独立财务员工打开本人待确认记录并明确确认 | 同一笔预收的确认人、状态与余额更新，保留原流水 | 未确认、错客户／合同、退款占用或不足额均不能算可用金额；本批不另建资金账。 |
| 6 | 订单经办员工读回当前合同和下单条件，明确创建订单 | 唯一订单草稿，保留合同及明细来源；数量、价格和合计由 Forge 生成 | 正常 Forge 订单详情重开，逐行对照来源，不只核总额。 |
| 7 | 经办人在新的订单上下文中明确提交 | 原生订单审批请求及明确办理人，订单进入待审批 | 原员工事项退出，审批人的事项离线仍留存；不以直接改状态冒充提交审批。 |
| 8 | 审批人本人桌面打开事项并同意或拒绝 | 原生 `approve` 后应用订单生效及合同累计；`reject` 后取消未通过订单，不增加合同累计 | 原生审批决定与业务应用结果分别核对；自审、错人和过期事项被拒。 |
| 9 | 经办／负责人重新登录查看结果，打开正常 Forge 页面 | 订单最终批准结果、来源链和准确明细持续可读 | 回执、订单状态、审批历史及本人事项一致；无额外项目、发货、开票或回款操作。 |

订单拒绝和发起人原生撤回另列为异常验收项，未实走前保持未验。审批决定使用原生 `approve/reject`，不提供 `revise`；拒绝后的订单取消并保留意见，不复用合同材料修订接口，不把取消单自动改回草稿。原生 `recall` 后保留审批请求 `recalled`，领域应用取消订单并解除原预收与该订单的绑定，保留原流水和合同累计；重复核对不得改变预收余额或重复应用结果。需要再次下单时重新核对当前合同及资金条件，由员工明确发起新的办理。字段、明细或材料变化不能沿用旧版本的通过意见。

原生审批决定可以先于最终业务应用独立持久化。若审批已通过而订单生效或合同累计写入失败，应显示这两个事实，沿已确定的原生决定核对并完成领域应用；不能要求审批人再次同意、把批准改为未决定，或将订单尚未生效写成已完成。

## Pi 的自然办理边界

员工可以先说“看看这份合同现在能不能下单”，这只触发读取和说明。明确说“登记这份签署凭证，签订日期为……”“把下单预付款要求保存为六千元”或“就按当前合同剩余明细创建订单，付款方式银行转账，交货日期……”后，Host 固定本轮消息、准确对象、版本、参数及文件，再执行已声明动作；不增加同义确认弹窗。

员工说中文枚举标签时，Host 使用原生 `enumLabels` 核对选择，实际提交声明值；不能任意翻译或猜值。标签重名、日期不合法、金额缺失、文件用途不清等情况只追问具体缺项。账户、记录、文件 ID、操作 key 和上下文版本均由 Host 绑定，不要求员工填写，也不交给模型自由生成。

创建订单成功只返回可读的新订单引用，不继承旧合同的写权限。提交订单前重新打开准确订单、读取当前可办动作，并取得该步的新员工消息。恢复会话、打开通知、查看源记录或复用材料均不自动延续上一轮写授权。

### 本机组件证据与限制

本批真实 PostgreSQL 组件检查已通过以下断言，测试使用隔离合成数据；没有对上述合成合同代办业务，也不代表任何员工已走完本场景。

- `sales-order-domain.native-postgres.integration.mjs`：重复签署、预收登记和转订单沿用原结果；预收未独立确认时不能下单；自确认和订单自审被拒；重复引用同一来源行导致累计数量超量时不能提交。
- 同一领域测试还保全原生审批决定已经批准、最终订单状态写入故障的中间事实：订单仍待应用，合同金额／数量累计共同回滚；随后根据已确定审批决定完成领域应用，重复核对不重复累计。这不是把原生审批和后续业务应用宣称为一个不可分阶段。
- 同一领域测试实际调用原生 `recall`，读回审批请求 `recalled`、订单 `cancelled` 与撤回结果，原预收的订单绑定解除；随后重复应用原生决定没有重复累计或改写原预收绑定。原生拒绝同样取消订单、解除该绑定，合同累计仍为零，原已确认预收可用于重新创建准确订单。
- `employee-business.native-runtime.integration.mjs`：由原生 CLI 启动服务并经真实 PG／HTTP 检查目录保留团队多文件定义、标准身份及本人回执归属；不同操作键竞争同一版本时仅一个成功；失效上下文返回可查询的 `failed/noEffect`。
- 同一连接测试在成功回执写入前注入故障，验证领域业务写入随事务回滚；接口仍保留 `unknown` 并只允许核对，同请求再次提交不重新派发原生动作。
- 同一连接测试验证签署凭证原生字段绑定后，后续财务岗位可经原生文件 URL 读取准确字节；到账凭证由独立财务确认岗位同样读取，摘要一致，无关账号两类原件均被拒绝。开发者可读能力定义，但仍不能因此取得该业务记录权限。
- 同一连接测试在 1002 条前置原始记录后仍能分页取得本人事项；带员工身份的 JWT 游标不能被同组织其他账号复用，跨账号请求被拒绝。

这些结果只证明测试覆盖的组件边界。部署实物和新桌面包已在[环境说明](../../docs/environments/开发联调环境.md#当前销售订单联调运行基线)核对；签署／到账原件、各岗位正常办理、原生拒绝和撤回取消路径、事项离线留存及最终独立页面读回仍须单独记录实际结果，当前不标通过。

## 必须穿插的拒绝与恢复验证

- 打开事项后只读；旧消息、模型建议、否定或条件表述不能触发写入。切账号后丢弃旧上下文、材料选择和确定计数。
- 签署前、条件未确认、预收未独立确认或金额不足时，正常下单入口拒绝；错误说明准确指出业务缺口，不泛称授权过期。
- 签署凭证必须符合原生归属与本轮选择，错误日期、替换文件、摘要变化和已有不同签署版本不能被覆盖。
- 订单沿合同准确行创建，服务／物料类型、原数量、税率、单价、折扣及合计一致；缺来源或越过剩余量、额度时拒绝。
- 同一操作 key 的重复和并发只取得同一回执，换参数或文件报冲突；不同 key 并发操作同一业务记录也不得产生双重订单、重复资金或覆盖签署版本。
- 原生执行前故障与已可能执行后失联分开。结果未知时只查询原操作，不再派发、不换键，也不把 404 或界面取消当作未执行证明。
- 同一领域事务中业务写入或成功回执写入失败应共同回滚；原生审批后续推进须实际核对，不能因提交回执成功就宣布订单批准。
- 原生订单审批只有当前实际处理人可以办理；经办人自审、无关开发者、旧材料／旧事项、被取代输入与 task token 均按相应边界拒绝。
- 订单拒绝或原生撤回后，审批请求、订单取消、原预收解绑和合同累计分别读回；重试核对不重复应用，不能把回执或界面关闭当作原预收已解绑。
- 员工离线不改变本人业务状态和原生审批。通知已读不等于事项已办；部分来源读取失败不得显示完整零待办。

## 通过条件与证据归属

本场景只有同时满足以下事实才能标为通过：员工正常桌面完成签署登记及明确条件，必要预收完成独立确认，订单准确创建并经原生审批完成；参与人的本人事项与消息正确；独立 Forge 正常页面重开读回订单、源合同、明细、签署及资金依据；必要原件实际下载核验；权限拒绝与幂等恢复证据不与正常路径冲突。

每项记录实际办理员工、来源记录与版本、明确的新消息、准确文件摘要、操作回执、审批意见、前后权威状态和独立页面观察。详细原始工具／接口／数据库证据仅私有保全，不把凭据、运维地址、客户正文或本机路径写入公开文档。组件检查只说明其覆盖的实现可用，接口读取仅作辅助证据。
