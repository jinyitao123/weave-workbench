# 契约 v1

这些契约只描述跨组件传递的信息，不规定 Forge 内部对象结构或 Weave 内部执行方式。

所有请求都需要可核验的员工与组织身份；团队调用另带任务级短期委托，员工本人接口只接受原生员工会话。所有会产生业务影响的动作都带有幂等键。执行结果允许明确表示“结果未知”，此时调用方必须先向 Forge 核对，不能直接重试。

## 三场景修复的执行约定

本节为 2026-09-24 并行修复的实现边界，仍须通过组件检查和桌面场景验收。

### 真实动作结果

- Forge 原生 MCP `run_action` 返回及权威业务记录决定业务结果；Weave 运行结束和模型文字不替代它。Weave 在现有运行活动/结果中记录动作事实，不新建执行队列、审批或独立终态。
- 每条事实绑定当前运行、节点、工具调用、动作名、对象和已冻结记录。只由能力桥写入；成员文字、材料或用户自填同名字段不能成为事实。状态为 `succeeded`、`failed`、`unknown`；只有 Forge 明确成功才记 succeeded，发送后丢失响应记 unknown，不能推断未执行。
- 下游成员只接收当前父运行内已确认的动作事实，可以描述其他节点已完成的动作，无需拥有该动作的写权限。平台指令须区分本节点和整个父运行。前序模型文本仍按工作数据处理，不能伪造工具回执。
- 员工续办接口在 `run.action_outcomes` 返回该运行的事实投影；字段为 `node_id`、`call_id`、`action_name`、`object_name`、可选 `record_id`、`status`、`summary`。summary 由平台根据已知动作名称及状态构成，不使用模型文本、不包含内部标识或原始错误。内部保存可以包含受限的原生结果数据，但不得保存凭据、请求头或模型私有思考。
- 原生收件箱继续使用现有 team-run-event：有业务动作时 summary 以动作事实生成，运行失败仍保留此前已经完成的动作；具体分析由员工打开原工作读取。没有动作事实时只称团队分析完成，不能称业务写入完成。未知结果不自动重放；取消不会删除已完成事实。
- 新版在成功读取平台活动后始终返回 `action_outcomes`；空数组明确表示本轮未记录 Forge 业务动作调用。活动存储或读取失败时返回错误，不能伪装成空数组。缺省字段仅兼容旧接口，表示未提供动作事实。最终汇总输入、终态消息和桌面续接都明确展示该平台事实，并放在可能被截断的模型摘要之前；工具返回成功只证明调用回执，不证明正式业务状态。桌面保留团队运行状态，独立显示/传给 Pi 动作回执，不从模型段落猜测状态。
- 续办接口另在 `run.business_result` 给出服务端统一计算的运行级业务结果，取值 `completed`（完成）、`needs_input`（需补充材料）、`action_failed`（至少一次业务动作调用失败）、`action_unknown`（至少一次业务动作结果未知且无失败）；运行没有面向业务的结果（失败、取消、放弃或仍在运行且无动作失败）时字段缺省。优先级固定：动作失败高于动作未知，二者都高于团队自己报告的完成或需补充，因为团队结束不代表业务写入。没有失败或未知动作且已有成功业务回执时，模型的补件意见不再产生 `needs_input`；正式后续事项仍由 Forge 决定。员工事件标题中的“（业务动作需核对）”与它同源，桌面显示这个字段，不再自己从运行状态与动作回执推导。该字段不代表 Forge 的正式审批状态。字段为新增可选项，旧桌面忽略未知字段即可，不需要同步发布。

### 团队业务动作的持久操作身份与幂等

- 系统在已持久保存的成员工具日志位置确定一次操作，位置包含成员运行、检查点段和序号；模型提供的 `tool_call_id` 与业务参数摘要不能决定操作身份。同一位置的恢复沿用同一身份，新的位置即使参数完全相同也属于新的操作。
- Weave 将操作位置与冻结输入、执行调用和业务能力绑定为稳定 `operation_id`。记录、材料及完整有效参数的摘要用于核对同一操作内容，身份不变但内容变化必须拒绝，不复用旧回执。账号/组织隔离继续由现有任务委托和 Forge 认证保证。
- 动作声明含 `idempotency_key` 或 `idempotencyKey` 字符串参数时，Weave 从工具定义中隐藏该参数并注入稳定操作身份；模型与材料参数绑定均不得覆盖。Forge 沿用该动作既有的幂等与内容冲突规则。没有声明幂等参数的动作保留原生业务防重放与平台未知结果停止规则，不宣称无条件自动重放。
- 发送前在现有运行活动记录的事务锁内原子核对并占位；同一操作的并发请求只有一份能发送。已确认成功或明确失败的重复操作返回原可信业务回执并关联当前工具调用，不再调用 Forge；结果未知或仅有开始记录时停止并核对。不同操作不因相同参数被误拦。
- 原生动作正文的 `ok` 必须为布尔值才表示成功或拒绝；`null`、数字、字符串或与 MCP 错误标志矛盾时保持未知。没有 `ok` 时，只有 MCP 明确错误标志、非空错误字符串或带明确错误语义的错误对象可确认失败；`error:false`、`error:0`、数组及无错误信息的对象不能解除未知结果保护。成功标志与异常非空错误字段矛盾时也保持未知。
- 操作身份、参数摘要及有界脱敏的原生业务回执只用于内部审计与恢复，不公开为员工编号；不存凭据、请求头、原始动作参数或模型私有思考。原有员工动作事实投影继续只返回状态和可读说明。

### 原生只读记录连接

- 桌面 Host 用当前员工 Forge 会话调用原生 MCP `list_objects`、`describe_object`、`query_records`、`get_record`。可查询范围来自原生读取授权，不以团队是否绑定写动作作为前提。禁止向此连接开放通用 create/update/delete 或任意 run_action。
- Pi 查询时只提交业务检索意图、目录返回的对象引用和分页参数；Host 验证对象来自本账号当前目录，排除 sys_*。结果携带名称、编码、获准状态/负责人及版本，返回不透明 record_key；无匹配、歧义、拒绝和服务失败分别表达。禁止无关唯一结果自动命中。
- 读取选定记录及关联明细时，只使用原生元数据中声明的关系和同一员工身份，不在桌面按合同/报价对象名特判。关联读取有数量上限并明确完整性；截断不能被当成完整报价。
- 当前 ObjectStack 17.3 的 MCP `describe_object` 只投影字段名称、类型、标签和必填性，未提供 `reference`；关系须从同一会话的原生具名元数据 `GET /api/v1/meta/object/{name}` 的 `item.fields.*.reference` 确认。先依据已读目录的对象名/标签收窄少数候选，再取具名元数据；不能每次读取全部对象定义，也不能仅因名称相似就认定关系。无法证明关联或子项读取不完整时返回 partial，不得宣称完整核算。
- 账号切换、员工轮次变化或取消使未完成的查询/交接结果失效。向团队交付的是该轮固定读取的字段、明细及版本，写动作仍沿既有单独授权与受保护对象绑定。业务保存时 Forge 再验证当前版本；读取不冻结后端业务记录。
- 首批只读快照由 Host 序列化进现有固定 `task` JSON，与 goal 分区，受已有 task 摘要和冻结意图保护；模型仅选择 record_key，不能转抄或覆盖快照。已由当前员工权限完整读取的明细关系，可在快照中按行顺序附带原生 `recordIds`，仅供受控领域动作填写明细引用，不作为页面展示内容；缺失、重复或越界的引用不得由模型猜造。登记仍使用已有 business_record 与可选 record_version，不另建快照表。原生没有可靠版本时不造值；报价主记录的 `pricing_version` 与快照格式 `version` 必须分开，领域保存动作仍按真实报价版本和明细归属校验。
- Forge 单行报价调价动作的对外参数使用 `expected_pricing_version`，值必须是本次获准读取的报价主记录 `pricing_version`，不得用快照格式 `version`。Forge 仍在同一事务核对当前版本、明细归属和幂等请求，再重算报价；参数改名不表示放宽版本冲突。既有调整回执内部仍可保留 `expected_version` 审计列。

### 报价起点与保存

- Forge 正常销售入口提供草稿创建、主表及明细编辑、保存后详情。权限按场景实际业务职责配置：销售处理本人线索、商机和报价；交付、商务在被分配的合同事项范围内读取与办理；团队开发者不因开发身份获得业务数据。独立核验是验收方式，不新增核验员或全销售域只读权限集。
- 优先用 ObjectStack 原生表单、列表、关系及事务能力；若原生组合保存不能保证头/行/汇总一致，只在 Forge 领域动作补这个原子保存边界。保存失败保留用户输入和可核对的结果，不用成功提示掩盖部分写入。
- 本批只含草稿：至少两行，数量、单价、税率与折扣由 Forge 共用计算规则生成小计和汇总，未知成本保留未知。原生对象与已有 `quotation_adjust_line_price` 复用；不追加审批、对外发送、转订单或多行通用模型写入。
- 验收先建立并重开 2300 元草稿；Pi 试算不写入，授权后只将设备单价改成 900，服务行及数量保持不变，总额 2100；并发旧版本拒绝，同请求重试返回同结果。

材料通过受管理的引用传递。桌面本地路径不能直接成为远程系统可读取的材料地址；上传后用摘要校验内容是否一致。

## 企业身份会话

`enterprise-session.schema.json` 是桌面可见的账号投影，`account-binding.schema.json` 描述 Forge 账号到 Weave 用户的稳定绑定；两者都不包含密码、Cookie 或 Bearer Token。`task-delegation.schema.json` 描述任务范围内的短期授权。

- 调用者：Workbench Host 调用 Forge 登录和 Weave 绑定接口；界面只读取账号、组织和 Forge 已验证的产品权限投影。
- 身份来源：Forge 注册并验证账号，Weave 以 `issuer + subject + organization` 建立本地绑定。桌面不创建第二套账号。
- 单次登录：Workbench Host 把一次性账号密码请求发给 Forge，随后把 Forge 会话交给 Weave 验证并换取产品会话。渲染进程不保存密码，Weave 不接收或保存密码。
- 自动绑定：首次登录创建稳定的 Weave 用户映射；重复登录返回同一 Weave 用户；不同组织或身份来源不能按邮箱合并。绑定只回答“这个 Forge 账号对应哪个 Weave 用户”，不保存独立产品角色。
- 产品权限：Forge 权限集是唯一来源。`智能体团队开发` 权限集开放团队配置、调试和发布；Forge 平台管理员增加平台管理能力。Weave 在登录交换时验证这些权限并签发短期会话，不允许本地角色覆盖验证结果。
- 业务权限：Forge 对每次业务动作继续执行自身权限判断。团队产品权限不能扩大 Forge 数据和流程权限。
- 保存方式：桌面登录令牌仅保留到本次进程结束，不调用系统钥匙串、不落盘；重开桌面后重新登录。交接记录不含令牌或密码，按账号保存在本地用户私有目录（0700）和文件（0600），固定材料与幂等信息在网络写入前原子落盘。旧加密记录保留，不自动触发钥匙串解密；命中旧记录时要求核对原工作，不能当作新请求重发。
- 传输：Workbench 按部署配置连接 HTTP 或 HTTPS，账号投影中的 `environment.secure` 明确标识当前连接方式；客户内网可直接使用 HTTP。
- 任务授权：Workbench Host 直接向 Forge 领取下述受限任务令牌，固定输入登记只把该令牌交给 Weave。Weave 不接收员工完整 Forge 会话；验证令牌的原生员工/组织、准确输入、发布版本、动作、记录和材料后加密保存为不透明引用。团队发布能力只是上限，本次动作必须是其子集，空列表表示只处理材料。凭据不进入模型、任务正文、回执或审计；每次发送前在线核验当前授权和任务租约。原有会话代持记录不能冒充新令牌，须原员工重新授权。
- 失效：Forge 返回 401 时，桌面清除对应账号会话并回到未登录；403 是当前资源或操作无权限，只显示该项拒绝，账号和其他合法读取保持可用。退出登录应先通过 Forge 原生会话接口吊销该会话，再清本地状态；网络失败仍清本地并明确记录远端吊销未确认，不把未确认写成已吊销。
- 身份来源：Forge以`FORGE_IDENTITY_ISSUER`配置部署级稳定标识，经公开只读`GET /api/v1/workbench/identity-source`返回`{version:"1",issuer}`；未配置503。员工身份另经原生会话验证，Weave以稳定标识绑定员工，网络地址只用于连接；更换地址不创建新员工。任务发行/current分别返回连接`issuer`与绑定`identity_issuer`，二者不能混用。
- 审计：登录、退出和委托签发记录主体、组织、设备会话、时间和结果，不记录密码与令牌正文。

## 开发观察

`development-observation.schema.json` 是 Workbench Host 从 Weave 读取后交给开发中心的只读投影。

- 调用者：已登录的 Workbench Host；只有 Forge 已授予 `智能体团队开发` 或平台管理权限的账号可进入开发中心。
- 身份：每次请求携带当前 Weave 会话，按会话组织限定团队、工作流和运行记录。
- 输入：不接收业务对象或任意查询；第一版固定读取当前组织的可见团队、每个团队的工作流和归属运行。
- 输出：团队角色、准确的已发布或草稿版本、节点关系和运行摘要。空数组表示真实暂无数据，不生成示例记录。
- 错误：401 使对应设备会话失效并回到登录；403 只拒绝当前范围，不退出账号。单个团队的工作流或运行读取失败须保留该来源错误，避免把不完整数据展示成完整事实。
- 幂等与取消：全程只读，无幂等键；窗口离开或刷新可以取消请求，不影响服务端状态。
- 审计：Weave 保留主体、组织、接口和结果；桌面不记录 Bearer Token 或工作流输入输出正文。

## 团队成员配置草稿

`team-member-config-draft.schema.json` 描述开发中心按“团队 + 智能体成员”保存的配置草稿。草稿与正在运行的智能体版本分离，保存草稿不会改变正在运行或新发起任务使用的配置。历史扩展字段 `publishedConfiguration` / `publishedRelationship` 为可选字段；当前实现读取的是注册配置与团队关系，不是发布时冻结的快照，桌面不得据此宣称“与已发布版本比较”。旧服务未返回这些字段时仍可读取与保存草稿。

- 调用者：已登录的 Workbench Host；只有 Forge 已授予团队开发权限的账号可读取和保存。
- 身份：Weave 从当前会话取得主体和组织，成员必须属于请求中的团队。
- 并发与幂等：客户端提交已读取的 `revision`。同一修订只能成功保存一次；较旧修订返回 `409 draft_revision_conflict`，防止覆盖另一位开发者的修改。
- 输入与输出：草稿包含智能体身份与指令、模型和运行时、技能与工具、材料与输出约束、执行限制，以及该成员在团队中的职责和交接要求。Loom 成员只能从组织已经接入且有正式版本的模型中选择，不允许手填一个无法运行的模型；Loom 由 Weave 调度，不显示运行位置，只有桌面 CLI 成员需要选择运行位置。密钥、请求头和长期凭据不进入草稿投影。
- 生效边界：本接口只保存草稿。发布必须由独立的验证和发布动作生成不可变智能体版本；MVP1 第一步不提供发布动作。
- 错误与取消：成员或团队不存在返回 404；无开发权限返回 403；请求取消时未提交的事务不产生草稿。
- 审计：保存记录操作者、组织、团队、成员、修订和时间，不记录密钥或令牌正文。

## 业务能力目录

`business-capability-catalog.schema.json` 描述 Forge 的业务能力只读投影，供 Workbench Host 和 Weave 开发目录复用。开发者看到并分配的是“查看销售合同”“提交销售合同”这类中文能力，不是 MCP 服务器、`run_action` 等通用工具或底层参数。

本轮增加 `GET /api/v1/workbench/business-actions/catalog`，直接返回该 schema 的对象，不套 `data` 包络。当前标准 `Action.ai` 的 strict schema 没有执行主体字段，原生 MCP 目录也没有本应用的调用策略装饰入口；现有客户端把 effect 固定为 write，不能据此区分只读与写入。因此由 Forge 从同一受控策略定义投影 `effect`、`executionMode` 及原生动作参数，Host 不硬编码个人动作名单，也不从名字或说明猜副作用。此接口是待实现的最小目录连接，不新增动作执行通道。

- 目录只接受有效员工会话；员工读取当前可见能力元数据，已具团队开发权限者可读取组织可配置能力定义。目录读取不授予业务记录访问、动作执行、团队委派或新账号权限；开发者可知道个人动作存在，但不能将 `employee_only` 分配、发布给团队。
- 返回的 `status=available` 只说明目录定义可用，不保证任意记录满足执行条件。本人实际办理仍须读取下述当前业务上下文，再经原生权限、RLS、业务状态与本轮授权检查；团队仍使用任务委托及其专用受限目录。普通目录可见不能让 task token 绕过 `employee_only`。
- 请求不接收账号、组织、对象记录、任意查询或幂等键；全程只读，可取消且不影响业务。401 表示会话失效，403 表示无目录读取资格，503 表示定义或策略无法可靠读取；不可用项保留稳定标识并给出原因，不能退回客户端旧硬编码。审计只记录当前主体、组织、读取时间和目录版本／摘要，不记录凭据或业务正文。

- 来源：Forge 只发布明确允许智能体使用的业务动作；未标记为可用的对象动作默认不进入目录。
- 调用者范围：`effect: read|write` 描述副作用，`executionMode: employee_only|team_delegable` 描述执行主体，两者独立。旧目录缺省 `executionMode` 时按 `team_delegable` 兼容；新目录必须显式声明。本批签署登记、合同转订单和原生审批本人办理动作明确为 `employee_only`，不能分配给 Weave 团队。Forge 的当前受控定义是权威，旧缓存、发布快照或客户端省略字段不能把个人动作降级为可委派。
- 连接：管理员配置一次 Forge 服务连接。连接地址、认证方式和密钥属于环境配置，不进入成员草稿。
- 分配：开发者把能力分配给团队成员，草稿只保存稳定的 `businessCapabilityIds`。发布版本冻结成员允许的能力标识；运行开始时，Weave 再以本次员工委托读取当前 Forge 动作目录，冻结动作说明、记录要求和声明参数。
- 执行目标：成员通过既有能力桥直接调用 Forge MCP 的受控业务动作；按员工真实授权限定范围。“交给团队看看”不构成正式提交审批授权，已有明确授权不重复弹窗。运行终态通知由系统自动产生，不作为每个团队必配的业务工具。
- 身份目标：Workbench Host 安全保管桌面会话；远端成员通过任务级委托调用 Forge。Workbench 根据本次员工表达从团队已发布能力中选择零个或少量业务动作，Weave 校验子集并冻结。Weave 以当前员工委托读取 Forge 动作目录；目录不可见、动作不存在或参数不合法时关闭该能力，不退回到自由填写 `params`。每次实际动作前再核对当前运行任务、员工、输入版本、本次动作范围和委托有效期，Forge 最后检查员工、组织、业务记录和当前流程状态。长期会话不进入模型或团队输入，也不能用共享管理员身份替代。
- 权限：Forge 每次执行仍按员工账号、组织、业务记录和当前流程状态判断是否允许。Weave 的团队配置不能扩大 Forge 权限。
- MVP1：合同场景先提供查看销售合同、查看关联报价、读取合同材料和提交销售合同四项；后续能力由真实场景缺口驱动增加。
- 部署：连接认证由环境接入统一管理，不重复写进团队配置。远端业务能力与受限委托是本批前置项；具体身份传递方式须核实 ObjectStack 当前能力后补齐契约，不预设某种 OAuth 实现已具备。
- 错误与审计：目录不可用时保留成员已有选择并标明不可用，不静默删除；发现、分配和调用分别记录操作者、能力、团队、任务和结果，不记录凭据正文。

### 员工本人业务动作

本节为本轮**待评审契约草稿**，不表示已经实现、部署或验收。[employee-business-action.schema.json](employee-business-action.schema.json) 顶层为 Host 执行请求，`$defs` 定义上下文查询、上下文回包、模型提案和本人操作回执。签署登记、合同转订单及订单复核由员工本人通过 Pi 办理，不为这些节点建立 Weave 团队。

| 接口 | 输入／输出 | 职责 |
| --- | --- | --- |
| `GET /api/v1/workbench/business-actions/context` | 查询参数符合 `contextQuery`；回包符合 `context` | 按当前员工和 Host 已选对象、记录读取受控动作上下文；可附通知或审批来源引用。只读，不执行动作。 |
| `POST /api/v1/workbench/business-actions/execute` | 请求符合 `executeRequest`；回包符合 `operation` | 核验 Host 固定的上下文、版本、当前消息、声明参数、文件与幂等键后，执行一次既有原生 MCP `run_action`。 |
| `GET /api/v1/workbench/business-actions/operations/{id}` | `id` 为 Host 已持久保存的 `opKey`；回包符合 `operation` | 仅当前员工、同一组织读取本人回执。全程只读，不续授权、不触发执行或重放。 |

原生 MCP 已有动作发现、权限、记录读取和执行能力，但本轮核对未发现覆盖“桌面当前来源、上下文版本、本人持久幂等回执”的完整入口。以上连接只补绑定、校验与结果保存；底层动作继续由原生 MCP 执行，业务前置条件、金额、预付款门、审批决定及处理人解析仍归 Forge。不得添加第二套执行器、队列、审批状态机，或用通用 CRUD 代替动作。原有原生审批上下文、同意／退回和修订接口继续使用；本连接不能绕过它们的请求轮次及材料版本校验。

1. **身份与任务拒绝。** 三个接口只接受当前有效的 Forge 原生员工会话，不接收员工或组织 ID，不接受任务 token。Forge 复用已验证的员工身份与岗位权限，不依赖模型声明的调用者类型。`employee_only` 必须在任务委托签发、动作目录、对象动作元数据和实际执行四处被拒绝；旧 grant 即使列有该动作，也不能调用。任务签发时 actor 仍可能是 human，不能仅判断 `principalKind` 就允许委派。标准 `Action.ai` 不支持的属性不直接塞入其 strict schema；Forge 用同一受控策略定义投影调用范围并执行校验。
2. **只读起点与来源。** 员工打开记录、完成通知、审批或恢复会话后，Host 初始仅允许读取。来源可以保留，但不延续原消息的写权限。Host 从正常选择或已核验来源绑定对象、记录；Forge 重新确认记录可见性，通知须属于当前员工，审批须允许当前员工读取，并核对来源指向同一记录。来源不是扩大权限的凭据。个人动作目录只包含当前员工可调用、当前记录状态可用且本批参数可安全表示的 `employee_only` 动作。
3. **上下文与并发。** `contextId` 是服务端受保护的上下文引用，绑定员工、组织、对象、记录、来源和动作映射；不是 bearer 凭据。`contextVersion` 是规范化绑定内容的 SHA-256，至少包含可靠的 `recordVersion`、来源版本、动作标识、原生参数声明摘要 `declarationVersion` 及执行策略。目录内 `action_ref` 唯一，取值为 1–64，不能跨上下文或刷新轮次使用。执行前重新读取权限、业务状态及定义；绑定变化、过期或版本不符返回 409，不自动选择相似动作或更新为另一份上下文后写入。上下文摘要不等于通用 CAS；所选业务动作仍须在自身事务边界重读、校验和防并发。无法取得可靠版本或对应动作没有所需并发保障时明确不可用，不以连接层的先读后写冒充原子校验。
4. **本轮新授权。** 只有新员工消息明确要求当前业务动作，Host 才允许提出执行。Host 固定当前账号、会话、消息 ID 和消息摘要，并在发送前确认消息仍存在、未改变且属于当前员工轮次；Forge 以原生会话确认调用身份，消息引用仅作来源审计，不能伪装成服务端已验证的自然语言授权。模型仅提交 `{action_ref, values}`，不提交账号、对象、记录、上下文版本、来源、文件引用或 `opKey`。Host 向模型和普通界面提供业务名称，不显示内部标识。
5. **参数与文件。** 本批仅支持原生字符串、数字、布尔值、枚举、合法 `YYYY-MM-DD` 日期和单文件参数；不接普通数组、嵌套对象、任意字段补丁或未声明参数。`values` 只承载声明的标量业务值，具体类型、枚举、长度与数值边界由 Host 和 Forge 按同一原生声明复核。文件不进入模型 `values`；Host 从本轮员工明确选定的文件固定 `file`，Forge 核验当前员工、组织、原件字节、摘要及动作既有归属要求，再按声明参数名注入。不能把历史可读文件自动当作本轮签署凭证；签署、主件等业务意义由员工明确指定。参数声明无法解析或超出本批类型时动作不可用，不降为自由文本。
6. **一次操作与幂等。** Host 在任何业务执行请求前，将账号、上下文、版本、员工消息、动作引用、完整标量、文件摘要和随机 UUID `opKey` 原子保存到当前账号私有记录，不保存会话凭据。`operationId` 等于该 `opKey`，由服务端按员工和组织隔离，因此执行响应丢失后仍能直接查询。Forge 在调用原生动作前持久记录下文定义的 `requestDigest` 和执行占位；员工、组织、来源、对象与记录、可靠记录版本、动作及声明版本由 `contextVersion` 绑定，完整请求继续绑定业务参数和固定文件。同一员工、组织、key 只能获得一次原生执行权。相同 key、相同绑定只返回原操作状态，变更任何绑定返回 `409 BUSINESS_ACTION_OPERATION_CONFLICT`；不能靠重新编号或换新 key 绕过同一未确认操作。
7. **结果和未知状态。** `in_progress` 表示已占位且尚无终局回执；`succeeded` 只来自原生明确成功；`failed` 必须有权威确定失败事实；发送后失联、进程中断或无法证明结果为 `unknown`。只有服务端能证实尚未进入原生执行，或整个业务事务已回滚，才可设置 `noEffect=true`；HTTP 错误、超时及取消不是这样的证明。`in_progress/unknown` 只能查询原操作；服务端查询可结合已有原生回执和准确操作关联事实核对，但不得重新执行，也不能用当前记录状态或模型文字猜原操作成功。查询 404、读取错误或材料失效都不能把未知改成未执行。只有原操作结果已权威确定，员工才可用新消息、新上下文提出后续新操作；未确认时不能换键或重派。
8. **来源及后续记录。** 成功回执可带服务端确认的新订单等 `recordReferences`，供打开和读取；这不授予新记录的写权限。下一步需要重新读取目标上下文并取得新员工消息授权。回执摘要来自受控原生结果，不接受模型自述，不直接透出原生错误堆栈、凭据或完整记录正文。
9. **取消与审计。** 请求取消只终止尚未发出的本地操作或停止等待；已进入原生执行的动作不因关闭桌面、退出会话或取消请求而宣称回滚。审计保存员工、组织、上下文与版本、来源、员工消息摘要、动作、操作 key、请求摘要、文件摘要、原生关联引用、结果及时间；不存令牌、密码、签署正文或模型思考。连接层回执没有独立业务终态决定权。

**原生枚举标签。** 本人上下文参数可含 `enumLabels: [{value, label}]`；原生 options 有标签时必须按原样保留，其 value 类型不变、唯一且与 `enum` 一一对应，不缺项、不增项，Host 和 Forge 均检查这项跨字段一致性，`declarationVersion` 覆盖标签映射。员工明确选择“银行转账”时，模型与原生调用仍传声明值 `bank_transfer`，Host 可用该值唯一对应的准确原生标签核对本轮新消息中的选择；不接受任意别名、回译或模型猜值。重复标签可保留，但同一标签对应不同值时不能仅凭标签认定授权，必须取得清楚选择。标签匹配不替代业务动作的新消息授权，也不把否定或条件表述当作已选择。

**请求摘要的准确算法。** `requestDigest = SHA256(UTF8(canonicalJSON(request)))`，其中参与摘要的完整对象固定为 `{version, contextId, contextVersion, opKey, employeeMessage, action_ref, values, file: file ?? null}`，不加入会话令牌、传输头、接收时间或回包字段。`canonicalJSON` 递归按 JavaScript UTF-16 顺序排列对象键，保持数组顺序，标量采用 `JSON.stringify` 的数值与字符串编码；拒绝 `NaN`、`Infinity`、`undefined` 和 schema 外字段。声明键为 ASCII，此规则与本批 JCS 语义对齐。除省略的 `file` 归一为 `null` 外不静默变更员工业务值，不转换日期时区、不猜金额。Host 对发送前保存的准确请求本地重算并核验每次回执摘要；Forge 按同一算法计算，同时重新核对 `contextVersion` 的服务端身份、来源和版本绑定。请求或读回摘要不符须停止并报冲突，不能重新发起。

错误约定：401 为员工会话失效；403 为当前动作或调用者不允许；404 为上下文、操作或来源不存在／不属于当前员工；409 为上下文过期、绑定变化或同 key 内容冲突；413 为输入或材料超限；422 为声明参数、文件或业务前置条件不满足；503 为当前权限、定义或回执不可可靠读取。拒绝在调用原生动作前确定时可返回 `noEffect=true`；已经占位或可能调用过原生动作时必须保留可查询的原操作，不用普通失败响应丢失关联。

审阅／验收边界：验证无新消息只读；错账号、错组织、过期上下文、旧动作引用及替换文件被拒；同 key 并发和同内容重试只产生一次原生调用；同 key 换内容 409；原生调用后断连及重启保持未知且仅查询；任务 token 对四个授权面均被拒；个人合法办理和原生角色分离继续生效。组件与接口通过不替代桌面正常路径及独立 Forge 业务读回。

本批销售订单的本人办理顺序为：合同负责人先确认结构化付款条件，再由独立员工登记签署，随后办理必要预收及独立确认、合同转订单、订单提交和原生审批。订单审批只提供原生 `approve/reject`：拒绝取消该订单且不增加合同累计，不提供 `revise`，不调用合同材料返修接口。原生审批决定与后续订单生效／合同累计应用可能分阶段持久化；应用失败时保留准确决定和故障事实，仅根据已确定的原生回执完成受控领域应用，不要求再次审批，也不自动重放未知操作。当前 Action／Flow、员工连接及本人事项源码已装配，本机组件检查有证据，部署和正常桌面业务验收仍待完成，具体范围见[销售订单场景](../../scenarios/sales-order-handoff/销售订单闭环场景设计.md)。

### 本批原生文件参数执行约束

以下为第一批重整的实施契约。Forge 原生 Action 参数沿用 `type=file` 与 `multiple`，不在 ObjectStack 的 strict AI 元数据中加入未支持属性，也不靠动作名、字段名称或描述关键词识别材料授权。

- 单值文件参数在 Weave 工具 schema 中只允许当前冻结 `forge-file` 资源的 ID；运行调用再次验证成员资格。文件选择可以由模型根据本轮员工要求提出，但不能提供清单外或另一轮的文件。必需文件参数在没有可用资源时拒绝构造工具；可选参数可省略。
- 多值文件参数必须显式绑定 `materials.ids`，由运行时注入当前完整冻结 ID 数组并从模型输入中移除；漏配、错误类型或模型覆写均在正式调用前拒绝。`multiple` 本身不代表默认把所有文件提交，必须保存该来源绑定。现有 `materials.manifest_json` 继续仅服务文本参数，不能作为原生文件数组的字符串回退。
- Forge 唯一的新提交写动作 `contract_submit_material_package` 使用 `primary_file_id`（单值 file）与 `material_file_ids`（多值 file，含主件）。主件须属于全集，其余为配套附件；名称、字节数与摘要由 Forge 按本人获准的原生文件和存储内容读取、校验，不接受模型填写的名称/SHA 作为版本证明。
- 原生 MCP `list_actions` 是员工当前可调用动作的允许列表。当前 ObjectStack 目录投影会把原生文件类型压成字符串；桌面与 Weave 用同一员工身份从 `GET /api/v1/meta/objects/{objectName}` 的 `item.actions` 补全原生参数声明，仅取允许列表及本次请求能力的交集。对象名、动作名和参数必须精确匹配；字段引用按原生字段声明解析。元数据不存在、被权限遮蔽、重复或不能解析时明确拒绝，不猜测类型、不退回自由字符串，也不从元数据新增可调用权限。声明补全仍不代替 Forge 执行时校验。
- 首批正式写工作按员工明确的一个提交材料集合冻结；只供参考的文件不得因为能读取就混入提交集合。复杂的多动作不同材料子集没有在本批默认为可用；意图不明确时保持只读并询问准确提交材料。
- Pi 提案和手工编辑共用上述来源类型及校验。开发模拟与正式运行共用文件类型、数量和来源校验；模拟只证明其实际输入覆盖的范围，不把单个合成文件的结果当作真实多文件业务通过。
- 旧发布定义和运行不被新配置覆盖。服务升级涉及旧标量提交入口时，保留准确的历史回执读取与显式不兼容反馈，不把旧输入静默转换为新的材料集合，也不保留可绕过完整版本校验的并行写入口。

## 新建团队

`team-create.schema.json` 描述开发中心的最小新建输入。Workbench Host 根据名称和目标建立一个可继续编辑的团队，并同时建立“团队负责人”和“执行成员”两个初始成员，避免新团队再次落入无成员的死路。

- 调用者：已登录的 Workbench Host；向 Forge 已授予团队开发权限的账号开放。
- 输入：开发者只填写团队名称和目标；内部名称、成员标识和默认协作关系由 Host 生成，不在界面展示。
- 默认成员：负责人负责理解目标、分派与汇总；执行成员负责完成任务并返回可核验结果。两者创建后均可在成员配置区修改。
- 一致性：Host 依次建立两个成员和团队；团队建立失败时回收本次已建立的成员。服务端原子创建向导接入后，可在不改变界面契约的前提下替换该适配。
- 错误：同名、权限或连接错误显示为可操作的创建失败；失败时不把团队加入本地列表。

## 团队与成员管理

`team-management.schema.json` 描述开发者修改团队资料、添加执行成员和将成员移出当前团队的桌面输入。移出只结束当前团队关系，不删除成员的不可变版本、既有运行或审计记录。

`workflow-management.schema.json` 描述开发者保存工作流草稿、检查并发布版本或归档流程的桌面输入。桌面编辑的是 Weave 草稿图，保存不改变已发布版本；发布仍由 Weave 校验并冻结依赖。

- 修改团队使用读取时的更新时间防止覆盖并发修改；名称和目标必须在刷新后稳定读回。
- 添加成员同时建立一个可编辑的 Weave 智能体和团队关系；任一步失败时不能在团队中留下半成品成员。
- 负责人不能通过成员移出入口删除；执行成员移出后不再参与新任务，历史任务继续显示当时冻结的成员名称与版本。
- 所有写入由 Weave 会话中经过 Forge 验证的权限判断，Workbench 不在界面层伪造权限结果。

## 员工工作与人工交接

`work-request.schema.json` 在当前实现中由 Workbench Host 映射到 Weave 的固定输入版本和团队派发回执。每次独立工作使用新的 `workId`，原始说明摘要、团队、工作流和准确版本一并冻结；重复回执不能创建第二条运行。

`agent-team-handoff.schema.json` 描述 Host 验证桌面运行时轮次后保存的固定交接包（轮次凭据只在内存中，不写入包）。当前已实现部分使用现有输入登记与派发接口；后续业务闭环补 Forge MCP 动作及受限委托，继续复用现有运行时。

- 调用者为桌面 Pi 扩展；只有 Host 持有 Forge / Weave 会话。账号绑定包含服务来源、组织、Forge 员工与 Weave 用户；账号切换、退出或过期后旧轮次失效。
- Host 在桌面员工输入进入运行时之前使旧轮次失效。扩展在实际处理员工输入时领取该轮次凭据；工具调用只携带该凭据。Host 对照原会话中该轮次的真实员工消息和顺序，不将后来补充的消息替换为原授权依据。意图由 Pi 理解，不加关键词判断或固定确认弹窗。
- 搜索只读取可见团队的名称和目标，使用工作摘要进行词项相关性筛选；这是文本检索，语义判断仍由 Pi 完成。仅查看所选团队时读取其流程。接什么、需要什么、交付什么复用团队目标和流程说明，不强制增加结构化表单。
- Pi 明确指定本次材料路径及所见文件的 SHA-256。Host 限定在当前工作目录内读取 UTF-8 文本、Markdown、CSV、JSON、可提取文本的 PDF 与 DOCX，并以原始字节 SHA-256 冻结确切原件。原件每份最多 2 MiB、每次最多 8 MiB；提取文本合计最多 700,000 字节，最终 Weave `task` 最多 950,000 字节。三个预算独立核算，超限在上传/登记前拒绝，不默默截断。扫描 PDF 页、DOCX 嵌入图像及未支持内容明确记录 `partial` / `unsupported`，列出缺失页或内容数量；仅 `complete` 表示提取器已读到其声明覆盖的全部文本，不表示 OCR 或视觉内容已识别。
- `agent-team-handoff.schema.json` 描述桌面当前用户私有目录中的冻结包。`materials` 只保存本轮新附加文件，使用 `materialId`、原件 `name/mediaType/bytes/sha256`、本地恢复所需的 `bytesBase64` 和提取记录 `extraction {status, mediaType, bytes, sha256, sourceSha256, content, extractor, coverage, limitations}`；`extraction.sourceSha256` 必须等于原件 `sha256`，提取摘要按 UTF-8 字节计算。原始 Base64 仅写入桌面本地固定意图，绝不放入 `work-request`、Weave `task`、模型输入或日志。
- 从 Weave 当前 `needs_input` 事项，或已结束且经权威动作列表确认没有业务动作的最新只读运行消息（检查成功或失败）打开 Pi 后，员工在当前轮明确允许复用旧件时，Pi 可把当前上下文中显示的完整文件名放入 `reuse_material_names`。Host 只在当前账号、准确父 `input_revision_id/run_id/workbench_session_id/team_id` 对应的固定材料清单中精确解析唯一同名项；同名多项、材料缺失或父事项已被后续输入取代都失败关闭。旧事项被后续输入取代时，员工须从最新运行消息继续，不能以旧事项覆盖当前输入。 成功的只读检查允许员工在新轮次明确授权后沿用同一批固定材料办理下一步；原检查授权不会自动扩展为业务写入授权。本轮动作重新取当前员工权限与已发布团队能力的交集，读取准确业务记录并固定新意图。`action_outcomes` 缺失或读取失败不等于零次调用；已有成功、失败或未知业务动作时，先核对原业务回执，不以材料复用为由自动重放。文件名只是当前清单的可读选择标签，不是存储查找条件；Pi 不提交文件路径、fileId 或哈希。Host 冻结 `continuation` 和 `reusedMaterials` 中的原始 Forge 引用、`materialId`、MIME、长度、SHA、来源及已核验提取文本，并把它们与本轮新材料组成一次新输入。`resources[]` 是完整集合；旧资源引用沿用原 `fileId`，只对本轮新附件执行 Forge 上传。owner 文件保留 `sourceKind=owner` 且不得带 `requestId`；approval 文件保留 `sourceKind=approval` 和原 `requestId`。复用原件不把原始字节复制进新固定包、Weave `task`、模型输入或日志。同次恢复使用成功保存的固定资源检查点，不重新上传旧引用或重复登记旧运行；上传入口仍缺服务端幂等键，若 Forge 已接收新附件而桌面在保存上传回执前崩溃，不能保证严格一次上传。
- 材料不设文件份数上限。Host 仍逐件限制 2 MiB、原件总量 8 MiB、提取文本总量 700,000 字节，并限制最终 `task` 为 950,000 字节；任何预算超限都在登记前明确失败，不截断。`team-run-result.missing_items` 的 8 项上限约束的是结果缺项清单，与文件数量无关。
- 一次交接最多 10 份文件（新附件加上复用的原材料合计），另有一个输入条目和至多一条业务记录，共 12 条资源。Host 仍逐件限制 2 MiB、原件总量 8 MiB、提取文本总量 700,000 字节，并限制最终 `task` 为 950,000 字节；任何预算超限都在登记前明确失败，不截断。超过 10 份时 Weave 在登记接口返回 **409** `dispatch_input_too_many_resources`，不写入任何输入版本、不接单；客户端须在上传前按同一总数自行检查，并把该错误码显示为“文件过多”这一明确原因，不得当作结果未知去重试。`team-run-result.missing_items` 的 8 项上限约束的是结果缺项清单，与文件数量无关。
- Workbench 仍通过 ObjectStack storage presigned upload 的 `scope=attachments` 上传原件原始字节，不对 PDF/DOCX 做 UTF-8 解码/重编码；上传回执以 `materialId`、文件 ID、MIME、长度和 SHA 固定。Weave 的 `task` 提供与原件 SHA 绑定的提取文本及覆盖状态，运行成员可直接阅读；文件引用指向 Forge 中的原件供有权业务参与者查看。文本继续使用 `owned-text-material`。PDF/DOCX 原件通过 `GET /api/v1/workbench/materials/{fileId}/original` 读取未改写的 HTTP body，要求 `If-Match: "<冻结的 SHA-256>"` 使用带双引号的 ETag 格式；Forge 只允许当前员工读取本人同组织、private、未绑定且已提交的 `scope=user|attachments` 文件，读取前核对元数据、MIME、长度、文件签名和原始字节 SHA。审批材料另用 `GET /api/v1/approvals/requests/{requestId}/workbench-context/files/{fileId}/original`，只允许当前待办审批人或未重提退回请求的原提交人，且 fileId 与 If-Match 必须和本次原生审批快照一致。两条原件路由均只支持 PDF/DOCX、单件不超过 2 MiB，返回原始字节及 `Content-Type`、`Content-Length`、`ETag`/`X-Content-SHA256`，设置 `Cache-Control: private, no-store`；不在 JSON、`approval-context.files`、Weave `task` 正文、模型输入或日志传输原件字节、Base64 或裸存储 URL。[owned-original-material](owned-original-material.schema.json) 冻结 `sourceKind=owner|approval`；`approval` 必须携带 `requestId`，`owner` 不得携带该字段。读取方只能按冻结来源调用对应原件路由，不得因 404 或状态冲突改试另一条路由。旧文本内容接口保持原样。owner 原件路由未登录返回 401，文件不存在或非本人所有返回 404，缺少或格式错误的 If-Match 返回 428，摘要不符返回 409，大小超限返回 413，MIME 不支持返回 415，元数据或签名无效返回 422，Storage 不可用返回 503。材料缺失、归属不符、快照失效、SHA 不符、MIME 不支持、字节签名不符或本地固定记录无法保存时，停止交接；恢复只使用已保存的固定意图，不重新读取已变化文件。账号、消息、会话、目标、准确团队流程版本、本次动作范围和材料版本共同冻结。
- owner 原件读取未登录返回 401，文件不存在或非本人同组织、private、未绑定原件返回 404；缺少或格式错误的 If-Match 返回 428，SHA 不符返回 409，超限返回 413，MIME 不支持返回 415，元数据或签名无效返回 422，Storage 不可用返回 503。成功读取审计员工、组织、fileId、MIME、字节数和 SHA-256，不记录原文或请求凭据。
- **当前实现：** 合同首次正式提交使用 Forge 动作 `contract_submit_frozen_material`，只绑定一个主件的文件标识、名称和 SHA-256；唯一首次提交记录防止同一合同重复提交。2026-09-29 实测中，销售同轮交给 Weave 的 PDF 技术协议没有进入首轮 Forge 审批快照，复核人只看见 DOCX 正文。退回修订入口可以把新正文和附件一起绑定到下一轮审批，但它不能弥补首轮缺件。
- **待评审的目标契约：** 首次提交应准确冻结本轮获准的主件和配套文件，并让复核人在同一审批快照读取；重复调用必须比较完整材料包，改动其中一份不得复用旧回执。ObjectStack 已提供多文件字段，Forge 下一轮修订已能整包读取；Weave 也有 `materials.manifest_json` 冻结参数来源，但 124 当前合同成员未配置该绑定。实施时须让动作只能消费本次冻结清单，并将主件选择与清单逐项核对，随后再由 Forge 原子保存完整版本。普通页面不展示文件 UUID 或摘要作为业务编号。
- Host 以账号、会话、真实员工轮次与团队流程版本产生合法 UUID，首次发送前以受保护文件原子保存固定请求；相同请求重用同一请求体，并发合并。相同幂等键更换目标或材料版本须报冲突，不能覆盖。重试读取冻结包，不重新生成会话摘要或重读文件。
- 员工只需要求“核对同一次交接”。Pi 根据当前完整对话判断是否继续原范围，调用一次原交接恢复工具；原请求关联标识只在工具内部使用，不要求员工提供，不增加独立检查工具、临时恢复凭据或确认弹窗。Host 在内部核对当前账号、会话、原授权消息及摘要、固定材料与动作范围，并将本次操作绑定当前员工轮次；取消、改变要求或切换账号会使进行中的旧调用失效。退出重登后的恢复仍使用原冻结材料、已保存文件引用和幂等标识，不要求重新附文件、不重传已确认原件、不生成第二份请求。正式业务写入继续由 Forge 校验当前员工权限、准确版本和业务状态。
- `/v1/workbench/dispatch-inputs` 回执须匹配固定任务摘要，再调用 `/v1/teams/:id/dispatch`；每次网络发送前重新验证轮次与账号，使用已绑定账号的请求头。回执须包含输入版本、客户端请求、运行、任务与准确流程版本。网络失败保留包，显式重试用同一 UUID；没有有效回执只能报告结果未知。
- 新员工输入撤销尚未派发的旧交接，不自动重试。已经进入服务端的派发无法靠本地撤销保证回滚，需核对原回执并按现有运行取消语义处理；不能宣称“先别发”撤回了已接单任务。
- 交接成功只表示 Weave 已按固定版本接单，不代表智能体完成审阅或 Forge 业务审批通过。审计保留材料摘要和服务端关联标识，普通员工只看到业务名称、状态及材料名称。

`task-notification.schema.json` 是待与原生能力对齐的桌面展示投影草案，不要求新增持久化对象；描述 Forge 面向员工提供的工作事项投影，不绑定合同、审批或某一种业务对象。Weave 继续拥有团队运行与局部重跑状态；Forge 负责员工账号、事项归属、未读通知和员工续办状态；桌面合并显示两边的权威状态。

`team-run-event.schema.json` 是平台自动连接团队运行与员工收件箱的写入契约。调用者固定为 Weave 服务，不是团队成员或模型工具；Forge 以部署级服务凭据验证调用方，并把 `assigneeAccountId` 作为现有 ObjectStack 账号解析，不能由模型猜测接收人。事件只承载运行结果、失败、取消、需要补充或人工步骤的摘要及返回桌面的定位信息，不执行合同提交、审批或其他业务动作。

团队需要给员工明确列出缺项时，开发者在同一工作流声明可选的 `result_protocol: "workbench_result_v1"`，并把最终交付来源节点的 `output` 与工作流 `output_contract` 配为 [team-run-result](team-run-result.schema.json) 对应的 `type: "json"` 与同一 `schema`。未声明的旧团队继续交付原有文本。Weave 必须用发布时冻结的图定义和现有 `NodeDeliver` 校验结果；`disposition` 只取 `complete` 或 `needs_input`，`summary` 去空白后为 1–1000 字符，`missing_items` 最多 8 项、每项去空白后 1–200 字符；`needs_input` 至少有一项缺项，`complete` 必须为空。模型正文或文件中的相似文字不能改变分类。

`needs_input` 表示**尚未形成正式业务结果的团队检查已结束，等待原员工补材料再发起关联的新轮次**；Weave 运行仍以真实终态 `succeeded` 记录，不新增运行状态或内部人工等待节点。经校验的分类及缺项随同一次最终交付物保存，原有终态 outbox 对同一运行只生成一条 `revision_required` 消息；员工打开后由本人权限读取原固定输入、材料、父工作与结构化缺项，不从通知正文猜测。`complete` 仍生成普通 `result`。若本轮存在失败或结果未知的 Forge 业务动作，动作事实优先展示并要求核对，不得因团队给出 `complete` 或 `needs_input` 就宣称业务完成或自动重放。正式审批退回仍由 Forge 原生业务事项办理，不使用这个团队结果分类。 若本次运行已有权威记录的成功 Forge 业务动作，团队的 `needs_input` 和缺项仅作为检查意见交付；终态事件使用现有 `result`，桌面不再从它产生团队补材料待办。下一步正式业务事项由 Forge 决定。旧通知保持原生记录不变，桌面只在按当前账号、准确来源引用读回的动作事实明确包含成功时抑制该补材料投影；读取失败或事实缺失不得当成成功。消息打开后仍分开说明动作回执、团队意见与当前 Forge 状态，不要求员工重复提交已进入正式流程的材料。

- 身份：Weave 从发起时已经绑定的 Forge 外部身份冻结接收账号和组织；运行结束后不得改用当前登录用户或共享管理员账号。
- 幂等：`eventId` 与 `source.idempotencyKey` 由准确运行和终态（人工步骤为准确交互）生成。Forge 按对象键递归排序后的规范 JSON 计算事件内容 SHA-256，随原生通知保存在 `payload.weaveEvent.digest`；相同键相同摘要返回原通知，相同键不同摘要返回 `409 TEAM_RUN_EVENT_CONFLICT`；摘要功能上线前写入、没有摘要的原生通知无法比较，按重复接受。接收账号不是事件组织成员时返回 `422 TEAM_RUN_ASSIGNEE_NOT_FOUND`。
- 人工步骤：Weave 团队流程的人工节点进入等待时，生成 `kind=human_review` 事件，接收人固定为发起该工作的员工（Weave 不解析其他业务处理人；需要其他员工处理时走 Forge 原生审批），`source.interactionReference` 指向等待中的交互。员工从原生收件箱打开后，桌面按三引用与交互引用向 Weave 读取并办理；桌面不再直接读取 `/v1/human-tasks` 列表。交互已办完或已取消时，后续读取返回 `409`，消息保留为历史。
- 交付：Weave 先将待投递事件写入自己的系统事件 outbox，再异步调用 `POST /api/v1/apps/forge/weave-events/team-runs`。Forge 接入 ObjectStack `messaging.emit`，由其原生通知 outbox 完成收件箱写入、重试和去重。
- 失败与恢复：网络失败、`429` 和 `5xx` 留在 Weave outbox 并退避重试；`400`、`401`、`403`、`409`、`422`（含接收账号不存在）属于永久错误，保留失败记录供运维恢复，不伪装成员工待办。Weave 重启扫描未完成事件，也会为尚未生成事件的已终态 Workbench 运行补建事件。
- 取消：运行尚未终结时不发送完成通知；终态事件一经 Forge 接收不删除。后续恢复或重跑产生新的运行和新事件，并通过工作引用保持上下文关系。
- 审计：两端记录事件、运行、工作、组织、目标账号、尝试次数和最终交付状态；不记录服务凭据、员工密码、Forge 会话或合同正文。

### 业务动作回执完成检查

开发者可在已有 `graph.delivery_contract.required_checks` 中声明 `verifier_id: "weave.business-action-receipts"`、`verifier_version: "v1"` 的只读检查，并将同一检查ID写入 `external_effects_check_id`。参数为 `required_capability_ids`（1至16个不重复且已给流程成员绑定的能力）、`when_authorized: true`、`allow_needs_input`（布尔值）。本版检查要求已启用 `workbench_result_v1` 及其合法三字段输出，绑定最终交付来源成员；桌面、发布与加载均须校验，不静默改写原输出。检查只要求声明列表与本轮冻结授权范围的交集；其他获准动作不会自动变成必做动作。未配置此检查的流程保留现有语义，不从模型摘要推断完成要求。

- 调用者是Weave现有成员完成校验与交付验证器。身份、run、冻结input、能力及受保护业务记录均取可信运行上下文，不接受模型提供的回执或记录替代。每次候选完成时重新读取同运行的权威动作事实，沿既有持久操作身份去重；不得用其他输入、记录或运行的成功回执抵数。
- 声明动作本轮未获授权时不要求写入。获授权且最终结果为 `complete` 时，每项要求必须有匹配成功回执；缺调用只能通过既有Loom完成校验返回纠正反馈，不由校验器执行或重放业务动作。`allow_needs_input=true` 时，合法缺件结果且尚无业务效果可交还员工；此结果不证明任何业务效果完成。
- 已有失败或未知动作、权威事实读取失败、身份或绑定不一致时，停止本策略节点的后续工具调用及完成校验，不能反馈“再提交一次”或把缺证记为零调用。保护在每次实际工具执行前读取，覆盖同一模型回复中的后续有状态工具；不改变未声明本检查的默认重试规则。已成功的动作不再要求重复调用。取消沿现有运行与任务授权规则，检查不能恢复已取消运行或回滚业务结果。
- 最终报告复用现有DeliveryContract验证记录，审计仅保留检查版本、参数摘要、准确运行/输入、匹配动作及状态，不写材料正文或凭据。原三字段结果、任务授权和业务回执协议不变；检查通过仍不等于Forge正式审批通过。
- 桌面Pi作者操作为 `{kind:"business_completion",flow:"准确流程名称",capabilities:["准确业务动作名称"],allowNeedsInput:true}`；仅修改草稿，由Host按当前目录解析并校验已绑定能力，沿现有修订、防重复保存、隔离试跑及发布路径生效。保留其他已配置的交付检查；不授予能力、不替员工授权，也不在普通员工页面展示内部标识。

本节定义本轮修复契约；实现、部署及业务验证状态见[合同场景](../../scenarios/sales-contract-handoff/合同场景设计.md#当前联调)。

## 员工工作投影

### 本人非审批业务事项

本节为本轮待评审连接契约；[business-work-list.schema.json](business-work-list.schema.json) 定义 `GET /api/v1/workbench/business-work` 的直接回包，查询参数为可选 `cursor`、`limit`（默认 50，最多 100）。当前已安装 ObjectStack 17.3 分发未提供已证实的通用员工业务 Tasks 服务；`plugin-audit` 的 `sys_activity` 是 append-only 事件，保留期 14 天，字段没有事项分配、办理状态或完成生命周期，不能拿它充当持久待办。这项核对只描述当前分发，不断言后续平台版本永远没有 Tasks 能力。

该接口仅投影已有业务状态，不新增任务实体。实现方式复用[审批事项只读投影](../../platform/forge/apps/forge-objectstack/src/plugins/approval-work-list.plugin.ts)的身份与分页边界；原生审批继续走 `approval-work-list`，不能在这里复制或把签署登记变成额外审批。

| 派生事项 kind | 权威来源与产生条件 |
| --- | --- |
| `contract_signature` | 已内部批准、负责人已明确确认结构化下单条件、尚未完成签署登记的合同。 |
| `contract_order_conditions` | 合同下单条件尚未明确确认时，向当前有权确认的合同负责人投影唯一条件确认事项；确认后按权威字段退出，不能把缺省条件当作无需预付款。 |
| `contract_prepayment` | 合同的结构化下单资金条件与已确认预收事实尚不满足，且当前确有登记工作。不能解析付款条款文字推算比例。 |
| `prepayment_confirmation` | 既有预收款记录处于需要独立确认的状态。 |
| `sales_order_creation` | 合同已满足签署及金额等下单条件，尚需创建订单。 |
| `sales_order_submission` | 已有本人经办草稿订单尚需提交；或原生审批已有确定同意／拒绝决定、对应领域应用尚未完成，需要原经办人核对并完成订单。仍在等待审批决定的订单不重复生成审批事项，领域恢复不重新征求审批。 |

- **调用者与输出。** 只接受当前有效原生员工会话，不接受 task token、员工 ID 或组织查询参数。Forge 仅根据上述已有字段、领域资格检查和当前原生组织／业务单元／有效任职产生结果；不得根据模型、通知文字、日期窗口或桌面缓存推断事项。每项包含 `workKey`、业务阶段、中文标题、来源记录与可靠版本、来源更新时间和分配状态；内部引用只供调用与去重，不展示给普通员工。
- **责任归属。** `assignment=assigned` 只返回当前真实办理人的事项。优先核验记录已有明确负责人；需要岗位时，复用原生有效任职解析真实账号，并校验组织、有效期、业务权限及职责分离。多人时只有已有明确有效负责人才能继续；否则标为待分配，不能任选第一个、向所有候选派同一事项或让模型选人。无人同样不能假定负责人。账号及岗位资料继续只维护在[演示账号主册](../../scenarios/演示账号与ObjectStack配置.md)，本契约不复制名单。
- **待分配边界。** `needs_assignment` 仅可向该原记录已有维护责任或既有分配权限的当前员工返回，并说明无人或多人原因；它不是该员工已获准执行业务的事项，不计入本人可执行待办、不生成可执行动作引用。没有这种权限者看不到他人的待分配记录。处理人调整沿已有业务负责人／原生任职管理办理，本接口不提供分配写入，不新设分配队列。
- **持存与退出。** `workKey` 是组织、来源对象、记录和办理阶段的稳定摘要；它只用于去重，不是另存 task ID。办理后由权威业务状态变化使该项自然退出；取消、重开或退回也由原业务字段决定。没有本地或服务端的独立“完成／忽略／关闭事项”状态，不写 `forge_employee_work_item`，不新建队列。通知只提醒，标为已读、删除通知、桌面离线或重启均不改变业务办理条件。
- **打开与办理。** 记录读取仍受原生 RLS；岗位候选或目录可见不能替代记录读取资格。Host 打开项时以其记录引用调用本人业务上下文接口，使用 `sourceKind=record`，重新校验状态、版本、本人责任和原生权限。`workKey` 不作为授权凭据，不需要增加第二套事项详情或执行接口。来源保留但初始只读；写入仍须本轮新员工消息和受控原生动作。
- **完整性与分页。** `readStatus=complete` 表示本页依赖来源都可靠读取；只有所有页面读完且无 `nextCursor` 才能称本人列表完整。`partial` 必须带不含正文的 `sourceErrors`，每种来源至多一项，本批六种来源合计最多六项；已有可确认项可显示，未读来源不能当作空或零待办。全部来源失败返回 503；401 使会话失效，403 只拒绝当前来源。分页复用 ObjectStack 原生 JWT 签名，游标最长 8192 字符、有效期 15 分钟，绑定当前员工、组织、来源及原始记录位置。Host 原样传回；签名无效、过期或跨账号／组织复用均拒绝，换账号或游标失效须重新读取，不复用旧账号的确定计数。翻页使用稳定来源位置与去重，不设固定总数截断。游标只保存分页位置，不是业务任务状态、写授权或新的队列。
- **副作用与审计。** 本接口只有读取，无幂等键、业务写入、认领、通知补发或模型唤醒；取消请求只停止读取。审计记录当前账号、组织、来源种类、完整性、时间和错误码，不记录原件、凭据或其他员工的记录内容。后续办理若失败或结果未知，按本人业务动作回执核对；不能在投影层标为完成。

该契约存在不等于当前字段条件、权限与桌面已接通。验收须覆盖源状态产生／退出、重复查询去重、通知已读后仍可办理、离线后仍可见、错账号和 RLS 拒绝、多人／无人待分配、部分读取失败和跨页完整性，不以事件列表或接口健康替代员工正常办理。

### 原生审批与运行事项

依据[决策 002](../../docs/decisions/002-任务委托身份来源与员工入口收敛.md)。桌面“我的工作”只读取下列权威投影并映射展示，不从消息标题、类型子串或时间顺序推断状态。

- 消息种类：只按原生通知 topic 精确识别 `weave.team_run.(result|failure|revision_required|cancelled|human_review)`；Forge 业务消息按 `GET /api/v1/workbench/notifications/{id}/source` 返回的 `kind` 识别。其他 topic 显示为普通通知，不判定为失败或待办。
- 运行投影：Workbench Host 收集当前页 Weave 消息的 `runReference`，调用 Weave `POST /v1/workbench/runs/lookup`（[work-run-lookup](work-run-lookup.schema.json)，每次至多 100 个）。Weave 按 `workbenchRunAccess` 同一归属规则只返回本人运行；`isCurrent=false` 表示同一工作会话已有更新的输入，桌面据此把旧“需要补充”消息显示为已被后续工作取代；`businessResult` 与动作计数决定显示文案。不存在或非本人的运行列入 `missing`，桌面保留原消息但不提供续办。读取失败时整页标为读取失败，不当作“无动作”。
- 审批投影：Forge 插件 `GET /api/v1/workbench/approvals?cursor=&limit=`（[approval-work-list](approval-work-list.schema.json)，`limit` 默认 50、最大 100）从原生 ApprovalsService 与动作历史只读投影本人可办理的 `pending` 事项和本人提交且尚未重提的 `returned` 事项，附最新退回意见。不新增存储，不替代原生审批办理路由。
- 读取窗口：审批投影逐页读至原生结束；没有固定500条截断。原生收件箱的200条上限由下文只读keyset连接补齐，包含所有精确topic；分页失败或完整性不能证明时标为不完整，保留可见事项。
- 错误：各来源分别报告 `loaded` / `failed`；401 使会话失效，其余错误不影响其他来源展示。
- 审计：只读，无幂等键；不记录消息正文或材料内容。

## 原生业务结果通知续接

[业务通知来源](business-notification-source.schema.json) 与既有 [Weave 通知来源](team-run-notification-source.schema.json) 复用 `GET /api/v1/workbench/notifications/{notificationId}/source`，不新增消息库、投递或任务状态。

- Forge 只向该原生收件箱消息的当前收件人返回来源，校验当前组织、收件箱行和通知行一致。业务来源只取原生 `source_object/source_id`；不从消息正文、标题或 actionUrl 解析记录。Weave 的现有来源格式保持不变。
- 业务消息返回 `kind=business`、Forge 对象/记录引用，以及领域已授权的当前原件引用。通知归属不授予业务记录读取权；桌面仍通过现有 ObjectStack 只读路径，以当前员工重新读取该记录。若无权读取，明确拒绝，不借管理员或系统权限返回业务数据。
- 合同领域复用当前材料快照、已有提交/修订记录及原生文件持有关系，投影员工有权读取的准确原件；材料规则留在 Forge。`materialStatus` 区分可读、没有材料、暂不可取得。`unavailable` 不得当成已读完，不能从旧通知正文补材料。原件字节与提取复用既有受保护读取；引用不含签名URL、正文或凭据。
- 员工打开通知后，Host 固定当前账号、通知来源与新读回的记录/材料，在独立会话交给 Pi。通知描述作为历史信息，记录快照标明当前读取时间。初始打开只读，不自动发起团队或业务动作；之后员工明确提出的新要求，仍走现有轮次、能力范围与 Forge 权限校验。
- 复用现有工作续接绑定、过期/账号变化检查及草稿保留。源记录、材料或账号已变更时重新打开，不能把另一笔业务替代进去。错误采用现有未登录、不可见、来源缺失及服务不可用边界；不新增用户恢复凭据或额外确认流程。

## Forge 原生审批上下文

`approval-context.schema.json` 定义 Workbench 打开单个 ObjectStack 原生审批时读取的受限展示上下文。Workbench 继续从原生审批列表读取本人事项，审批人仍用原生 approve/reject/revise 路由办理；退回后的修订递交必须经下文的材料绑定动作，不让桌面直接调用原生 resubmit。该读取契约不建立第二套待办或审批状态。

- 调用者是持有效 Forge 员工会话的 Workbench Host；员工账号从已验证的 Bearer 会话取得，不接受调用方传入 `userId`、岗位或受理人。
- 路径为 `GET /api/v1/approvals/requests/{requestId}/workbench-context`。Forge 必须先用 ObjectStack 原生 ApprovalsService 校验当前主体；`pending` 只向当前待处理 approver 返回，`returned` 只向原始 submitter 返回。已经办完的历史参与者、管理员覆盖权限均不因本只读接口获得材料上下文。
- 返回内容限于该审批请求冻结的字段快照、展示标签、退回意见、该快照明确绑定的文本文件，以及可选的 `originalFiles` 元数据。文本文件保持在 `files`；PDF/DOCX 只在 `originalFiles` 返回 [owned-original-material](owned-original-material.schema.json) 的 `sourceKind/fileId/name/mediaType/bytes/sha256`；审批来源另含 `requestId`，且必须等于外层 `requestId`；Forge 生成上下文时必须逐项校验该关系。不返回 `content`、Base64 或预签名 URL。文件标识必须属于此请求的固定主件/附件版本，返回前核对其 SHA-256。供 Host 续办的 `businessObject` 来自原生请求的 `object_name`/`record_id`，`sourceMaterialVersion` 是冻结 payload 按 JSON 对象键递归排序、UTF-8 编码后的 SHA-256，文件 `fileId` 来自原请求快照；这些内部标识不在产品页面展示。`returnVersion` 是最新 `revise` 动作 ID，和同一动作的 `returnReason` 一起投影。任一必需来源缺失时不得准备修订提交，不从标题、消息正文或当前合同记录猜测。不得以提交岗位权限为由开放通用合同/附件读取。
- 二进制读取路径为 `GET /api/v1/approvals/requests/{requestId}/workbench-context/files/{fileId}/original`。Forge 每次请求重新从 Bearer 会话与 ObjectStack `ApprovalsService` 解析员工，只允许 `pending` 当前 approver 或 `returned` 原提交人；退回请求一旦被重提即返回 `409`，不允许读取旧轮次。`fileId` 必须在该 request 的冻结主件/附件字段集合中，`If-Match` 必须与冻结 SHA 完全一致；审批字段只读范围不会扩大为任意合同/附件读取。原始响应仅接受 PDF/DOCX 且每件最多 2 MiB，回传字节前核对记录引用关系、MIME、长度、签名和 SHA；设置 `Cache-Control: private, no-store`、`Content-Disposition: attachment`、`ETag` 和 `X-Content-SHA256`。未登录返回 401；未参与、不存在或不在本次快照中的文件统一 404；缺少或格式错误的 If-Match 返回 428；快照缺少冻结 SHA、字节/元数据无效返回 422；快照或摘要已变化返回 409；格式不支持 415；超限 413；存储不可用 503。原件不放进上下文 JSON 或审计日志。
- 非当前参与者或不存在的请求统一返回 `404 approval_context_not_found`，避免探测事项存在性；已变化的状态返回 `409 approval_context_stale`；认证失败返回 `401`；超限或不支持的材料返回 `413` / `422`。该读取无服务端副作用，无幂等键。
- Forge 审计员工、组织、requestId、读取结果和文件标识/摘要，不记录正文。二进制原件读取必须提供 If-Match；缺少或格式错误返回 428，快照 SHA 与 If-Match 不一致返回 409。读取成功时仅审计员工、组织、requestId、fileId、字节数、SHA-256 和结果，不记录字节、Base64、令牌或业务正文。Workbench 在 UI 展示前仍校验输入账号代次；不把返回正文写进日志、调试遥测或团队定义。
- 此上下文只读，不批准、不驳回、不更改业务记录。

### 退回后的材料递交

员工原文与运行提示分开固定。可信桌面发送路径保存实际员工文字及本轮选定附件来源，Host按同一附件格式重新组装并严格比对完整运行提示；运行会话证据仍匹配完整提示，`employee_request`仅匹配Host核验后的员工原文，不能要求模型抄附件元数据。队列、steer和follow-up保留同份来源；旧调用没有来源时维持原全文严格匹配，不任意剥离文本标记。账号/轮次/本地文件权限和摘要校验不变。打开返修自动开场只读，不能当作员工递交授权。 新来源的修订主件与每份附件都须以path+SHA匹配本轮实际选件，冻结后再核对长度/MIME；未选第三文件或版本不符在上传前拒绝。旧调用继续保留原保护，不凭模型声明扩大本轮材料范围。

Workbench Host 只在原提交员工打开 `returned` 事项、Pi 根据其明确意图准备好新版本后调用 Forge 修订业务动作。Host 在首次网络发送前原子冻结当前账号、Pi 实际处理的员工轮次、`requestId`、`returnVersion`、`sourceMaterialVersion`、`businessObject`、完整主件与附件字节及各自 SHA-256、允许动作和 UUID 幂等键；断线恢复只读该包，不能重新采样变化的文件或会话。账号切换、员工说“先等等”、事项状态变化或新一轮退回使尚未提交的旧意图失效。模型不得提供操作者 ID、记录 ID、审批状态或自行选择文件 ID。

桌面修订工具保留旧文本调用：`body` 是本轮确认的修订正文，Host 将其按 UTF-8 固定为 `修订正文.md` 主件，`materials` 继续表示员工本轮选定的附件。新版可用 `primary_material: { path, sha256 }` 指定一份本地正文原件；它与 `body` 必须恰有一个出现。Host 必须按当前员工轮次冻结该准确文件的原始字节并核对 SHA-256，再用现有 Forge 文件上传能力上传；Pi 不得构造 Forge `fileId`、MIME 或长度。选择 PDF/DOCX 时，Host 递交原件字节，不把解析文本或模型改写内容当作该主件。未选正文、两种正文同时出现、选定文件摘要变化或账号/事项轮次变化时，在调用 Forge 前停止。

Forge 从当前员工会话和原生审批请求重新取得操作者及业务对象，核对该员工为最新退回请求的原提交人、本次 `returnVersion` 仍是最新退回动作、源快照未变、全部新文件已提交且字节/摘要/归属相符。Forge 的领域规则决定主件、附件及字段如何形成新材料版本；合同只是其中一种规则。相同幂等键与同一冻结包返回同一回执，换内容返回冲突；同一退回轮次不能并发绑定两个版本。明确的 `pending`、`committed`、`unknown` 回执要能按幂等键核对，未知结果先查询再决定是否恢复，不盲目重放业务写入。

ObjectStack 原生 ApprovalService 的所有 resubmit 入口必须在写审批动作前校验 Forge 产生的材料绑定；没有绑定、绑定过期、材料已变化或原提交人不符时拒绝，原审批状态和流程保持不变。绑定消费与审批动作写入须在同一数据库事务中确定结果。原生自动化恢复是事务后的另一阶段，须沿已有流程运行回执按同一幂等键核对并可安全续跑；数据库提交成功但恢复结果未知时不能写成“未提交”，也不能盲目执行第二次审批动作。恢复后下一轮审批请求读取新材料快照，旧轮次快照及意见保留。桌面不能调用原生 resubmit 路由绕过业务校验；Forge 不另建审批状态机或调度器。网络取消只停止尚未提交的本地准备或等待；若业务动作已提交，必须核对回执，取消 Weave 运行不撤销 Forge 结果。审计记录账号、组织、原请求与新请求、业务对象、源与新材料摘要、幂等键、动作结果及时间，不记录合同正文或长期凭据。**实现、上线和本轮业务验收分别以版本锁、环境证据与合同场景为准；契约存在不等于完整场景已通过。**

当前接口为 `POST /api/v1/approvals/requests/{requestId}/workbench-revision`，请求体遵守 `approval-revision.schema.json`：`returnVersion`、`sourceMaterialVersion`、UUID `idempotencyKey`、一份 `primary` 和本轮员工明确选定的 `attachments`（不设文件份数上限）。每份引用都含 Forge `fileId`、名称和 SHA-256；兼容旧调用时可省略 `mediaType` 与 `bytes`，此时 Forge 仅按 UTF-8 文本校验。新调用必须把 `mediaType` 与 `bytes` 成对提交；PDF/DOCX 主件或附件必须提供这两个字段，MIME 限为 `application/pdf`、`application/vnd.openxmlformats-officedocument.wordprocessingml.document`，长度须大于 0。文本 MIME 仅接受 `text/plain` 或 `text/plain; charset=utf-8`。

`mediaType` 和 `bytes` 是对已上传 Forge 文件的预期值，不是内容来源或授权凭据。Forge 从当前员工会话、原生审批请求及 ObjectStack `sys_file` 元数据确定员工、组织、业务对象、文件所有人、归属和存储键；随后用原有 ObjectStack Storage 下载实际字节，核对声明 MIME 与已存 MIME、名称扩展名和文件签名、声明长度与元数据长度、实际字节长度及 SHA-256。PDF 必须以 `%PDF-` 开始；DOCX 必须使用 `.docx` 名称并具备 ZIP 文件签名；文本仍须通过严格 UTF-8 解码。每份不超过 2 MiB、整包不超过 8 MiB。Office 文件还须属于当前审批组织，并使用 `scope=attachments`、`acl=private`，使下一轮审批上下文能够按原件权限读取。Office 文件的 MIME 或字节元数据缺失/不匹配、原始字节或摘要不符、文件不属于当前员工/组织或绑定到别的合同，均失败关闭；请求不接受 Base64、存储键、任意 `userId`、合同记录 ID 或审批处理人。

`GET /api/v1/approvals/requests/{requestId}/workbench-revision/{idempotencyKey}` 只读核对原员工的回执。`resumed` 表示已观察到下一轮原生请求；`prepared` 表示新材料已固定但原生动作尚未确认；`resume_unknown` 表示动作已写但下一轮未观察到。相同请求键、身份、退回版本与准确文件清单返回原绑定；同键换文件、换摘要或换元数据报 `409`；请求或退回版本过期报 `409`，非原提交人或不可见请求报 `404`，存储 MIME 不支持报 `415`，字节/摘要/签名不一致报 `422`，单件或整包超限报 `413`，服务不可用报 `503`。`newVersionDigest` 覆盖按原顺序排列的主件及附件引用、已验证 MIME、实际字节数和 SHA-256。只有 `resumed` 可向员工称为递交成功；其余状态不得自动重放原生动作。

原生审批服务创建下一轮请求后，Forge 应将已绑定的新主件与附件冻结到该请求快照。PDF/DOCX 仅以 `originalFiles` 元数据返回；小李、小陈等当前合法处理人仍通过 approval context 核对本轮 `requestId`、冻结 SHA，并调用受保护的原件读取路由获取字节。下一轮上下文必须指向新材料，而旧请求仍保持旧版本和原意见。

当前候选中同键同材料重试返回原绑定，换材料报 `409`；账号无权或事项不存在返回 `404`，过期轮次 `409`，文件校验失败 `422`，输入超限 `413`，服务暂不可用 `503`。这条接口由 Forge 插件填补原生能力缺口；Weave 团队正常的 Forge 业务动作继续通过 ObjectStack MCP `run_action`，不为续办另造团队调度。**限制：** 当前插件的准备记录与原生审批动作尚不能作为一个跨自动化恢复的原子操作；首次调用若在动作前失败，回执保留 `prepared` 且不会自动重试；多进程同时递交和真实数据库恢复尚未验收，C06 不能关闭。文件上传回执丢失时可能留孤立文件，仍由 N01 处理。

- `result`、`failure` 是通知，告知发起员工团队运行的终态，不要求 Pi 持续等待或轮询。
- `revision_required`、`human_review` 是可操作事项。它们必须指向同一笔原工作、明确材料版本、退回原因、责任员工、返回位置和复核范围；被指派员工打开事项后，桌面才把这些上下文交给该员工的 Pi。
- 正式业务提交前，智能体团队发现材料问题，以 Weave“需要补充”运行结果及系统事件返回原员工，不创建 Forge 修改事项。进入正式业务流程后，人类员工退回或业务规则要求补件，才通过 Forge 受控动作与原生审批形成可办理事项。合同只是首个验证场景，不改变这两个阶段的职责；具体实现缺口见阶段问题清单，不因契约写明而视为已完成。
- 退回后的新材料形成新版本，保留父事项和原运行引用。默认回到原复核位置；能够证明只影响部分成员时可请求局部重跑，实际执行范围仍由 Weave 校验。
- 创建和状态更新使用 `source.idempotencyKey` 去重。重复投递不产生第二个员工事项；并发办理必须由 Forge 的记录版本检查拒绝旧写入。
- Weave 的人工节点仍可作为团队运行中的同步等待点，但员工入口只有原生收件箱：等待开始时以 `human_review` 事件通知处理员工（见上文“团队运行事件”）。处理员工以自己的身份办理，不能借此替换原任务执行主体或取得发起人的长期凭据。

2026-09-22 方向纠偏：已有 `create_employee_work_item` 签名 webhook 与通用事项对象为未验收试验，不再作为本链路的目标调用契约或部署前提。团队主动发起的修改、复核与提交通过 Forge MCP 业务能力完成；系统运行事件另行自动接入原生收件箱。具体 MCP 工具名、受限委托、原生事项映射、幂等回执查询及错误/取消/审计字段，须在原生能力核验后补齐并验证；当前 schema 或接口存在不代表此链路已接通。

## 审批退回与材料版本

### 每轮材料持有与历史原件读取

本节是本批实施目标；历史数据修复与真实验收状态见项目状态页。

- Forge 首次提交和退回修订共用材料集合校验：主件属于提交集、当前员工有权使用每份文件、服务端读取字节并计算摘要。正常页面和受控 MCP 使用同一业务规则。旧 `contract_submit_frozen_material` 只兼容与历史提交记录完全匹配的回执读取，其余明确拒绝；普通旧提交入口不得绕过完整集合校验。
- 审批提交、修订和上下文读取不再另设 10/11 份的文件计数限制。保留单件与合计字节、文件类型、重复引用、身份与摘要校验；不能出现提交集合合法却在读取环节因另一份数限制被拒的情况。
- 每轮提交记录保存不可变的主件、配套附件、摘要与审批请求关系，并通过 ObjectStack 原生 `sys_attachment` 持有原件。替换当前合同文件只改变当前指针，不撤销历史轮次持有。原生文件被替换后可能已标记软删除；只有精确匹配有效历史持有关系的读取器可以访问仍保留的字节，不能开放任意已删除文件。保留和回收继续使用原生文件生命周期，不另建文件库或垃圾回收器。
- 历史只读路径是 `GET /api/v1/approvals/requests/{requestId}/workbench-history/files/{fileId}/original`。Bearer 员工先经原生 ApprovalsService 校验，且属于同组织、该轮原提交人或该轮已冻结的实际审批参与人。当前岗位、管理员身份和通知正文不能替代历史参与证据；不能证明参与关系时拒绝。
- 文件必须同时匹配该轮审批不可变快照和提交/修订记录的原生持有关系。`If-Match` 必须精确匹配冻结 SHA；存储字节仍校验 MIME、长度、签名与摘要。响应和错误沿用现有原件路由约束，不返回签名 URL，不从当前合同指针猜测旧原件。仅返回文件字节，不授予办理、重提或恢复权限。
- 当前审批上下文路由保持其当前事项约束；旧轮次被新轮次取代后仍拒绝当前办理。历史读取与当前办理分别授权。员工本人原件读取同样识别本人合法历史持有，确保已冻结运行不因新轮次替换文件而失效；仍不得跨员工或跨提交集合使用文件。
- 保存材料、创建审批及回执恢复使用同一正式提交记录协调；重复同内容返回原回执，同键不同内容拒绝。失败保存原状态与明确可恢复位置，不把审批未创建写成已提交。并发与进程中断按真实数据库和原生生命周期验证，不以仅内存模拟代替。

### 审批辅助与当前事项办理范围

本节是已批准实施的边界，代码与真实桌面通过状态以项目状态页为准。员工从本人当前审批事项请求 Pi 协助时，Host 重新读取 Forge 已授权的审批上下文，并固定账号、对象、记录、请求轮次和材料快照版本。界面不能把自行拼接的材料文本作为授权依据。

- 审批辅助使用与该事项关联的独立会话，不沿用无关事项或普通聊天的历史。不同账号、记录或请求不得共享上下文绑定；新一轮必须明确其对应的审批快照，历史意见仅作标明来源的历史内容。
- 辅助会话初始为企业只读。员工在后续实际轮次明确表达办理意见后，仅可使用 Forge 当前事项返回的允许动作；不把整段会话升级为通用写入权限。企业交接、其他记录写入、退回修订提交及可能继续执行的恢复工具仍由 Host 拒绝。本地文件能力不是企业权限，不据此宣称完整操作系统沙箱。
- 审批提示只描述当前事项、环节、允许范围和材料来源，不在通用桌面固定合同、交付或商务检查口径。完整文本、部分提取、未读取内容的限制须原样保留。
- 错误：账号已变化、上下文过期、原请求已被后续轮次取代或不再有权读取时，拒绝绑定并保留员工已有草稿；不得自动换成另一条事项或旧上下文。
- 审计只记录账号范围、事项/快照关联与被拒绝的操作类型，日志不记录文件正文或会话凭据。

当前事项办理通过 Forge 选择性开放的原生 MCP `run_action`，复用 ObjectStack 原生审批服务，不直接暴露系统对象写入、不新增审批或通知体系。首批覆盖原生同意与退回修改；业务对象上开放哪些动作由 Forge 配置，桌面不根据人物、合同或审批节点写分支。

- Forge 的当前事项上下文可返回 `availableActions`：每项含 `label`、`description`、`execution`（固定 `tool: run_action`、`actionName`、`objectName`、`recordId` 和 `params`）及 `inputs`（员工可填写的字段定义）。固定参数含原生 `approvalRequestId`、`itemVersion`、`sourceMaterialVersion`；本批员工输入为意见 `comment`。未获当前办理权时返回空目录。`itemVersion` 来自原生状态、当前节点/轮次、待处理人员和动作历史，不能仅用材料摘要代替事项版本。
- Host 从已绑定事项读取并固定目录；Pi 只引用当前目录项并填写声明字段，不提供操作者、对象、记录、请求、版本或工具地址。账号、员工实际消息与轮次、目录指纹留在 Host。发送前重读事项并匹配；换账号、改变要求或事项版本变化使旧调用失效。
- Forge 动作处理器从认证用户及会话重建非 system 的业务调用上下文，不向原生服务传递 MCP 脚本的 system 提升身份。重新核对事项与记录关系、材料和事项版本、当前处理资格；原生服务决定通过、退回、最大修订次数导致的拒绝及下一事项。
- 相同请求的重复办理以原生动作历史核对，不新建第二套回执账本。本批 Forge MCP 连接入口以当前 PostgreSQL 事务的 advisory lock 串行同一原生请求，锁内核对版本、历史并调用原生服务；多实例共用同一数据库时生效，不新增表。内存锁不能宣称并发安全。直接原生 REST 未经过此连接入口，其并发保障尚未验证，不宣称所有审批入口均已补齐。同一员工、原版本和相同意见已实际生效时返回原生重复结果，不再写意见；意见不同或其他人/轮次已改变事项时明确冲突。
- HTTP MCP 保留标准 JSON-RPC `result` 外壳；MCP `content` 的 text JSON 可以是 Forge 原生 `ActionEnvelope`（`ok`、`action`、`objectName`、`recordId`、`result`）。调用方只在 `ok=true` 且动作、对象、记录均与本次固定调用一致时解出内层业务回执，再校验其 `requestId`、`recordId`、调用前 `itemVersion`、`sourceMaterialVersion` 和决策/状态/布尔结果；包装正确不能替代业务回执有效。原生错误或身份/版本不符不转成成功。
- 退回后最新事项版本变化是预期，不拿新的事项摘要否定已匹配调用前版本的成功回执。若只观察到原生历史，而历史不能证明动作对应的材料与事项版本，只返回观察结果并保持 `unknown`；不伪造确定回执、不新建重复办理、不新增平行回执账本。
- 结果未知先读取原生事项及动作历史，不盲目重放。返回真实决策、原生状态及是否重复；办理成功与整个审批完成分别表达。账号失效、越权、陈旧版本、意见无效及服务不可用分别保留既有认证、权限、冲突、校验和可恢复错误，不显示为暂无事项。

### 本次对象绑定与续办的共同约束

调用者为受信任的桌面 Host，身份来自当前 Forge/Weave 登录及实际员工轮次。Host 在冻结包中保存 `businessContext`，登记固定输入时发送 `business_record: { object_name, record_id }`；不得从远端成员生成的任务正文反推授权对象。首批每次工作最多绑定一条业务记录，无对象的分析/创建动作可以不传。记录绑定表示本次操作范围，不等于记录内容版本或业务权限授权。

- Weave 将对象绑定计入整个登记请求的摘要，并在现有任务委托 `resources` 内保存 `forge-record`（`id`、`object_name`、二者规范 JSON 的 `sha256`）。不新增任务库或授权引擎。相同登记 UUID 更换对象返回 `409 input_registration_conflict`，不得刷新为另一个对象。
- 实际业务工具由 Forge 目录的 `requiresRecord` 决定是否必须绑定记录。必须绑定却缺失或对象类型不匹配时停止构建工具；运行时将冻结记录注入 `run_action.recordId`。模型省略该参数即可执行；显式传入另一记录在网络写入前拒绝。明确声明无需记录的动作不获得 `recordId`，即使同一任务为其他动作绑定了记录，模型也不能另填。Forge 在实际执行时仍校验员工权限及当前状态。
- Host 的业务查找没有正相关候选就返回未找到；有候选也仅供 Pi 根据员工上下文选择，不因只有一条而擅自确定对象。查找仍不等于员工最终意图正确性已被证明。
- 新员工输入或切换账号使尚未交付的旧轮次及其异步能力目录失效；已进入服务端的动作只能核对回执，取消不等于撤销。恢复原包仍须当前员工明确继续原版本，不能替换绑定对象。
- 审计沿用输入版本、员工、动作、登记摘要、运行及回执关联。模型提示、通知正文和工具调用文本均不是新的授权来源，不写入凭据。

版本、续办和工具参数必须共同满足：打开原事项取得最新业务状态及允许动作，办理时引用本次固定输入，修订形成新版本而恢复保留旧版本。此处首批只实现记录标识约束；文件参数保护、业务记录并发版本、完整主件附件包和结构化参数表达仍属于 C02/C05/C11，不能据此关闭这些问题。总仓桌面与 Weave 源码候选需配套部署；旧服务不识别新字段时明确失败，不降级成正文提示。

- Forge 原生审批请求及其动作历史是审批意见、处理人和状态的权威来源。桌面按当前员工身份读取本人待办；退回时读取 `GET /api/v1/approvals/requests/{id}/actions` 的最新 `revise` 意见，打开事项后再读取请求快照和有权访问的文件。通知仅用于提醒，不替代审批请求。
- 销售修订合同包时，必须明确绑定主合同和所有待复核附件。每份文件固定 Forge 文件标识、名称和 SHA-256；Forge 校验员工、合同、退回审批和文件归属后保存新材料清单。桌面始终不能直接调用原生 `resubmit`；Forge 材料动作经原生守卫原子继续审批。
- 修订绑定重复调用同一清单返回原结果；同一修订轮次更换清单必须显式报冲突。原生审批只接受原提交员工的受信任身份与有效绑定，ObjectStack 建立下一轮请求并重新解析审批人。旧轮次意见和文件保持可读，不覆盖旧快照。
- 桌面交给 Pi 的是当前员工可见的退回意见、业务字段及经摘要校验的文件正文。跨账号切换必须隔离本地会话与工作目录；仅隐藏旧会话列表不足以保护 Pi 的文件读取范围。

## 待办完整分页与账号边界

- 桌面从 ObjectStack 本人的原生通知与审批请求分页读取，按原生游标或已确认分页协议继续，直到明确结束；固定200条通知、50条审批不是业务总量上限。不得另建通知或待办存储。

## 受限任务授权与原输入续办

本节为本轮实施契约，部署及真人验收完成前保持待验。身份、签名与员工桌面会话验证复用 ObjectStack，任务授权生命周期与桌面会话分离；Forge 只保存本次业务授权范围与幂等记录，不创建另一套账号、组织、登录会话或业务调度器。

1. Host 先保存本轮固定意图并上传选定材料。`POST /v1/workbench/dispatch-inputs/prepare` 携当前 Weave 身份和固定登记请求，只读返回 `input_revision_id`：已有同内容登记沿用原值；新登记按受认证的workspace/user/registration_id稳定派生，不接单、不写任务队列。同登记更换内容409，越权404，不返回别人登记。
2. Host 用员工原生 Forge 会话调用 `POST /api/v1/apps/forge/task-delegations`。请求/响应遵守[任务授权签发机器契约](task-delegation-request.schema.json)，请求含 `request_id`（发行幂等键）与 `scope`，scope含准确 `input_revision_id`、`registration_id`、`task_sha256`、`workflow_id`、`workflow_version`、`allowed_actions`、`resources` 和可选 `business_record`；资源沿用固定输入的原生文件/记录引用结构。员工与组织由原生会话取得，不能从请求指定。Forge验证现有权限、所选记录与材料，保留来源桌面会话的审计引用，使用原生auth的server-only签名能力发行；同键同范围且原工作未永久关闭时返回同一授权记录，同键换范围409，续期用新的持久请求键。相同原输入已有运行终态、员工取消或账号禁用的永久撤销事实时，新旧发行请求键都返回409 `FORGE_TASK_REVOCATION_FINAL`；不能通过增加generation跨过历史撤销。
3. 响应 `version="1"`、`token_type=forge_task`、`access_token`、`grant_id`、`generation`、`issued_at`、`expires_at`、`scope_sha256`、`scope`、`subject`（id/organization_id）、连接 `issuer` 及稳定 `identity_issuer`。有效期最多24小时且与已交接任务独立于桌面会话；运行终态或员工取消触发撤销。token只在Host进程与Weave加密委托内使用，不暴露员工；签名audience为Forge任务连接，通用CRUD、原生MCP、auth和其他发行入口不接受该token。
4. Weave登记沿已有API提交固定输入及准确input_revision_id，专用 `X-Weave-Forge-Authorization` 只接上述任务token。`GET /api/v1/apps/forge/task-delegations/current` 用该token返回 `version="1"`、`active=true` 和在线有效性、上述可信身份/范围/代际与实际时间；Weave与本次账号、输入、图版本、资源和动作逐项核对，不在本地伪造有效期。
5. 成员仅通过 `POST /api/v1/apps/forge/task-delegations/mcp` 调用原生MCP能力。 `GET /api/v1/apps/forge/task-delegations/objects/:objectName` 复用原生具名对象元数据，保留fields与完整动作params，仅返回本次record/allowed_actions对象及所选动作，用于补足MCP摘要丢失的原生file类型；任务token不能改走通用/meta。Forge连接校验token、授权记录代际、绑定组织仍有有效原生成员资格及当前原生权限，再调用原生MCP桥；只暴露声明动作及范围内只读元数据/记录，拒绝通用CRUD、范围外动作/记录/材料和再次发行。`GET /api/v1/apps/forge/task-delegations/files/:fileId/original` 只服务scope内准确来源的文件，核对原生权限、长度及摘要，复用现有原件持有规则。授权撤销、过期、员工停用或组织资格结束后每次调用都拒绝；退出桌面登录不撤销已交接授权。
6. 工作上下文提供 `run.authorization`，包含 `status=active|renewal_required|not_applicable` 和必要可读原因，不带token。只有确认尚未发送的授权拒绝才标记 `authorization_expired`/`no_effect` 并沿现有parked runtime等待，保留操作位置与检查点；已开始或未知效果继续只读核对，不因续期而重发。
7. 原员工从该工作打开续授权。`run.authorization.grant_id`仅供Host对同一原工作调用撤销接口，不作为产品可见编号。`POST /v1/workbench/dispatch-inputs/:id/authorization` 接新任务token和 `expected_generation`（并发围栏）；仅替换同账号、同原输入和完全同范围的授权，保留输入/运行/操作身份。过期或旧代际409，越权404。随后只在有无副作用证明的授权等待上沿现有stage_retry恢复；没有证明的旧终态运行明确拒绝安全自动续办，不伪改终态、不创建新输入掩盖失败。授权更新完成但stage_retry尚未排队时，原parked运行返回 `status=active, can_renew=true`；该组合表示原无副作用等待仍可恢复，不是新授权到期。客户端必须能读回该状态并以原run、输入和retry_node_id恢复，不能因active而丢弃原恢复证明。
8. `DELETE /api/v1/apps/forge/task-delegations/:grantId`撤销授权：任务令牌只可撤销自身，reason为`run_terminal`；员工会话只可撤销同员工、同原生组织的授权，reason为`employee_cancel`。返回`{version:"1",grant_id,revoked:true,reason}`；同授权重复200，保留第一次撤销原因。同grant_id的历史终态/取消/禁用构成持久关闭围栏，current及发行均核验；并发新代即使晚于撤销插入也不得获得有效业务权限。发行在同一授权对象内先记为issuance_pending，原生事务内复验失败回滚；提交后、签名返回前再复验本次调用者会话，并以pending且未撤销的条件CAS确认。提交后会话失效只关闭该仍pending的发行记录为issuance_aborted，保留nonce作为未发行证据；已经由同请求另一副本确认的授权不被迟到失败撤销。current只接受最高已确认代，pending或已放弃的新代不替换原有效代。issuance_aborted只关闭本次发行，同键重复409，新请求键可合法重试原范围；代际分配使用历史最大值加一，expected_generation比较当前已确认代，已有未确认候选时拒绝另一新键竞争。这不把父会话活性重新加到已交接任务。Weave在运行终态提交后持久登记撤销需求，沿现有后台连接清理入口退避重试；Host以精确原run上下文取得grant_id，直接用本人Forge会话确认employee_cancel撤销后，再仅携WeaveJWT发送原run的stop；无委托或开发运行仍走原stop。撤销未确认不能宣称已取消。员工取消不回滚已有业务效果。
9. 原生 `POST /api/v1/auth/sign-out` 负责主动退出吊销桌面会话；已交接任务继续，不把退出当作员工取消；Host先捕获旧账号会话再调用，退出始终清本地，迟到结果不得影响新登录账号。200（或原会话已明确失效）记确认，网络/服务故障标远端吊销未确认并给必要提示；普通401清理不再触发另一次登出请求。

终态撤销与后续新任务分开：当前输入的只读运行已失败，或已成功交付“完成/需要补充”且原动作范围明确为空，权威动作回执也明确为空时，原员工可在新消息中明确授权复用准确材料版本，形成关联原工作的独立新输入。成功终态的合法 needs_input 还允许原动作范围非空，但来源必须当前、未关闭/取代，范围完整可读取，业务回执严格为空，且不属于仍可续授权的等待；已有失败、未知或任何动作记录均拒绝。Host再次读取本人来源与固定输入，核验账号、材料、结果和当前状态，按本轮消息生成新登记与发行幂等键，选择当前可用发布版本、取得新范围委托；原父版本只保留为来源证据，不续期旧授权、不恢复旧运行，不继承原写权限。失败或普通完成且原写范围非空仍按原保护拒绝。失败且无有效交付的重启仍限只读；非终态等待、取消、关闭、取代或事实缺失不能借此重放。产品仅对服务端确认可续办的当前parked工作提示更新授权。

错误保持分层：401任务token无效/已过期/员工已停用；403当前业务范围、原生组织资格或权限拒绝；409发行内容冲突、输入内容冲突或授权代际冲突。发送前的授权拒绝附 `error.no_effect=true`、`error.phase="authorization"` 及原生错误码；自动续办只接受明确过期或可续授权的代际替换401证明；员工取消返回403 `FORGE_TASK_CANCELLED`，账号禁用返回401 `FORGE_TASK_SUBJECT_INACTIVE`，两者保存首次拒绝证明且同输入重新发行返回409 `FORGE_TASK_REVOCATION_FINAL`，不能续授权、stage_retry或走失败边绕过，403组织/业务权限拒绝及未知错误不能因重新授权而重发；发送后的网络不确定不能使用此标志。审计只记原生主体/组织、授权与输入身份、范围摘要、发行/续期/拒绝/退出时间和结果，不记录员工会话、task token、材料正文或模型私有思考。

Weave对Forge投递人工等待及终态事件时，组织取固定输入登记的Forge原生组织，受理员工取可信原生账号；不能用Weave workspace充当Forge组织，也不能猜测处理人。旧只读输入仅在同账号外部绑定唯一且可验证时补足组织。

工作上下文 `source.input_status=current|superseded|closed` 和可选 `superseded_by_input_revision_id` 由同workspace/user且准确root/parent工作链的已接受输入确定。只有确认同工作链取代关系时，桌面才退出旧needs_input待办投影；同会话的无关新工作、closed状态或读取失败不证明已办。原通知、原动作事实及Forge业务状态不修改。

## 原生本人收件箱分页连接

ObjectStack 17.3原生notifications只能返回最多200行，未接受offset/cursor；审批原生limit/offset+total已可分页。本轮只为该已核实缺口增加 `GET /api/v1/apps/forge/workbench/inbox`，复用sys_inbox_message和sys_notification_receipt，身份取原生当前员工并实时核验绑定组织的有效成员资格，不接受目标user/org，不另存通知或待办。

请求 `limit`（1–200，默认100）及可选 `cursor`。返回 `version="1"`、`notifications`（id/type/title/body/read/actionUrl/createdAt，与原生投影相同）、`next_cursor`（结束时null）、`has_more`；按created_at与id稳定降序进行keyset分页，游标绑定账号、组织和第一页边界，拒绝跨账号/组织复用及损坏游标。只读原生收件箱；read状态由同本人、同notification、inbox channel的原生receipt决定。页失败或无法证明完整时保留可见部分和来源错误，不能宣称完整或空待办。
