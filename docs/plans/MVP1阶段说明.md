# MVP1 系统验收目标与开发方案

状态：当前有效的 MVP1 目标与执行方案；尚未完成系统验收。

2026-09-23 阶段归档：用户确认以“已有交接、提交审批和人工退回”作为[MVP1 第一阶段](../releases/001-MVP1第一阶段里程碑.md)成果。下列完整目标不因此缩减或变为已通过；阶段后的修复按[分类与优先级](问题清单.md)推进，业务差异与共性能力分开处理。

本页维护当前目标、范围和执行顺序；变更通过 Git 历史追踪。具体执行顺序见[落地步骤](MVP1阶段说明.md#落地步骤)，桌面助手与团队的接入方式见[桌面助手与团队接入方案](../architecture/系统架构设计.md#桌面助手与团队接入)，实际进展只在[项目状态](../项目状态.md)维护。

产品采用同一个桌面客户端：员工使用工作模式，开发者按权限增加开发模式。首个业务场景使用销售合同交接，同时验证一次团队修改和一次 Forge 应用修改。

桌面基线于 2026-09-21 再次确认：使用本仓 `desktop/` 的 GooeyPi 产品改造。统一登录、工作模式、开发者配置与运行可视化均在该入口实现和验收；旧 DSH/Host 桌面不属于 MVP1 交付入口。

账号采用一条主路径：管理员或用户在 Forge 注册账号并通过权限集授予产品能力，首次从 Workbench 登录时由 Weave 按受信任的 Forge 用户标识自动建立本地绑定。用户不再注册或输入第二套 Weave 密码。Weave 不独立维护员工、开发者和管理员角色；它验证 Forge 权限并继续独立管理团队执行。绑定、登录和业务授权是三件可审计的事实，界面上合并为一次登录体验。

以下均为目标标准，不代表当前已实现或已验收。

## 当前先交付：第一条完整业务流

首个业务验收以“合同评审通过”为终点，包含实际文件、团队检查、团队退回、人工退回和员工续办。只完成团队交接、工具调用或待办显示不能宣布通过。本批先交付下列闭环；D5 的完整隔离调试与 D6 的 Forge 应用修改保留在后续 MVP1 开发验收批次，未通过前不宣称全部 MVP1 完成。

1. **开发者配置可用团队。** 小周在桌面完成团队/成员/单流程的新增、原位编辑、移除、保存、调试与更新，给成员绑定 Forge 真实能力；保存前不落盘，已发布版本不被未保存编辑影响。重开读回一致，并用一次指令调整证明团队行为确实改变。桌面每团队只开放一个流程，后端保留多流程。
2. **销售交付明确版本。** 小王与 Pi 准备合同和附件，明确授权后提交；账号、实际员工轮次、材料和幂等键固定。接单后 Pi 结束等待，团队持续运行。至少一种场景实际使用的办公文件完成远端读取、下载和打开；现有文本交接只是中间成果。
3. **团队检查结果可续办。** 团队发现具体缺项后结束本次运行，Weave 自动把“需要补充”的结果关联到原员工收件箱。销售离线后重新登录仍能看到，打开后 Pi 读取原工作、固定材料和检查意见，修改并递交新版本。新一轮检查关联原工作，不要求原 Pi 会话一直在线，也不为团队检查另建 Forge 业务事项。
4. **进入正式人工评审。** 有明确“提交评审”授权且团队检查满足要求时，通过 Forge 动作登记准确版本并发起评审；只有“给团队看看”的授权不得推进正式审批。Forge 解析交付、商务两名真实处理账号，各自在桌面打开、查看和办理本人事项。
5. **人工退回后办完。** 至少一位复核人经其 Pi 提交退回意见，销售打开修改事项、修改并重交，Forge 按规则回到原复核位置。首批采用保守的版本规则：新版本重新完成交付与商务两项人工复核；不因旧版本已通过而自动沿用。两人通过后，Forge 保存正式“评审通过”，桌面显示同一结果，独立审计者从 Forge 页面核验合同版本、材料、处理人和意见。

本批必须补齐的能力和验收断点集中在[落地步骤](MVP1阶段说明.md#落地步骤)。团队检查结果由运行通知自动送达；正式业务提交和退回由 Forge 动作与原生审批承接，人员和返回路由由 Forge 决定，遵循[统一产品架构](../architecture/系统架构设计.md#运行反馈业务动作与员工续办)。

本批同时验证：团队失败也有自动反馈；员工“先别发”；缺文件不提交；重复调用与业务已成功但回执丢失；过期事项和并发旧版本被拒绝；账号切换不串数据；离线、重开后能续办。没有证据的环节保持待验收。

后置：订单到回款的完整 OTC、任意业务域、复杂条件/循环设计器、受影响成员自动局部重跑、能力市场与能力包管理界面。需要写工具的开发调试只能进入已隔离的测试环境；隔离未具备时阻塞该调试步骤，不伪造试跑成功。

## 一、员工工作模式

| 编号 | 验收目标 | 实际检查方式与通过标准 |
| --- | --- | --- |
| E1 | 一个账号登录后即可工作 | 先在 Forge 注册真实员工账号，再在 Workbench 使用同一账号登录；首次登录自动建立 Weave 绑定并连接所属组织。后续不要求注册或登录第二套账号。能看到本人获准使用的能力和待办；切换账号后，材料、会话、绑定和待办不串用。 |
| E2 | 本地准备材料 | 助手能在授权工作空间内读取、整理和修改合同，成果保存为可打开的实际文件。个人草稿不会自动成为正式业务记录，也不会因登录企业账号而上传整个目录。 |
| E3 | 明确递交工作 | 用户说“提交这份合同”后，系统明确本次递交的文件版本、目标和范围，生成可持续查询的工作编号。后续修改本地文件，不得悄悄改变已递交材料。 |
| E4 | 按业务规则办理 | 团队使用当前员工身份发现并调用 Forge 允许的业务动作；缺材料时列出具体缺项，补齐后继续同一项工作。需要确认时展示具体内容并保存决定；已有授权不反复询问。确认提交不能被显示为审批通过。 |
| E5 | 看懂执行进展 | 任务能区分执行中、等待补充、等待人员处理、失败、取消和完成。说明正在做什么、卡在哪里、下一步由谁处理；状态来自实际执行记录。关闭再打开客户端后仍能查到。 |
| E6 | 跨员工接续办理 | Forge 产生真实待办，处理员工在自己的桌面收到并查看关联材料，助手协助准备处理意见，最终以处理员工身份办理。通知与待办关联同一项工作，重复通知不重复办理。 |
| E7 | 获得可核验成果 | 至少完成一种本场景实际使用的办公文件格式的上传、下载和打开验证，不能只交付文本摘要或链接。正式合同状态、处理人和交付物可关联，另一身份从 Forge 独立读回一致结果。 |

复杂业务详情可以从桌面打开 Forge 原生页面。桌面集中呈现工作、待办和成果，不重复建设整套业务页面。

## 二、开发者开发模式

| 编号 | 验收目标 | 实际检查方式与通过标准 |
| --- | --- | --- |
| D1 | 看见可开发对象 | 列出有权开发的团队和 Forge 应用，标明当前环境、已发布版本和草稿。能区分“允许使用”“允许修改”“允许发布”，权限由服务端落实。 |
| D2 | 看懂团队配置 | 查看团队目标、角色分工、技能、工具绑定、输入输出、步骤关系、分支及人工处理点。提供关系图总览，点击节点可查看完整的可编辑定义。团队分工和工作流都必须从桌面完成新建、查看、修改和删除（有历史时为归档）的完整验证。 |
| D3 | 修改并检查差异 | 从已发布版本创建草稿，通过配置编辑或助手修改角色、技能、工具和步骤关系；修改都落到同一份定义，可查看保存前后的差异，并校验引用与配置有效性。每一项写入都要刷新回读；归档后从开发列表移除，已发生的运行和版本记录仍可追溯。 |
| D4 | 从运行定位配置 | 一次试运行能关联准确版本，在关系图或时间线上显示实际经过的步骤。可以查看授权范围内的输入输出、工具调用、耗时、用量、失败及重试记录，并返回对应配置位置。 |
| D5 | 两种调试都可用 | **只读分析**可读取获准线上数据，正式写入和外部发送由工具权限层禁止；**隔离试跑**可执行真实创建、提交和审批，但只写入测试环境，通知进入测试通道。结果清楚标明环境与测试性质。 |
| D6 | 修改 Forge 应用 | 完成一个具体需求，例如“合同增加交付地点并在提交时校验”。在隔离分支修改字段、页面和业务规则，展示差异，完成检查、预览与业务验证；相关团队同步调整材料提取和缺项提醒。 |
| D7 | 发布可追溯版本 | 团队与应用分别形成版本，发布者能看到测试证据、具体变更和目标环境。新任务使用指定新版本；既有任务保留原定义关联。涉及应用规则变化时，要验证在途业务兼容性，不默认整个系统已自动冻结。 |

当前编辑体验统一为查看与编辑一体化：保留团队卡片和可操作流程图，无独立编辑按钮，点击配置项直接修改，模型、工具和关系从目录选择，高级参数折叠。新增成员先填名称和职责。修改只在本地内存中保留，显式保存后才存储；保存草稿与更新团队分开，调试从当前流程进入，生效从修改详情发起。流程通过节点添加、连接、移除调整；一团队在桌面只展示一个流程，无流程时才出现新建流程入口。

空组织必须能够开始开发。MVP1 的最小入口只要求团队名称和目标，创建时同步建立一个负责人和一个执行成员，完成后直接进入成员配置；成员扩充、流程编排和发布不塞进首次创建步骤。

## 三、共同必测的异常与证据

- **权限拒绝**：员工无法通过对话或直接调用修改团队、发布应用、读取未授权材料；开发权限不自动扩大业务数据权限。
- **重复与中断**：重复提交、客户端断线、业务成功但回执丢失时，不重复创建合同。结果未知必须先核对；可恢复、可安全重试、需人工处理要明确区分，不承诺所有步骤都能原地续跑。
- **等待与取消**：等待人工期间任务持续存在；取消后能确认调度和执行是否停止，并说明哪些业务动作已经发生。
- **版本与独立读回**：记录桌面、Weave、Forge、团队和契约版本。以发起员工、处理员工、开发者和独立审计身份验证。模型声称完成、健康检查通过、页面可打开，都不能单独算业务通过。

## 四、开发阶段

| 阶段 | 主要交付 | 阶段结束条件 |
| --- | --- | --- |
| 1. 身份与观察基础 | Forge 注册、登录与权限集、Weave 自动绑定、逐任务委托、基础任务状态与事件关联 | 同一账号一次登录；首次绑定和再次登录均可读回；Forge 授权后开发入口生效；越权调用被拒绝且可定位 |
| 2. 员工完整闭环 | 材料交接、Forge 动作、必要确认、跨员工待办、文件成果与业务回读 | E1–E7 在真实环境逐项通过 |
| 3. 开发者工作区 | 配置查看与编辑、版本差异、关联运行、两类调试、应用修改与发布 | D1–D7 通过；改进后的团队与应用被员工实际使用 |
| 4. 组合验收 | 异常验证、版本记录、安装与重开验证、证据整理 | 全部必测项有结果，失败项有明确记录，不用组件测试代替系统验收 |

开发者工作区中的基础查看能力前置到阶段 1–2，用于观察真实运行；草稿编辑、隔离试跑与发布在阶段 3 完成，详见[落地步骤](MVP1阶段说明.md#落地步骤)。

总仓负责桌面、共享契约与组合验收；Weave 组件负责团队定义、执行及观察能力；inoForge 负责业务规则、动作与应用变更。按确定提交集成，先本地检查，再部署指定线上开发环境联调。

## 五、第一版范围

macOS 完成完整验收，Windows 保持可构建，尚未实测的交互与执行能力单列。桌面待办作为必需通道，飞书等通知作为后续扩展。暂缓全业务域覆盖、通用拖拽设计器、云开发平台和大型运维看板。

MVP1 不引入 Cerbos、OpenFGA 或另一套统一身份平台。只有当真实场景证明 Forge 权限集无法表达团队产品权限时，才另立后续方案。

## 落地步骤

### 先走通完整业务流

| 顺序 / 工作项 | 本批必须做到 | 现场验收结果 |
| --- | --- | --- |
| 1 / FLOW-01 | 核实 ObjectStack 原生审批、消息及权限；定义 Forge 的业务 MCP 动作与受限身份委托 | 明确复用的原生对象与动作；可发现的业务能力包含授权材料读取、合同登记/提交评审、办理复核、提交修改及查询回执。团队检查反馈不伪装成 Forge 业务动作；业务动作拒绝越权和旧版本，不暴露通用数据写入 |
| 2 / DEV-01、OBS-01 | 桌面连接远端能力目录，开发者配置成员职责、真实工具绑定与单流程；显式保存、调试、更新及重开读回 | 小周从桌面完成增删改；新版本实际改变团队处理行为。写工具调试仅在隔离环境，不能用后台改团队代替桌面路径 |
| 3 / FLOW-01 | 冻结并传送实际文件；接单后异步执行，系统自动将成功/失败关联到员工收件箱 | 小王递交后可离线；团队能读取相同版本；重复递交只有一件工作；失败通知无需模型主动调用工具 |
| 4 / FLOW-01 | Weave 自动投递团队“需要补充”的运行结果；桌面从消息给 Pi 传入原工作、材料和要求；提交新版本回到团队检查 | 演示一次团队缺项反馈、销售离线后接回、修改、重交；原工作与版本历史持续关联，不产生平行业务待办 |
| 5 / FLOW-01 | 明确授权后进入 Forge 正式评审；按真实账号分配交付与商务复核；人工退回与修改续办 | 小李或小陈退回，小王修改重交；新版本完成两项人工复核后正式通过；审计者从 Forge 页面独立读回 |
| 6 / ACCEPT-01 | 将重复、回执丢失、并发、离线、切换账号和取消穿插到同一场景 | 记录每个断点的实际结果；不重复办理，不丢事项，不把 Weave 完成冒充评审通过 |

先完成第一步的原生能力核验与契约，才决定最小实现。已有通用员工事项对象和签名 webhook 属于待审视的试验，不据此扩大平台模型；不建设要求每团队配置的终态通知机制。

### 后续 MVP1 开发验收批次

第一条业务流通过后，再完成 D5 完整隔离调试、D6 一次 Forge 字段/页面/规则修改及对应团队调整、D7 应用与团队版本发布和在途兼容性验证。首个业务闭环完成不等于所有 MVP1 验收项通过。复杂图编辑、局部重跑和订单到回款放在更后续阶段。

### 执行与证据

组件在各自源码主仓实现并验证，总仓按确定提交集成。服务能力可以通过代码补充；涉及团队定义、成员配置和工具绑定的场景操作必须由开发者账号在桌面完成。先看桌面用户行为，接口和日志只辅助定位。阻塞时保留现场，不以模拟返回替代实际执行。

同一合同由销售发起、交付与商务分别办理，交付物使用者打开实际文件，独立审计者从 Forge 原生页面读回正式状态。记录材料版本、团队与组件版本、人员、回执和失败断点。员工无需技术术语或重复确认已明确的提交意图；只有“看看”的授权不能扩展为正式审批提交。
