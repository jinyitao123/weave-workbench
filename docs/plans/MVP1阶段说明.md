产品采用同一个桌面客户端：员工使用工作模式，开发者按权限增加开发模式。首个业务场景使用销售合同交接，同时验证一次团队修改和一次 Forge 应用修改。

桌面基线于 2026-09-21 再次确认：使用本仓 `desktop/` 的 GooeyPi 产品改造。统一登录、工作模式、开发者配置与运行可视化均在该入口实现和验收；旧 DSH/Host 桌面不属于 MVP1 交付入口。

账号采用一条主路径：管理员或用户在 Forge 注册账号并通过权限集授予产品能力，首次从 Workbench 登录时由 Weave 按受信任的 Forge 用户标识自动建立本地绑定。用户不再注册或输入第二套 Weave 密码。Weave 不独立维护员工、开发者和管理员角色；它验证 Forge 权限并继续独立管理团队执行。绑定、登录和业务授权是三件可审计的事实，界面上合并为一次登录体验。

以下均为目标标准，不代表当前已实现或已验收。

## 当前先交付：第一条完整业务流

首个业务验收以“合同评审通过”为终点，包含实际文件、团队检查、团队退回、人工退回和员工续办。只完成团队交接、工具调用或待办显示不能宣布通过。本批先交付下列闭环；D5 的完整隔离调试与 D6 的 Forge 应用修改保留在后续 MVP1 开发验收批次，未通过前不宣称全部 MVP1 完成。

1. **开发者配置可用团队。** 小周在桌面完成团队/成员/单流程的新增、原位编辑、移除、保存、调试与更新，给成员绑定 Forge 真实能力；保存前不落盘，已发布版本不被未保存编辑影响。重开读回一致，并用一次指令调整证明团队行为确实改变。桌面每团队只开放一个流程，后端保留多流程。
2. **销售交付明确版本。** 小王与 Pi 准备合同和附件，明确授权后提交；账号、实际员工轮次、材料和幂等键固定。接单后 Pi 结束等待，团队持续运行。至少一种场景实际使用的办公文件完成远端读取、下载和打开；现有文本交接只是中间成果。
3. **团队检查结果可续办。** 团队发现具体缺项后结束本次运行，Weave 自动把“需要补充”的结果关联到原员工收件箱。销售离线后重新登录仍能看到，打开后 Pi 读取原工作、固定材料和检查意见，修改并递交新版本。新一轮检查关联原工作，不要求原 Pi 会话一直在线，也不为团队检查另建 Forge 业务事项。
4. **进入正式人工评审。** 有明确“提交评审”授权且团队检查满足要求时，通过 Forge 动作登记准确版本并发起评审；只有“给团队看看”的授权不得推进正式审批。Forge 解析交付、商务两名真实处理账号，各自在桌面打开、查看和办理本人事项。
5. **人工退回后办完。** 复核人通过本人 Pi 提交退回意见，Forge 保存正式审批意见并产生员工事项；销售从桌面把原事项、固定材料和退回原因交给自己的 Pi，一起完成修改。销售明确要求递交修订材料后，Forge 业务动作绑定新材料版本、校验客户规则，并让原生审批流程继续。首批采用保守的版本规则：新版本重新完成交付与商务两项人工复核；不因旧版本已通过而自动沿用。两人通过后，Forge 保存正式“评审通过”，桌面显示同一结果，独立审计者从 Forge 页面核验合同版本、材料、处理人和意见。此流程由对话中的业务意图触发，不额外暴露原生审批状态转换按钮。

本批必须补齐的能力和验收断点集中在[落地步骤](MVP1阶段说明.md#落地步骤)。团队检查结果由运行通知自动送达；正式业务提交和退回由 Forge 动作与原生审批承接，人员和返回路由由 Forge 决定，遵循[统一产品架构](../architecture/系统架构设计.md#运行反馈业务动作与员工续办)。

本批同时验证：团队失败也有自动反馈；员工“先别发”；缺文件不提交；重复调用与业务已成功但回执丢失；过期事项和并发旧版本被拒绝；账号切换不串数据；离线、重开后能续办。没有证据的环节保持待验收。

后置：订单到回款的完整 OTC、任意业务域、复杂条件/循环设计器、受影响成员自动局部重跑、能力市场与能力包管理界面。需要写工具的开发调试只能进入已隔离的测试环境；隔离未具备时阻塞该调试步骤，不伪造试跑成功。

## 一、员工工作模式

| 编号 | 验收目标 | 实际检查方式与通过标准 |
| --- | --- | --- |
| E1 | 一个账号登录后即可工作 | 先在 Forge 注册真实员工账号，再在 Workbench 使用同一账号登录；首次登录自动建立 Weave 绑定并连接所属组织。后续不要求注册或登录第二套账号。能看到本人获准使用的能力和待办；切换账号后，材料、会话、绑定和待办不串用。 |
| E2 | 本地准备材料 | 助手能在授权工作空间内读取、整理和修改合同，成果保存为可打开的实际文件。个人草稿不会自动成为正式业务记录，也不会因登录企业账号而上传整个目录。 |
| E3 | 明确递交工作 | 用户说“提交这份合同”后，系统明确本次递交的文件版本、目标和范围，生成可持续查询的工作编号。后续修改本地文件，不得悄悄改变已递交材料。 |
| E4 | 按业务规则办理 | 团队使用当前员工身份发现并调用 Forge 允许的业务动作；缺材料时列出具体缺项，补齐后继续同一项工作。需要确认时展示具体内容并保存决定；已有授权不反复询问。确认提交不能被显示为审批通过。 |
| E5 | 看懂执行进展 | 任务能区分执行中、等待补充、等待人员处理、失败、取消和完成。说明正在做什么、卡在哪里、下一步由谁处理；状态来自实际执行记录。关闭再打开客户端后仍能查到。 |
| E6 | 跨员工接续办理 | Forge 产生真实待办，处理员工在自己的桌面收到并查看关联材料，助手协助准备处理意见，最终以处理员工身份办理。通知与待办关联同一项工作，重复通知不重复办理。 |
| E7 | 获得可核验成果 | 至少完成一种本场景实际使用的办公文件格式的上传、下载和打开验证，不能只交付文本摘要或链接。正式合同状态、处理人和交付物可关联，另一身份从 Forge 独立读回一致结果。 |

复杂业务详情可以从桌面打开 Forge 原生页面。桌面集中呈现工作、待办和成果，不重复建设整套业务页面。

## 二、开发者开发模式

| 编号 | 验收目标 | 实际检查方式与通过标准 |
| --- | --- | --- |
| D1 | 看见可开发对象 | 列出有权开发的团队和 Forge 应用，标明当前环境、已发布版本和草稿。能区分“允许使用”“允许修改”“允许发布”，权限由服务端落实。 |
| D2 | 看懂团队配置 | 查看团队目标、角色分工、技能、工具绑定、输入输出、步骤关系、分支及人工处理点。提供关系图总览，点击节点可查看完整的可编辑定义。团队分工和工作流都必须从桌面完成新建、查看、修改和删除（有历史时为归档）的完整验证。 |
| D3 | 修改并检查差异 | 从已发布版本创建草稿，通过配置编辑或助手修改角色、技能、工具和步骤关系；修改都落到同一份定义，可查看保存前后的差异，并校验引用与配置有效性。每一项写入都要刷新回读；归档后从开发列表移除，已发生的运行和版本记录仍可追溯。 |
| D4 | 从运行定位配置 | 一次试运行能关联准确版本，在关系图或时间线上显示实际经过的步骤。可以查看授权范围内的输入输出、工具调用、耗时、用量、失败及重试记录，并返回对应配置位置。 |
| D5 | 两种调试都可用 | **只读分析**可读取获准线上数据，正式写入和外部发送由工具权限层禁止；**隔离试跑**可执行真实创建、提交和审批，但只写入测试环境，通知进入测试通道。结果清楚标明环境与测试性质。 |
| D6 | 修改 Forge 应用 | 完成一个具体需求，例如“合同增加交付地点并在提交时校验”。在隔离分支修改字段、页面和业务规则，展示差异，完成检查、预览与业务验证；相关团队同步调整材料提取和缺项提醒。 |
| D7 | 发布可追溯版本 | 团队与应用分别形成版本，发布者能看到测试证据、具体变更和目标环境。新任务使用指定新版本；既有任务保留原定义关联。涉及应用规则变化时，要验证在途业务兼容性，不默认整个系统已自动冻结。 |

当前编辑体验统一为查看与编辑一体化：保留团队卡片和可操作流程图，无独立编辑按钮，点击配置项直接修改，模型、工具和关系从目录选择，高级参数折叠。新增成员先填名称和职责。修改只在本地内存中保留，显式保存后才存储；保存草稿与更新团队分开，调试从当前流程进入，生效从修改详情发起。流程通过节点添加、连接、移除调整；一团队在桌面只展示一个流程，无流程时才出现新建流程入口。

空组织必须能够开始开发。MVP1 的最小入口只要求团队名称和目标，创建时同步建立一个负责人和一个执行成员，完成后直接进入成员配置；成员扩充、流程编排和发布不塞进首次创建步骤。

## 三、共同必测的异常与证据

- **权限拒绝**：员工无法通过对话或直接调用修改团队、发布应用、读取未授权材料；开发权限不自动扩大业务数据权限。
- **重复与中断**：重复提交、客户端断线、业务成功但回执丢失时，不重复创建合同。结果未知必须先核对；可恢复、可安全重试、需人工处理要明确区分，不承诺所有步骤都能原地续跑。
- **等待与取消**：等待人工期间任务持续存在；取消后能确认调度和执行是否停止，并说明哪些业务动作已经发生。
- **版本与独立读回**：记录桌面、Weave、Forge、团队和契约版本。以发起员工、处理员工、开发者和独立审计身份验证。模型声称完成、健康检查通过、页面可打开，都不能单独算业务通过。

## 四、交付层次

本表定义产品完成范围，不要求按层次串行开发；当前修复的施工顺序统一以[落地步骤](MVP1阶段说明.md#落地步骤)为准。

| 交付层次 | 主要交付 | 完成条件 |
| --- | --- | --- |
| 身份与观察基础 | Forge 注册、登录与权限集、Weave 自动绑定、逐任务委托、基础任务状态与事件关联 | 同一账号一次登录；首次绑定和再次登录均可读回；Forge 授权后开发入口生效；越权调用被拒绝且可定位 |
| 员工完整闭环 | 材料交接、Forge 动作、必要确认、跨员工待办、文件成果与业务回读 | E1–E7 在真实环境逐项通过 |
| 开发者工作区 | 配置查看与编辑、版本差异、关联运行、两类调试、应用修改与发布 | D1–D7 通过；改进后的团队与应用被员工实际使用 |
| 组合验收 | 异常验证、版本记录、安装与重开验证、证据整理 | 全部必测项有结果，失败项有明确记录，不用组件测试代替系统验收 |

开发者的基础查看、草稿保存防错和当前流程观察随员工闭环前置交付；完整隔离试跑及应用开发按各自前置条件完成，详见[落地步骤](MVP1阶段说明.md#落地步骤)。

总仓负责桌面、共享契约与组合验收；Weave 组件负责团队定义、执行及观察能力；inoForge 负责业务规则、动作与应用变更。按确定提交集成，先本地检查，再部署指定线上开发环境联调。

本节是基于已有代码、三份场景和问题清单重新排定的执行计划，不是新增架构或已通过清单。它优先于下方较早批次的开工顺序；下方身份、材料、恢复等技术约束继续适用。任务状态和实际版本只维护在[项目状态](../项目状态.md)。

#### 第二步：环境关口与可并行准备

**C13 已按用户决定保留阻断。** 当前没有可用的正式签名包或签名环境时，不反复安装、登录、发起同类交接。可继续做材料准备、代码审查和隔离验证；这些不记为真人通过。具备可用条件后，只安排一次受控复验：Keychain 可用、无秘密内容的加密保存/读取成功、应用重开后仍能恢复，再进入第三步。签名一致是必要检查之一，不能未经验证断言 Developer ID 会解决所有 Keychain 故障；不降低为明文存储。

员工可用性还需核对企业连接：固定 Forge/Weave 地址和标准部署入口，关闭临时开发进程后客户端仍能连接。临时 SSH 转发可用于定位，但依赖人工重建隧道的结果不能算“普通员工安装即用”通过。此处只补必要连接配置，不建设新的配置平台。

#### 第三步：只用一条只读工作验交接和消息

小王在真实 Pi 会话附上确定的合同正文和技术协议，说“这版给合同团队看看，先别正式提交”。核对两个附件已完成异步处理，再提交一次；实际 Forge 写动作授权范围为空。必要时先用已有 Markdown 作为恢复连通性的最小检查，通过后用准备好的办公原件做正式材料验收，不能用前者代替后者。

依次核对：接单回执 → Weave 固定的准确文件和输入版本 → 成员真实读取及检查 → 终态结果 → 原生收件箱 → 小王桌面消息。接单后 Pi 可结束当前轮次；小王关闭桌面后任务继续，重开只见一条对应结果，打开后 Pi 得到原任务、材料和意见。根据样例应识别真实交付/验收冲突，不能编造没有读到的字段。原件读取失败、提取不完整与检查通过分别呈现。

任一步失败只记录一条明确断点并保存现场。确认没有接单也不自动另造多条任务；修复后由新员工意图重新提交，或按已保存意图恢复。工具/API 检查可定位，但不能替代这条桌面行为。

#### 第四步：在同一合同上走完两种退回

1. 小周在本人桌面核对现有合同团队，按场景只调整一条可观察的检查要求；保存、重开、同材料只读调试、更新团队，确认销售新任务实际使用该配置。只补当前链路缺项，不重做已经可用的团队编辑器。
2. 团队检查指出缺项后，小王从结果消息接回 Pi，补齐材料并形成新版本；新一轮关联原工作。正式评审必须另有员工明确授权。
3. Forge 给交付、商务两位真实员工形成原生事项；小李本人通过桌面 Pi 查看指定材料并退回一次。小王离线重开后接回原事项、退回意见与材料，修改正文和附件，明确要求递交。
4. 校验新材料后继续同一合同、原审批；小李和小陈分别在本人桌面复核。本人及合法材料使用者在 Edge 的 Forge 页面读回版本、意见、状态并打开原件；无关账号无法领取或办理。

通过标准是内部评审完成、准确材料可用、旧意见与旧版本保留、过期事项不能继续办理。不得将该结果升级为客户签署、正式订单或项目。

#### 第五步：沿用线索与报价场景证明复用

合同公共交接关口可用后，用同一版本组合依次完成线索和报价。若合同出现特有业务阻塞，保留未通过现场，可转到不依赖该阻塞的另一场景；共性的接单或存储仍不可用时，不用后台调用替代桌面验收。

- 线索：小王 Pi 读取准确线索 → 团队只读分析 → 结果消息 → 新轮次明确授权转化 → Forge 页面唯一客户/商机、本人归属、未知日期保持空白 → 无关账号拒绝。
- 报价：正常页面两行草稿 → Pi/团队读取全部明细并只试算 → 小王只授权设备单价改 900 → 数量和服务价不变，总额 2,100 → 重开及 Edge 本人读回；成本未知时保持未知。止于草稿，不加报价审批或发送前置。

两场景共享当前交接、身份、文件、消息和回执能力。更换业务对象应由 Forge 动作和团队配置表达，不在桌面添加场景名称分支。

| 桌面原生读取与续办 | 接现有原生只读 MCP；查询范围不再依赖写动作；选定对象和元数据关系对应的明细有版本、范围与完整性；消费可信 action_outcomes | 无写授权能查询分析；无关唯一记录不匹配；换号/改口迟到结果拒绝；冻结完整两行报价，后续写仍用原有明确授权。只改后端/共享类型，不碰另一会话的开发界面 |
| 部署初始化 | 复用已存在通知精度迁移，纳入标准部署并验证当前数据库字段类型 | 干净 PostgreSQL 初始化后投递前字段精度正确；失败阻止发布；重复执行安全。无新通知系统、无 ObjectStack 源码补丁 |

报价交互固定为：销售报价列表“新建报价”→填写客户、报价类型、主体、有效期等真实必要信息→增删物料/服务行→预览计算后的金额→保存草稿→同一报价详情。失败保留输入和明确失败位置；保存前不显示正式成功。已有报价详情进入修改，冲突先读回最新版本；不追加审批或对外发送。

根代理先审接口与变更范围，再核对相称的工程检查。各包完成即回到原场景的对应断点验证；组件通过、部署、桌面实际通过分别记录。三条开发线统一 `gpt-6-luna/max`，复用现有工作树并明确文件归属；组件形成提交后再按固定 SHA 同步总仓，不覆盖另一会话的界面改动。

方案确定后最多三条开发线同时写入；子智能体统一使用 `gpt-6-luna`、`max`。主代理拥有共享契约、总仓组件锁、文档与合并验收，先固定接口再派发实现。

| 开发线 | 独占范围 | 首批任务 | 禁止跨越的边界 |
| --- | --- | --- | --- |
| 桌面线 | 总仓 desktop/ | C01/C02 的可信上下文与迟到响应缺口；C03/C04 权威结果读取与 Pi 续接 | 不写 Forge 领域规则，不改 platform 副本、不直接配置远端团队；团队配置通过桌面开发账号操作 |
| Weave 线 | weave-next 的 businessaction、输入登记/委托与相关测试 | C11 参数保真和调用前校验；C02 固定记录/材料范围；C07 原结果与未知状态的传递 | 不写业务对象、不重新判断 Forge 权限、不新增调度/通知系统 |

一个文件只能有一个写入负责人；跨线发现同一接口缺口先返回主代理协调。当前三座主目录各自独立，可按组件并行而不新建工作树；只有同仓确需冲突写入时再临时隔离。子任务不自行合仓、推送或部署；主代理按确定提交同步组件树，不能收尾时整包复制未提交文件。

#### 合入与场景门槛

- 每线交付实际改动、必要定向测试、原生能力验证证据和剩余限制。类型/构建检查不能作为场景关闭证据。
- 主代理核对契约与来源树一致，按固定版本构建 124 镜像。用户已明确要求 124 Forge/Weave 全新初始化；先列出该两套应用的容器、数据卷和旧镜像，确认不涉及无关服务，再清理并以标准 Compose 创建全新运行环境。场景所需账号、团队和材料通过正常产品入口准备。
- 按门槛逐条跑：先验证 A/B 对象与材料、换号和授权撤回；随后合同修订续办；线索和报价在各自受控动作完成后穿插验收。任一场景失败只修证实的断点，不扩写整套能力。
- 最终必须有员工桌面发起/办理、权威业务状态保存、另一身份或独立 Forge 页面读回；部署、真实工具调用和用户目标完成分开记录。

首批暂后置 C10 的双开发者冲突体验、自动刷新优化、全部历史配置回退、大目录性能、更多办公格式和局部节点恢复；已有冲突仍必须拒绝覆盖并保留改动。C09 先验证当前岗位的实际收件人。客户模板、阈值、命名和去重口径留在 Forge 规则及 Weave 团队定义，需要时按具体场景调整。

### 先明确跨系统共同约束

在扩大实现前，用现有契约补齐下表语义。优先复用已经存在的字段、原生接口和状态；确需增加字段时，先记录缺口及调用双方，再改 schema。表中是需要落实的语义，不表示对应字段都已存在。

| 约束 | 必须明确的输入与结果 | 责任位置 |
| --- | --- | --- |
| 谁在授权、授权哪件事 | 身份来源、组织、员工、实际处理轮次、会话、允许动作；新输入和换号如何使旧请求失效 | Host 产生可信轮次；Weave 校验本次委托；Forge 最后检查业务权限。沿用 enterprise-session、agent-team-handoff、task-delegation |
| 操作哪个对象和版本 | 明确业务记录、预期业务版本、固定输入版本；区分“重试原请求”和“修改后新提交” | 固定输入登记与受控业务动作；不得从模型正文反推授权范围 |
| 交付哪份材料 | 原件引用、名称、MIME、字节数、摘要、解析内容引用；材料包版本及其与主件/附件的领域映射 | Host 冻结和上传，Weave 读取同版，Forge 保存正式版本。文件引用不能只进入提示词 |

| 打开事项后如何继续 | 原工作、父运行或原审批、固定版本、退回原因、当前材料、当前允许动作及不可办理原因 | 桌面打开时向权威服务读取。团队检查结果来自 Weave，正式业务办理条件来自 Forge |
| 如何确认已经办成 | 稳定请求键、可查询回执、实际业务结果、未知状态、重复/冲突、取消影响、审计关联 | Forge 负责业务结果；Weave 记录执行和已调用动作；桌面分别展示。复用 work-request、delivery-receipt、team-run-event 和原生收件箱 |

优先级是先把上述约束确定到能够实施，再按下面批次交付。材料、续办和结构化参数共用同一设计，不能等续办页面做完才补版本。内部关联标识只用于调用和审计，普通页面显示业务名称、材料名称和可读状态。

### 批次 1：保证同一员工、同一次意图、同一份材料

**1.1 收尾记录绑定候选（C02）。**

- 核对 Host 固定包、Weave 输入登记、委托资源和 Forge 工具调用的同一记录关联。登记幂等键更换记录或输入必须冲突；不得重新生成内容来让重复请求通过。
- Forge 目录未说明记录要求时保持收紧；需要记录的动作只接受本轮绑定记录，明确无需记录的动作不能意外继承另一个动作的记录。
- 查找没有有效匹配时返回未找到；多个候选由 Pi 根据上下文澄清，不用“唯一候选”替代员工意图。
- 修改位置：总仓 enterprise.ts、enterprise/agent-bridge.ts、交接/委托契约；Weave dispatch_input、business_delegation、businessaction。
- 验收：同员工可访问 A、B 两条记录，只授权 A；替换 B 在写入前失败。重复同请求取回原结果，改对象冲突；合同与线索/报价使用相同约束。数据库验证使用明确隔离的测试库，不能因为本机存在数据库服务就直接写入。

**1.2 补齐材料参数保护（C02、C11）。**

- 沿 Forge 当前动作元数据核对哪些参数表示材料、清单或其他业务值。先证明现有参数/绑定元数据能否表达来源；不足时补最小来源声明，禁止按字段名猜文件、临时增加 JSON 别名。
- Forge 原生动作参数只声明业务字段，不表达本次员工材料来源；在成员能力配置中显式映射字段来源：唯一材料的标识、名称、摘要，或全部材料的有序 JSON 清单。Host 固定材料引用；Weave 将映射版本随成员发布冻结，从模型参数中移除映射字段并注入固定值。材料清单保留逐项身份与顺序，模型不能混入另一份有权访问但未获本次授权的文件。
- 唯一材料来源在任务恰有一份文件时才可使用；多份材料、缺少材料、映射指向不存在参数或模型试图覆盖受保护字段都在访问 Forge 前拒绝。业务团队按职责决定单文件还是完整清单，不根据参数名猜测语义。
- Forge 声明 `file` 的单文件字段可绑定本次唯一文件标识；没有映射的文件字段和声明 `multiple` 的文件字段暂时拒绝运行，不能退化成可由模型随意填写的文本。
- 首批可先覆盖已支持的文本材料和实际动作所需结构；批次 3 再增加一种办公原件及完整修订包。文本范围内也必须做到准确绑定。
- 验收：A 文件授权、B 文件同样可访问时，替换标识、摘要、名称或清单项目均被阻断；失败不写业务。原文件被编辑后，重试仍递交冻结字节；新版本需要新的输入登记。

**1.3 隔离账号工作现场（C01）。**

- 按身份来源、组织和员工划分企业会话、材料工作目录、缓存及关联运行时。切换时撤销旧能力，迟到的目录、事项、文件和运行响应不能更新新账号视图；旧请求的 401 不能把新账号退出。
- 新账号进入自己的会话时由 Host 取得新授权；“换号后让员工手动重启会话”只作为当前候选限制，不能作为该问题的关闭方案。旧账号运行时不得在新账号下继续获得业务能力。
- 先定义旧本地数据的归属迁移：无可靠归属的历史会话不得按当前登录者自动认领；保留原数据，明确迁移状态，再按可核对归属处理。
- 修改位置：Workbench App、登录 IPC、EnterpriseService、CapabilityBridge、会话/工作区/运行时服务。
- 验收：销售、处理员工、开发者交替登录并退出重开，各自只见授权现场；在旧请求延迟返回、登录失败和相同账号重新登录时分别验证；合法新会话仍能交接。

**1.4 统一受理人与岗位解析（C01、C09）。**

- **正式业务审批归 Forge 原生 ApprovalService。** Workbench 从 Forge 读取当前员工参与的原生审批，用原生 decide 接口办理；员工不需要转去 Forge 浏览器。Forge 以请求冻结的 `pending_approvers` 校验决定人，销售退回由原提交员工办理。Weave 内部 `human_task_*` 是团队工作区共享等待点，M3 设计要求当前 workspace membership；它不代表合同审批，不从 `audience_ref` 猜具体员工或岗位。
- Forge 原生 ApprovalService 是审批收件人与办理权限的权威。当前合同提交预检和 Flow 的岗位解析代码不一致，但尚未证明目标场景会路由给错误人员；先用真实 pending 审批核对 `pending_approvers` 是否是已确认的交付与商务处理人。若不匹配，先修当前 Forge 流程/预检的现有配置或重复规则，不为未发生的通用情况提前开发 ObjectStack 岗位快照能力。无人、多人和任职有效期的统一规则留到真实业务规则要求时再扩展。
- 审批参与资格与材料读取分开校验。当前 approver 能读该请求冻结的字段和指定版本文件，但不能因审批身份获得所有合同、其他审批历史或无关文件的通用读取权；开发者配置目录权限与运行时业务数据权限仍分别验证。
- 修改位置：Workbench `getApprovalContext` 与员工工作项；Forge 原生审批上下文适配和修订材料业务动作；如现有 ObjectStack 原生路由不能守住修订材料绑定，再补最小服务层守卫/幂等契约；Weave 只保证内部等待回答绑定当前 `interaction_id`，不新增岗位 ACL。
- 验收：Workbench 只显示本人 native 请求，销售退回后把事项交给 Pi；员工明确递交修订材料后，Forge 校验版本并让原流程继续；当前交付/商务 approver 收到且能读取准确快照，非参与员工无法读取/决定；本轮先实测实际收件人与岗位任职相符。Weave 同一 run 出现后续人工问题时旧/空 `interaction_id` 被拒绝且状态不变，当前 ID 成功，重复请求仍幂等。

第一批退出条件是对象、文件、员工轮次及受理范围一起成立。记录绑定的组件测试通过只结束工作包 1.1 的工程部分，不关闭整个 C01/C02。

### 批次 2：工作可见、结果可信、配置可控

**2.1 修复本人工作查询与分区呈现（C03）。**

- Weave 提供按当前授权员工归属读取 TeamRun 的一致查询；列表、数量、详情与分页使用同一归属规则，不能继续靠桌面猜 project 标识去读另一套运行模型。
- 桌面将运行、正式待办、通知分别加载，分别显示加载失败并允许刷新；打开页面、接单后和重开时获取当前数据，一处服务失败不清空另一处已有内容。
- 团队运行状态、Forge 动作结果、正式审批状态、通知已读分别展示。需要补充和业务结果未知有明确入口，通知已读不表示事项已办理。
- 修改位置：Weave runs/TeamRun 查询及 employee_run_events；Workbench enterprise.ts、App、EnterpriseWorkPage。
- 验收：接单即在本人列表找到同一工作；Forge/Weave 单侧不可用时其他分区仍可打开；团队运行结束但业务提交失败不会显示“业务完成”。

**2.2 建立业务结果核对和安全重试（C07、C08 的最小恢复部分）。**

- 核对 Forge 已有幂等与回执能力；缺口只补到受控业务动作。每次写动作有稳定请求标识、当前员工/对象关联及可查询结果；查不到和未执行不能混为一类。
- Weave 保存实际工具失败与已经发生的业务结果。模型后续异常、用量异常不得覆盖原始业务错误或把已发生写入改述为“从未执行”。
- 出站后的超时先显示结果待核对；优先查原回执，再决定重试。只有证明没有产生结果且可以安全重放，才用原请求键和原输入重试。
- 修改位置：inoForge 领域动作及回执读取；Weave businessaction/teamrun；Workbench 工作详情。
- 验收：在隔离调用路径制造“Forge 已提交、响应未返回”，重开后取回原结果且不产生第二次审批/商机；失败提示指向具体可继续步骤。故障注入不停止共享服务或改变其他人的工作。

**2.3 修复开发配置的防错与防丢失（C10、C11）。**

- 团队卡片和流程图保持现有入口；负责人、执行成员及节点引用保存后逐项回读，非法引用明确报错，不替换成首个成员。
- 修改只留在本地编辑状态；点保存才写草稿。发生版本冲突，保留本人修改，读取最新配置并给出差异；由开发者解决冲突后重新保存，不自动覆盖双方内容。
- 调试位于当前流程；区分实际输入输出、真实只读调用、被模拟的写调用和未执行步骤。更新团队从修改详情发起，不能把模拟成功作为生产动作可用的证据。
- 修改位置：桌面团队开发侧栏（TeamDevelopmentWorkspace）、useTeamDraft、StepInspector、MemberInspector、TrialPanel；Weave 草稿修订检查和配置引用验证。
- 验收：开发者从桌面新增、修改、删除成员/节点并显式保存，重开及调试执行者一致；两位开发者同时修改时能找回双方内容；未保存退出没有产生远端新草稿。此包可提前实施，不依赖完整合同修订。

### 批次 3：完整版本交付和两类退回续办

**3.1 交付可打开的原件与完整修订包（C05，必要的 N01）。**

- 开工先从现有场景素材选定一种真实办公格式并登记，固定原件字节与 MIME；解析内容是原件的派生产物，解析失败须可见，不能用摘要替代原件。
- 每份材料上传后保存回执，按原请求核对与恢复。多文件中断不反复上传已确认文件；若现有存储不支持消除“回包丢失”的重复文件，记录明确限制并补最小文件幂等连接，不另建存储系统。
- Forge 领域动作接受本次完整主件/附件版本，核验归属、预期业务版本、缺项和幂等后返回版本回执；同一版本内容不可覆盖。保持旧审批快照不变，新一轮从当前完整版本取快照。
- 先验证 ObjectStack 原生 ApprovalService 和当前 Forge 重提守卫插件对修订材料版本的完整校验；有缺口在 Forge 插件扩展点补受控绑定和恢复，不修改 ObjectStack 源码。不能只在桌面更新材料展示、再直接推动原生审批状态。
- 修改位置：Workbench materials、上传恢复、下载打开；Weave 资源读取；inoForge 领域材料动作、审批快照集成。
- 验收：销售原件、团队读取和复核人下载内容一致；正文和附件一起修改后新审批只读新包，旧轮次仍打开旧包；中途缺件、旧版本并发覆盖均被阻断。

**3.2 让桌面按当前事项继续（C04、C06、C11）。**

- Forge 以既有事项/记录为基础提供受权限保护的当前上下文：正式状态、材料版本、允许动作、不能办理原因及原处理意见。业务对象特有的字段校验放在领域动作/投影内。
- 桌面从事项进入 Pi 前重新读取当前上下文；可恢复原会话就关联原会话，否则建立关联同一工作的会话。需要补齐的数据引用要持久保留，不能只复制消息正文。
- 团队检查缺项由 Weave 结构化结果和系统事件返回原员工；正式人工退回由 Forge 决定修改责任人和返回位置。修改形成新输入，并保留父工作/审批与意见；恢复原提交不得偷偷变成新材料。
- 审核者本人 Pi 能读取本事项、整理意见并按该员工明确要求提交。提交瞬间重新验证动作仍允许；开发者账号和原发起员工身份不能替代处理员工。
- 修改位置：Weave 运行结果/事件和输入关联；inoForge 原生事项扩展与动作投影；Workbench EnterpriseWorkPage、App 和企业能力桥。
- 验收：分别走一次团队缺项与人工退回；销售离线重开后 Pi 取得正确的原工作、版本和意见；复核人通过自己的 Pi 办理。换到非合同事项，桌面不增加对象名分支。

**3.3 完成结构化参数与基础恢复（C08、C11）。**

- Forge 元数据到 Weave 工具定义完整保留当前场景需要的嵌套对象、数组及字段约束；输入和前序输出采用有限、可验证的字段路径映射，先不增加表达式引擎。
- 桌面接入现有 Weave 停止、查询与安全阶段恢复。委托到期后由原员工重新授权，仍绑定原输入和已发生业务回执；不能借恢复改成员权限或换业务对象。
- 停止后呈现已经完成的业务动作和未执行部分；若执行中状态还未确定，持续显示待核对，不声称全部撤回。
- 验收：报价首批读回两条明细，只有被授权的一行按原生标量参数改价并由 Forge 原子重算整表；缺字段或换保护字段被阻断。完整多行数组参数在原生目录或 Forge 插件能提供条目 schema 后另验；断线、超期、停止和重开均找回同一工作，不重复已确认的业务写入。

第三批退出条件是员工能携带准确材料和意见继续一件工作，并由权威系统保存新结果。只有“打开 Pi 会话”或“补附件成功”不能算续办完成。

### 批次 4：按既有场景逐条验收复用

使用现有测试账号和场景素材，账号信息留在约定的本地安全位置。正式环境限定为[环境说明](../environments/开发联调环境.md)中的 124 测试部署；每次操作前核对环境、账号、材料和组合版本。团队定义变化必须由开发者账号从桌面完成。可以预置明确标注的测试业务数据，不能事后从后台改状态补出通过结果。

| 场景 | 桌面实际路径与结束点 | 必须穿插的异常 | 独立读取证据 |
| --- | --- | --- | --- |
| [合同交接](../../scenarios/sales-contract-handoff/合同场景设计.md) | 开发者配置团队 → 销售与 Pi 准备指定原件 → 团队缺项 → 销售补充 → 明确提交评审 → 处理员工本人 Pi 退回 → 销售改正文/附件并重交 → 两岗位按新版本复核通过 | 先别发、缺材料、错记录/错文件、换号、离线、未知回执、并发旧版本、停止后核对 | 交付物使用者打开原件；审计者在 Forge 核对同一审批、版本、真实受理人和意见。终点为本批明确的评审结果 |
| [线索转商机](../../scenarios/lead-to-opportunity/线索转商机场景设计.md) | 员工定位已有线索 → 先分析不转换 → 明确授权准确一条线索 → 转换 → 重开继续跟进；不额外插入审批 | 相似候选、只有一条但不相关、取消转换、回执丢失后重复调用、重复创建 | Forge 源线索、客户、商机及负责人关系一致；只有一次转化结果，独立使用者能继续办理 |
| [报价核算与调整](../../scenarios/quotation-review/报价核算与调整场景设计.md) | 团队读取两行明细 → 只试算 → 员工授权指定行改价 → Forge 保存并重算 → 重开读取；首批仍为草稿 | 缺成本、错行、结构化参数缺失、半写入、并发已改价、重复调整 | Forge 明细和汇总属于同一保存版本；按场景样本从 2,300 元到 2,100 元，未授权行与数量不变 |

线索/报价如果缺少受控业务动作，应在 Forge 增补有明确对象、权限、幂等与并发条件的领域动作；不得开放通用写表工具绕过。金额计算由 Forge 的确定性业务规则完成，Pi 不充当第二套定价器。

报价场景要求的真实隔离调试依赖 N05；隔离环境和服务端权限未具备时，只记录已完成的只读映射或员工办理片段，报价全场景仍待验。第一条合同员工闭环可按既定范围先验收，但不能据此关闭 D5 或整个 MVP1。

每条场景按发起员工、处理员工/结果使用者和独立审计者分别取证。测试脚本与日志辅助定位，不代替桌面发起、桌面办理及 Forge 页面最终读回。失败保留原工作和材料，回到对应问题修复，不改写旧验收记录。

### 每个工作包的交付要求

1. 开始时在项目状态中关联问题编号、目标用户步骤、源码仓和工作分支；检查既有原生能力及候选实现。技术前置取证完成后才确定新增接口/字段，不凭方案文字假定能力已存在。
2. 跨仓先落实契约与失败语义，再分别形成组件提交；单包以一个可验证结果为边界，不把身份、结果、配置、材料同时塞入一份不可审查改动。
3. 做与变化相称的检查：参数/权限拒绝、幂等冲突和恢复要有有效行为检查；数据库内容必须在隔离持久库核对。纯文档运行 make check；已有通过检查只在新改动或具体风险出现时重跑。
4. 组件交付使用准确 SHA；总仓同步整个来源树和锁，核对差异与调用兼容，再形成候选组合。共享 schema 新旧调用不兼容时明确阻断，不能默默退回提示词约束。
5. 现场验收同时记录桌面版本、服务提交、团队发布版本、原输入/业务材料版本、角色、预期及实际结果。业务产物需被另一授权身份独立读取。日常结果回写问题/状态；独立冻结评审才按编号留档。
6. 合并源码、部署、业务验收各自有证据。本轮已授权的阶段主线收束不等于后续任意发布已通过。发布范围、共享数据影响和回滚条件按当次明确授权执行。
7. 出现越权、错对象/错材料、无法确定是否已经写入、丢失改动或版本不一致时停止扩大场景；先恢复可核对状态。不得靠重新新建工作、换管理员账号、改工具别名或后台补数据掩盖断点。

工作包完成记录至少回答：员工现在能完成哪一步；改了哪些仓库；准确版本是什么；哪些证据是工程、哪些是实际用户结果；剩余哪个断点。问题只有达到其完整关闭条件才关闭，不按提交数或接口数量计完成。

### 客户规则和实施前待核实项

| 项目 | 当前处理方式 | 决定放在哪里 |
| --- | --- | --- |

### 后续 MVP1 开发验收批次

当前必须解决项之外，后续按场景真实需要推进，不一并扩张：

- N01 的严格逐文件上传恢复：多文件现场出现重复存储时优先补；批次 3 已要求能够找回并复用确认过的文件。
- N02 的分页与关系查询、N04 的配置开放：线索定位或报价明细在既有能力下做不到时，作为对应场景前置补齐，不无限期放在后续。
- N03 的非合同审批收敛：下一条使用审批的非合同场景启用前完成一个原生迁移；线索转换本身不新增审批。
- N05 的真实写入隔离、N06 的已发布历史恢复、N07 的实际成员执行图与 D6 应用开发：分别验收服务端隔离、版本恢复、真实轨迹和一次应用变更；Loom 原有返回能力先读取，不用桌面静态图冒充实际执行。
- N08 的目录规模和长时恢复优化按观察到的使用量处理；第一批需要的基本分页、刷新、停止与结果核对已由 C03/C08 承担。

第一条完整员工业务流通过后，继续完成 D5 隔离试跑、D6 一次 Forge 字段/页面/规则修改和对应团队调整、D7 发布及在途兼容性。完整 MVP1 仍以 E1–E7、D1–D7 和共同异常验收为终点；阶段源码基线和某一业务片段都不能替代该结论。
