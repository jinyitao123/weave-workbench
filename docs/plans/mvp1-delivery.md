# MVP1 落地步骤

日期：2026-09-20。本文把[MVP1 验收目标](mvp1.md)拆成可交付步骤；实际进展见[项目状态](../project-status.md)，本轮只完成方案存档。

## 交付顺序

| 顺序 / 工作项 | 做成什么 | 本轮交付物 | 完成时能演示什么 |
| --- | --- | --- | --- |
| 0 / SYNC-01 | 确认从哪一版继续 | 已有 Weave 修复回流，确定参与联调的版本；准备合同样本及发起、处理、开发、审计账号，核对服务与环境 | 能确定每个问题对应哪一版，旧成果有归属；不需要等所有业务模块收拢 |
| 1 / ACCESS-01 | 员工登录就能开始工作 | 企业环境接入、可替换身份适配、五项产品能力、登录/退出/切换账号、一次最小真实权限判断 | 员工看到自己的工作；开发者看见能力与判断原因；越权访问被明确拒绝，对应 E1、D1 |
| 2 / OBS-01 | 看清团队怎样工作 | 团队详情、只读关系图、节点配置、一次运行的执行时间线和失败位置 | 开发者能从一个真实任务追到使用的团队版本和步骤；员工能看懂进度，对应 D2、D4 及 E5 的基础部分 |
| 3 / FLOW-01 | 让一份合同跨员工办完 | 材料递交、缺项补充、必要确认、合同登记与提交、另一员工待办、实际文件成果 | 两位员工用各自桌面完成交接，审计者读回正式结果，对应 E2–E7 |
| 4 / DEV-01 | 让开发者改进这套能力 | 团队草稿与差异、只读分析、隔离试跑；一次 Forge 字段/页面/规则修改与配套团队调整；分别发布版本 | 修改“交付地点必填”后，测试能拦住缺项，发布后员工实际用到新规则，对应 D3、D5–D7，并补全 D4 |
| 5 / ACCEPT-01 | 证明可以稳定交付 | 权限、重复提交、断线、等待、取消、版本切换与应用兼容性验证；桌面安装重开和版本证据 | 按 MVP1 逐项记录通过、失败和未验证；必需项全部通过后才宣布 MVP1 完成 |

步骤 1 同时补最小观察能力，步骤 2 用真实受权测试任务验证，并在步骤 3 接入正式业务回执；不会先做一个没有真实数据的看板。OBS-01 与 FLOW-01 完成后，再扩展到开发者修改和发布。

## 每步怎样推进

每步先明确桌面、Weave、Forge 需要交换什么信息，再补对应功能。复用已有账号、执行事件、业务动作与检查工具；组件在各自主仓形成确定提交，总仓组合验证。先本地检查，再部署指定线上开发环境；写入试跑使用明确隔离的测试数据与通知通道。

每步交付一个能实际操作的用户路径、对应版本和验证记录。后台接口可用、界面示例和模型自述不算完成。未通过则保留问题现场，修复当前路径后再继续依赖它的步骤。

当前从步骤 0 的版本与修复核对开始，随后进入步骤 1 的真实登录与身份贯通。ENG-02 的远端共享安排单独跟踪，避免把仓库整理当作员工功能已经交付。
