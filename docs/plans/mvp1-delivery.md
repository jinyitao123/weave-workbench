# MVP1 落地步骤

日期：2026-09-22。验收目标见[MVP1](mvp1.md)，职责以[统一产品架构](../architecture/product-architecture.md#运行反馈业务动作与员工续办)为准，实际状态只在[项目状态](../project-status.md)维护。

## 先走通完整业务流

| 顺序 / 工作项 | 本批必须做到 | 现场验收结果 |
| --- | --- | --- |
| 1 / FLOW-01 | 核实 ObjectStack 原生任务、审批、消息及权限；定义 Forge 的业务 MCP 动作与受限身份委托 | 明确复用的原生对象与动作；可发现的业务能力包含授权材料读取、请求修改、合同登记/提交评审、办理复核、提交修改及查询回执。拒绝越权和旧版本，不暴露通用数据写入 |
| 2 / DEV-01、OBS-01 | 桌面连接远端能力目录，开发者配置成员职责、真实工具绑定与单流程；显式保存、调试、更新及重开读回 | 小周从桌面完成增删改；新版本实际改变团队处理行为。写工具调试仅在隔离环境，不能用后台改团队代替桌面路径 |
| 3 / FLOW-01 | 冻结并传送实际文件；接单后异步执行，系统自动将成功/失败关联到员工收件箱 | 小王递交后可离线；团队能读取相同版本；重复递交只有一件工作；失败通知无需模型主动调用工具 |
| 4 / FLOW-01 | 团队通过 Forge MCP 请求修改；桌面打开最新事项并给 Pi 传入材料和要求；提交新版本回到团队检查 | 演示一次团队缺项退回、销售离线后接回、修改、重交；原工作与版本历史持续关联 |
| 5 / FLOW-01 | 明确授权后进入 Forge 正式评审；按真实账号分配交付与商务复核；人工退回与修改续办 | 小李或小陈退回，小王修改重交；新版本完成两项人工复核后正式通过；审计者从 Forge 页面独立读回 |
| 6 / ACCEPT-01 | 将重复、回执丢失、并发、离线、切换账号和取消穿插到同一场景 | 记录每个断点的实际结果；不重复办理，不丢事项，不把 Weave 完成冒充评审通过 |

先完成第一步的原生能力核验与契约，才决定最小实现。已有通用员工事项对象和签名 webhook 属于待审视的试验，不据此扩大平台模型；不建设要求每团队配置的终态通知机制。

## 后续 MVP1 开发验收批次

第一条业务流通过后，再完成 D5 完整隔离调试、D6 一次 Forge 字段/页面/规则修改及对应团队调整、D7 应用与团队版本发布和在途兼容性验证。首个业务闭环完成不等于所有 MVP1 验收项通过。复杂图编辑、局部重跑和订单到回款放在更后续阶段。

## 执行与证据

组件在各自源码主仓实现并验证，总仓按确定提交集成。服务能力可以通过代码补充；涉及团队定义、成员配置和工具绑定的场景操作必须由开发者账号在桌面完成。先看桌面用户行为，接口和日志只辅助定位。阻塞时保留现场，不以模拟返回替代实际执行。

同一合同由销售发起、交付与商务分别办理，交付物使用者打开实际文件，独立审计者从 Forge 原生页面读回正式状态。记录材料版本、团队与组件版本、人员、回执和失败断点。员工无需技术术语或重复确认已明确的提交意图；只有“看看”的授权不能扩展为正式审批提交。
