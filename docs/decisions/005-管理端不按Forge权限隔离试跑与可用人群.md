## 背景

[决策 004](004-团队配置集中到Weave管理端.md) 把团队配置集中到管理端后，在 124 上实际使用暴露出三处卡点：

- 一版草稿只归第一个试跑它的开发者，其他人既不能试跑也不能发布；已发布且没有改动的团队，换一个账号就无法试跑，页面也看不到别人的试跑记录。
- 团队“可用人群”要在管理端手填 Forge 权限集的内部名称，填错不报错，保存后可能谁都用不了。
- 管理端的运行列表只显示本人提交的任务，看不到员工实际发起的团队运行。

管理端的使用对象还包括没有 AI 和 IT 基础、接受培训的业务人员，这些规则无法向他们解释。

## 决定

1. **试跑与发布不按开发者个人隔离。** 能进入管理端的开发者、管理员和所有者，都可以试跑同一份已保存草稿，也都可以发布；发布门禁按“同一修订、同一冻结候选”下任何一位开发者的成功试跑计算。每次试跑仍记在发起它的账号名下，准入回执和模拟回执按该账号核验，不把一次试跑的回执用于它范围之外的能力。本条替代团队工作区契约原“发布覆盖绑定当前发布者，不能借用另一开发者的试跑”。
2. **试跑和发布是两个页面。** 试跑页只做试跑和查看试跑记录；发布页说明当前版本、待发布的修改和还差什么。
3. **管理端不再填写 Forge 权限集。** 团队“可用人群”从管理端和团队草稿的可编辑内容中移除。谁能使用一个团队，由 Forge 配置管理页为该团队选择的“可使用人员名单”决定；没有配置名单的团队，组织内全部账号可用。本条替代[决策 002](002-任务委托身份来源与员工入口收敛.md) 第 5 条。
4. **管理员查看团队运行时连内容一起看。** 管理员和所有者可查看本工作区全部团队运行及其输入、每步输出、工具调用和日志，包括员工从桌面和飞书发起的业务任务；只读，不能代员工停止、重试或确认。开发者仍只看本人提交的任务和试跑。

## 过渡

- Forge 的名单配置页和 Weave 读取名单的接口尚未实现。实现前 Weave 不再按权限集过滤团队，已发布团队对组织内全部账号可用；草稿里已有的 `audience` 原样保留但不生效，名单接口落地后删除该字段及其校验。
- 名单接口先在[团队工作区契约](../../contracts/v1/团队工作区契约.md)写清调用者、身份、输入、输出和错误，再由 Forge 与 Weave 分别实现。

## 限制

- 进入管理端的身份和角色仍按[决策 003](003-Weave独立管理端与身份接入.md) 由外部身份交换与运维 API Key 取得，本决定不改“谁能打开管理端”。
- 管理员能看到的运行内容，可能包含员工在 Forge 任务委托下读到的业务数据；查看人不需要在 Forge 拥有对应记录的权限。这是本决定接受的范围，不因此向管理端开放 Forge 查询或写入。
- 试跑中的业务动作仍是隔离模拟，不访问 Forge、不写业务数据；本决定不改变正式运行必须有当前员工任务委托的规则。
- 本记录只是决定，不代表上述改动已实现或已在 124 验证；进展见[项目状态](../项目状态.md)。
