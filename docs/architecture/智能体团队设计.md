# 智能体团队设计

状态：2026-10-03 用户确认以远端团队设计为落地指导。本文维护团队设计与实施边界，目标未整体实现或验收；当前进展见[项目状态](../项目状态.md)。

本文维护 Weave 智能体团队的设计方法、Forge 销售与项目两块的团队设计，以及 Forge 需要配合开放的能力。产品职责与权威状态以[系统架构设计](系统架构设计.md)为准；场景流程、账号、开发者配置步骤和验收证据在各[场景文档](../../scenarios/README.md)维护；跨组件字段以[契约](../../contracts/README.md)为准。

## 设计原则

- 团队承接员工交来的一段有明确输入和交付要求的工作，交付检查意见、草稿或分析。审批结论、处理人和业务状态由 Forge 决定，团队不替代。
- 要深做的是三件事：团队接哪一段工作、交付和写入怎么约定、按什么口径检查。成员和流程从一个负责人起步，有实际需要再加。
- 团队按工作内容划分，不按业务节点或员工岗位划分。同一段工作被多个岗位使用时共用一支团队，能否写入由每次运行的授权决定。
- 已记录的团队故障主要出在边界上：写入发生在一个步骤，交付却取自另一个没有回执的步骤；模型声称已提交，业务调用为 0；检查支线没收到任务原文；提交动作没绑定本轮材料。见[问题清单](../plans/问题清单.md) C03/C07、C10 及[合同场景](../../scenarios/sales-contract-handoff/合同场景设计.md)。下文的设计卡针对的就是这几类问题。

## 什么时候建团队

至少满足一条才建团队，否则由员工和 Pi 在本地完成：

1. 组织要统一一类工作的做法：多名员工反复办理，需要同一口径，并且可以发布、可以追溯；
2. 员工离线后仍要继续推进的较长工作；
3. 需要职责分离：检查者不写入，或正式动作前必须先过统一检查；
4. 需要多个专业视角并行判断。

以下环节不建团队：评审和审批结论；签署登记与归档；按岗位确定处理人和发送通知；能用规则确定的一致性校验（交给 Forge）；员工本人的日报与进度填报。

## 团队能读什么、写什么

团队经任务委托访问 Forge，范围由[任务范围](../../platform/forge/apps/forge-objectstack/src/plugins/task-delegation-scope.ts)和[能力桥](../../platform/forge/apps/forge-objectstack/src/plugins/task-mcp-bridge.ts)限定：

- 一次运行至多绑定一条业务记录，成员用通用读取只能读这条记录本身，读不到明细行和关联记录；
- 本轮材料至多 10 份，单份不超过 2 MiB，合计不超过 8 MiB；
- 写动作不能换到其他记录：需要记录的动作只能作用于绑定记录，不需要记录的动作不能指定记录；文件参数只能取本轮材料；
- 每名成员只看到本轮允许范围与其发布能力的交集，Forge 执行时再按员工权限和业务状态校验；
- 能读到哪些字段随发起员工而变。例如 PMO 和解决方案岗位看不到项目预算、合同额等金额字段（[岗位权限集](../../platform/forge/apps/forge-objectstack/src/permissions/otc-role.permission.ts)）。团队遇到看不到的内容时写明“无权读取”，不推测。

需要明细或关联记录的团队，由 Forge 提供上下文读取动作（见下文“Forge 需要配合开放的能力”），或由 Pi 在交接时把快照固定进本轮输入，不让团队自己查找关联记录。

## 设计卡

每支团队用一张设计卡写清下列各项。输入、交付、退回员工和可用人群即[团队能力卡](系统架构设计.md#团队发布什么)要求的内容；位置、写入、证据和确定性是团队能力卡没有覆盖的部分。

| 项 | 要回答 | 落在哪里 |
| --- | --- | --- |
| 位置 | 哪个岗位在哪个业务环节交来；交付后接哪个 Forge 动作或人工环节 | 本文 |
| 输入 | 绑定哪类记录；必需和可缺的材料；用哪个上下文读取动作；每一步收到什么 | 团队目标、步骤输入 |
| 交付 | 检查类用结果分类（完成或需要补充；完成只表示检查做完，不表示没有问题），其他类用章节固定的文档；每个问题都带出处 | 流程交付、成员交付要求 |
| 退回员工 | 什么情况以“需要补充”结束，缺项怎么写 | 汇总成员指令 |
| 写入 | 只读、草稿登记或正式提交；用哪个动作；由哪个成员持有；哪些参数由平台注入 | 成员业务能力与参数绑定 |
| 证据 | 关于业务状态的说法只依据 Forge 回执；交付取持有回执的那一步 | 流程形状、平台 |
| 确定性 | 金额、合计、材料集合由 Forge 或规则计算，模型只引用和解释 | Forge 动作、Weave 交付校验 |
| 可用人群 | 哪些 Forge 权限集可以使用 | 团队可用范围 |

下文各团队的卡片中，“证据”一项对所有写入团队都相同（见“写入规则”），不逐一重复；“确定性”只在涉及金额的团队单列。

## 结构与写入

只在以下情况加成员：依据的材料和判断标准不同；要把写权与检查分开；并行能明显缩短时间；材料超出单个成员能处理的范围。成员不对应人的岗位，团队里的检查员不是复核人本人。

| 类型 | 默认形状 | 交付 |
| --- | --- | --- |
| 检查 | 负责人；或整理 → 并行检查 → 汇总 | 结果分类，问题带出处 |
| 计算 | 负责人；金额以 Forge 计算为准，需要时加确定性校验 | 逐行差异与依据 |
| 起草 | 起草 → 审校，有次数上限的回改 | 文档，附假设与待确认项 |
| 分析 | 负责人 | 文档：事实、判断、待确认项 |

桌面已开放必需业务动作回执检查，尚未开放通用确定性检查及回改循环（见下文“Weave 与桌面需要的平台能力”）。计算类以 Forge 的计算结果为准，起草类当前只做一轮审校。

写入分三级，默认只读：

| 级别 | 含义 | 进入本轮范围的条件 |
| --- | --- | --- |
| 只读 | 不调用写动作 | 默认 |
| 草稿登记 | 在绑定记录上登记团队成果的新版本，不改变业务状态，员工在 Forge 确认后继续办理 | 员工本轮要求登记 |
| 正式提交 | 代员工触发业务状态变化，如转商机、改价、提交审批 | 员工本轮明确授权的确切动作 |

写入规则：

- 审批意见（同意、退回）和指定处理人不交给团队，由员工本人经 Pi 办理。提交审批属于发起方的正式提交，可以按本轮授权交给团队。
- 持写权的成员只出现在流程最后一步，交付取这一步的输出。业务能力目前按成员绑定，不能按步骤收窄，而负责人通常也执行第一步，所以写权交给只在最后一步出现的提交成员。线索团队就出过这种问题：负责人在第一步完成了转化，交付却取自没有回执的后续步骤，最终消息否认了已经发生的转化（问题清单 C03/C07）。
- 员工只说“看看”时，本轮范围里没有写动作，提交成员只汇总检查结果，不需要条件节点。
- 提交成员执行前重读绑定记录，按 Forge 当前状态和版本办理；结果不明时先核对原请求的回执，不重复写入。
- 员工明说的关键值（金额、单价、日期）按原值使用，没说的留空，不由模型估算。

## 销售与项目的团队设计

范围是 Forge 销售（线索、商机、报价、合同）和 Forge 项目（立项、交接、计划、调试与验收），订单与售后不在本文范围。节点编号引用[OTC 业务主流程](订单到回款业务流程.md)中的通用项目流程图；交付路径分类依据[Forge 三类业务定义](../../platform/forge/docs/business-model.md)，该文建议首期做“需求整理”和“验收准备”两项 AI 工作，这里各对应一支团队。权限集名称见[演示账号与 ObjectStack 配置](../../scenarios/演示账号与ObjectStack配置.md)。

| 团队 | 块 | 类型 | 写入 | 现状 | 批次 |
| --- | --- | --- | --- | --- | --- |
| 线索分析 | 销售 | 分析 | 正式提交：转商机 | 已有，写权移到提交成员 | 一 |
| 需求整理 | 销售 | 分析 | 只读，后续草稿登记 | 新增 | 一 |
| 报价核算 | 销售 | 计算 | 正式提交：单行改价 | 已有（现名报价核对团队），调整写权与交付来源 | 一 |
| 合同检查 | 销售 | 检查 | 正式提交：提交审批 | 已有（现名合同评审协作团队），写权移到提交成员 | 二 |
| 项目交接 | 项目 | 检查与起草 | 只读，后续草稿登记 | 新增 | 三 |
| 阶段材料检查 | 项目 | 检查 | 只读 | 新增 | 三 |
| 验收准备 | 项目 | 检查与起草 | 只读，后续草稿登记 | 新增 | 四 |
| 计划草拟 | 项目 | 起草 | 草稿登记 | 后续 | 五 |

以下环节不建团队：项目立项、关联合同与订单、开始和暂停等状态操作，由员工在 Forge 办理；合同转订单和订单复核中来源、数量与金额的一致性，由 Forge 规则校验；KP 评审、报价与合同审批、签署登记，由人作结论；日报和进度由员工本人填报，Pi 可以协助。

### 线索分析团队

| 项 | 设计 |
| --- | --- |
| 位置 | 线索阶段（A1–A3）。销售交来做只读分析；看完结果后，销售另起一轮明确授权，同一团队执行转商机 |
| 可用人群 | 销售负责人（`sales_lead_owner`） |
| 输入 | 绑定线索；本轮沟通材料 |
| 交付 | 分析轮交付文档：事实逐条标出处、机会判断与理由、待确认项。转化轮交付 Forge 回执中的客户与商机，并写明金额、日期的来源 |
| 退回员工 | 不单独退回，缺失信息列入待确认项。转化轮发现线索已转化或状态不允许时，不转化，说明原因 |
| 写入 | `sales_lead_convert_to_opportunity`，只给提交成员；金额和预计成交日期取员工本轮所说，没说的留空 |
| 成员与流程 | 负责人理解任务 → 信息整理员 → 提交成员转化 → 交付取提交步骤的输出 |
| 口径 | 客户材料取证规则：记录字段、材料原文、员工估计和推测分开写；机会判断标准由业务负责人提供 |
| 样例 | 信息完整；预算或联系人缺失；同名客户；“先别转”时零动作；授权转化 |
| 与现状差异 | 2026-09-29 已把交付来源改为转化步骤，但转化能力仍在负责人，而负责人也执行第一步；改由只在最后一步出现的提交成员持有。现状依据场景记录，改动前由开发者读回当前发布配置确认 |

### 需求整理团队

| 项 | 设计 |
| --- | --- |
| 位置 | 商机阶段，需求调研与初勘之后、形成方案和报价之前（A3–A4、B1–B3）。销售或解决方案交来；成果经员工确认后，作为方案、报价、SOW 和项目交接的共同依据 |
| 可用人群 | 销售负责人、解决方案（`forge_solution_operator`） |
| 输入 | 绑定商机或售前项目（解决方案岗位读不到商机，由其发起时绑定售前项目）；本轮客户材料，如询价或招标文件、会议纪要、初勘记录 |
| 交付 | 需求整理稿，章节固定：交付路径判断（一次产品、一次柜机或二次项目及子类型，附依据）；供货与服务范围（每项写名称、数量、规格或选型条件、出处，注明已确认还是推测）；交付与验收要求；商务信息原文摘录，不作推断；缺失与冲突（缺什么、该问谁、影响哪个下游环节） |
| 退回员工 | 不单独退回，缺失与冲突写在文档里。材料读不出，或与绑定记录对不上时，在文档开头写明并停止整理 |
| 写入 | 首版只读，员工确认后自行登记；Forge 开放“登记需求整理稿”后，由提交成员登记 |
| 成员与流程 | 负责人 → 交付。招标文件等长材料读不全时，拆成技术要求提取、商务与验收要求提取两条并行支线，再由负责人归并去重、标出冲突 |
| 口径 | 交付路径分类规则，包括“定制不等于二次项目”“签收不等于验收”；范围条目格式；常见遗漏清单，如现场条件、接口、培训、质保、验收标准 |
| 样例 | 完整询价；缺验收标准；招标文件与纪要冲突；带定制件的产品类需求 |

### 报价核算团队（现名报价核对团队）

| 项 | 设计 |
| --- | --- |
| 位置 | 报价草稿阶段（B4–B5）。销售交来核算；报价复核人办理本人审批事项时，也可以交它做只读核对（尚未实测）。交付后由销售决定改价或提交审批 |
| 可用人群 | 报价经办（`sales_quotation_draft_operator`）、报价复核（`sales_quotation_reviewer`） |
| 输入 | 绑定报价；明细与核价版本由 Forge“报价核算上下文”返回，该动作开放前由 Pi 读取后冻结为材料 |
| 交付 | 结果分类（完成或需要补充）：逐行差异（行、字段、Forge 当前值、问题）、合计复核、缺项；只有调用员工能读成本时，才给出成本与毛利 |
| 退回员工 | 缺明细或税率，或核价版本与员工所说的不一致时，以“需要补充”结束 |
| 写入 | `quotation_adjust_line_price`，只给提交成员，只执行员工本轮指定的行和单价；复核人使用时始终只读 |
| 确定性 | 金额、税额、合计以 Forge 计算为准；团队只引用 Forge 返回的数并解释差异，不自行给出新合计 |
| 成员与流程 | 负责人核对 → 提交成员改价 → 交付取提交步骤的输出。成本可读且确需毛利分析时，再加成本核对成员 |
| 口径 | 税率与舍入、折扣权限、毛利门槛，按客户规则 |
| 样例 | 原价无误；指定改单价；缺成本；税率不一致；复核人无成本权限 |
| 与现状差异 | 现有流程最后一步是汇总，改价能力在负责人；汇总步骤没有回执，Pi 曾把它的零调用误读为整个团队没有执行（[报价场景](../../scenarios/quotation-review/报价核算与调整场景设计.md)）。按上一行调整。现状依据场景记录，改动前由开发者读回当前发布配置确认 |

### 合同检查团队（现名合同评审协作团队）

| 项 | 设计 |
| --- | --- |
| 位置 | 合同草稿提交复核前（C2–C3）。销售交来；交付、商务、法务复核人办理本人事项时可以交它做只读辅助（尚未实测）。交付后：本轮已授权提交的，由团队提交审批；否则销售看过结果再办理 |
| 可用人群 | 合同经办（`sales_contract_operator`）、合同复核（`sales_contract_reviewer`）、法务复核（`sales_contract_legal_reviewer`） |
| 输入 | 绑定合同；本轮材料：合同正文、技术协议或 SOW、报价、其他附件。Forge“合同复核上下文”开放后，合同明细、付款条款和来源报价明细改由它返回 |
| 交付 | 结果分类：完成或需要补充；问题按交付、商务、条款偏离分组，逐条带出处（文件和条款） |
| 退回员工 | 缺技术协议、报价等必需材料，或无法确定主件时，以“需要补充”结束；条款冲突不算缺件，作为问题列出 |
| 写入 | `contract_submit_material_package`，只给提交成员；`material_file_ids` 由平台注入本轮全部材料，主件从本轮材料中选。审批同意和退回由复核人本人经 Pi 办理 |
| 成员与流程 | 协调员整理 → 交付检查员、商务检查员并行 → 协调员汇总 → 提交成员提交或只转交结果 → 交付取提交步骤的输出。客户提供标准条款库后，增加条款偏离检查员，作为第三条并行支线 |
| 口径 | 交付清单：范围、工期、验收标准、责任边界、现场条件。商务清单：金额与报价一致、付款比例与节点、质保、违约、税。另有标准条款库及允许偏离的范围 |
| 样例 | 齐全一致；缺技术协议；付款比例与报价不一致；工期或响应时限冲突；“看看”时零动作；授权提交（试跑走隔离分发器）；非标条款 |
| 与现状差异 | 本轮发布v10已将首步理解、并行检查与最终唯一写入步骤分开，真实提交和回执检查通过；仍由负责人承担最终汇总，按步骤收窄能力尚未开放。后续调整为仅在最后出现的提交成员时须正常试跑发布；条款支线按需增加，现状以开发者读回及[合同场景](../../scenarios/sales-contract-handoff/合同场景设计.md#当前联调)为准 |

### 项目交接团队

## Forge 需要配合开放的能力

团队按应有的方式设计，Forge 的开放能力随之调整。新增或调整的动作沿用现有 AI 动作的做法（`ai.exposed`、平台注入幂等键、同请求返回原回执），动作标识由 Forge 确定。

**上下文读取。** 只读；按调用员工的权限裁剪字段（如成本）；带哪些关联记录由 Forge 规则决定；返回内容的版本摘要，后续写动作可据此拒绝过期结果；超出上限时标明截断，不静默丢项。

| 读取 | 绑定记录 | 返回 | 服务团队 |
| --- | --- | --- | --- |
| 需求上下文 | 商机或售前项目 | 商机或项目、客户、来源线索要点、已有资料清单 | 需求整理 |
| 报价核算上下文 | 报价 | 主表、全部明细、核价版本、税率与舍入、员工可见的成本 | 报价核算 |
| 合同复核上下文 | 合同 | 合同明细与费用、付款条款、来源报价明细、合同类型及是否需要法务复核、附件清单 | 合同检查 |
| 项目交接上下文 | 项目 | 项目、已关联合同与订单、物料与服务范围、资料清单、成员岗位 | 项目交接 |
| 阶段评审材料 | 项目 | 计划与工作项、按分类的资料清单、预算与合同额 | 阶段材料检查 |
| 验收准备上下文 | 项目 | 物料与服务范围、调试记录与结论、交付包资料项及证据状态、已有验收项与整改 | 验收准备 |

现有的“读取项目物料与服务范围”（`project_read_delivery_scope`）只读取已关联的有效合同与订单，可以作为项目交接和验收准备上下文的基础开放给 AI。它会返回含税单价和小计，开放前要核对返回内容符合调用员工的字段权限。

**草稿登记。** 只作用于绑定记录；不改变业务状态；携带来源版本，过期即拒绝；同一请求返回原回执，同一幂等键换了内容则报冲突；成果在 Forge 页面可见，由员工确认后继续办理。

| 登记 | 绑定记录 | 内容 | 服务团队 |
| --- | --- | --- | --- |
| 登记需求整理稿 | 商机或售前项目 | 文档正文、结构化范围清单、来源版本 | 需求整理 |
| 登记项目交接包 | 项目 | 交接文档与结构化摘要，作为交付资料的新版本 | 项目交接 |
| 保存计划草案 | 项目 | 整份计划结构，校验日期与前置关系，形成未启用的计划修订 | 计划草拟 |
| 生成验收准备草稿 | 项目 | 验收项（标准、出处、证据，状态为待验收）与资料缺口 | 验收准备 |

现有的“新建客户验收”要求交付包已齐、每一项都已有通过或未通过的结果和证据，适合验收后登记，不适合验收前准备，所以验收准备另需一个允许“待验收”状态的草稿动作。现有计划只能逐项新增工作项或套用模板，计划草案需要整份提交、整份校验。

**能力元数据。**

- 区分读和写。能力目录契约已有 effect，桌面目前仍把所有 Forge 动作投影为写动作，并要求本轮员工授权（[桌面能力目录](../../desktop/electron/main/enterprise.ts)）。
- 区分“可委托团队”和“员工本人办理”。审批同意与退回（`contract_approval_mcp_approve`、`contract_approval_mcp_send_back`）只给 Pi，桌面不再把它们列为成员可绑定的能力。这需要先在[业务能力目录契约](../../contracts/v1/business-capability-catalog.schema.json)中增加标记。
- 团队发布的读取动作随每次运行进入允许范围，不需要本轮写入授权；写动作仍按本轮意图收窄。现在本轮范围只放员工授权的动作，员工只说“看看”时范围为空，上下文读取也会一起失效（[任务交接](../../desktop/electron/main/enterprise/task-handoff.ts)）。Forge 仍逐次校验权限。这一条改变了[系统架构设计](系统架构设计.md)中“纯查看、分析或建议传空范围”的规则，须先作决定、改契约，再改架构文档。

**业务闭环能力。**

- 阶段评审：KP1–KP3 在 Forge 中还没有评审记录或审批流程。应复用 ObjectStack 原生审批建模，评审人按岗位解析，不另建评审体系。这属于 Forge 项目独立闭环的工作，阶段材料检查团队的下游依赖它。
- 规则下沉：合同转订单、订单复核中来源、数量与金额的一致性，由 Forge 做确定性校验，不建团队。

## Weave 与桌面需要的平台能力

- 权威动作事实及最终必需回执检查已实现并由本轮合同实走验证；交付来源继续指向持回执的最终写入步骤。更丰富的跨步骤回执呈现仍按实际需求扩展，不能用模型文字代替 Forge 回执（问题清单 C03/C07）。
- 按步骤收窄业务能力。成员的能力目前在所有步骤都可用；支持按步骤收窄后，负责人可以兼任提交，不必另设提交成员。
- 桌面新建流程时按类型给默认骨架。现在的默认骨架是“理解任务 → 成员 → 交付成员输出”（[流程骨架](../../desktop/src/pages/team-workspace/graph.ts)），只适合只读团队。
- 检查结果结构化。现有结果分类除分类本身外只有摘要和缺项两个字段（[团队检查结果契约](../../contracts/v1/team-run-result.schema.json)），Weave 还限定摘要不超过 1000 字、缺项不超过 8 条，放不下逐条问题和出处；文档类团队也不能同时给出“需要补充”。需要扩展契约。
- 员工明说的关键值作为结构化授权值固定下来，由平台注入或比对，不由模型转抄，与问题清单 C02 的方向一致。
- Weave 后端已有条件、循环和确定性交付校验（[流程类型](../../platform/weave/internal/kernel/workflow/machine/types.go)、[交付校验](../../platform/weave/internal/kernel/deliverycheck/verifier.go)），桌面只开放了负责人、成员、并行、汇合、交付和结果分类。计算类团队需要时再开放确定性校验，起草类团队需要时再开放回改循环，不一次全部开放。

## 检查口径与样例

- 检查口径（清单、条款库、计算规则）是团队效果的主要来源，而且因客户而异（问题清单 B01、B04）。口径由目前实际办理这项检查的业务人员参与编写，放在成员技能（随团队发布形成版本）或 Forge 规则里，不写进桌面代码。多个团队共用的口径，如客户材料取证规则、交付与商务检查清单，使用同一份技能正文。
- 每支团队在场景材料中保留一组固定样例，至少覆盖：完整通过、缺一项、有冲突、只看看。有写入的再加授权写入，试跑走隔离分发器，不写 Forge。样例使用合成或脱敏材料。
- 每次修改都用同一组样例试跑；发布前必须有同一修订的成功试跑。[决策 001](../decisions/001-Weave平台范围收窄与唯一客户端.md) 已下线 Weave 评测；等团队多到人工比对不过来时，再决定是否建立按样例批量试跑的轻量回归。

## 落地顺序

当前先完成销售订单闭环：员工本人登记明确标注的合成签署凭证、登记并独立确认合同预付款、创建及提交销售订单、由正式订单复核岗位本人办理原生审批。签署、资金确认、转订单和复核不新建Weave团队；金额、来源、版本、下单条件和状态由Forge确定。员工Pi接入复用当前事项动作及准确业务来源，初始只读、每轮新原文授权，未知回执先核对，不扩旧委托。项目交接、交付验收与回款后置。

按[项目状态](../项目状态.md)的安排，销售与项目先在 Forge 独立闭环，再接 Weave 与桌面。每支团队依次经过：对应的 Forge 环节独立通过 → 开放所需 Forge 能力（涉及跨组件字段的先改契约）→ 开发者在桌面配置并按样例试跑 → 员工从桌面走正常路径办理，Forge 页面独立读回。

| 批次 | 前提的 Forge 环节 | 团队 | 需要的 Forge 能力 |
| --- | --- | --- | --- |
| 一 | 线索至报价 | 线索分析、报价核算调整写权；需求整理只读版 | 报价核算上下文、需求上下文、能力元数据 |
| 二 | 合同复核 | 合同检查调整写权 | 合同复核上下文 |
| 三 | 合同到项目交接、阶段评审 | 项目交接、阶段材料检查 | 项目交接上下文、阶段评审材料、阶段评审建模 |
| 四 | 调试与验收 | 验收准备 | 验收准备上下文 |
| 五 | 计划 | 计划草拟；需求整理、项目交接、验收准备改为草稿登记 | 各项草稿登记动作 |
