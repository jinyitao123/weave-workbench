# 开发、同步与发布

## 源码归属

| 内容 | 源码主仓 | 总仓角色 |
| --- | --- | --- |
| 桌面产品 | 本仓 `desktop/` | 在 GooeyPi 来源基线上持续改造；上游升级按需评估 |
| Weave / Loom 集成及团队执行 | [weave-next](https://github.com/jinyitao123/weave-next) | `platform/weave/` 是指定提交的 subtree 集成副本 |
| Forge 业务平台与应用 | [inoForge](https://github.com/jinyitao123/inoForge) | `platform/forge/` 是指定提交的 subtree 集成副本 |
| 跨组件契约、场景、版本组合、桌面交付 | 本仓 | 产品组合的唯一维护入口 |

两个组件仓继续独立演进、测试和发布。总仓按产品需要升级，不跟随远端分支自动更新；源码在一个目录树中可见，不改变服务边界，也不要求组件同进程部署。当前已使用 subtree，继续沿用，不再迁移一遍 submodule。

`components.lock.json` 的 `revision` 是导入的来源提交。它不是部署证明，也不是整个产品版本。产品版本由总仓提交确定；正式交付还需记录组件镜像或产物摘要及环境。桌面改造由总仓提交承载，GooeyPi revision 仅记录来源基线。

## 日常开发

1. 桌面和组合工作在总仓完成；组件自身的功能或修复默认在对应独立仓库的工作分支完成。
2. 跨组件功能先在总仓修改契约，组件任务引用同一工作项及契约版本；各组件的内部设计仍由源码主仓维护。
3. 组件检查通过并形成可审查提交后，总仓导入完整 SHA，更新版本锁，执行相关检查和跨组件场景。
4. 联调中在集成副本发现问题，可以做最小诊断修复，但必须在[状态页](../项目状态.md)登记回流项。补丁回到源码主仓并形成提交后，再通过正常同步消除偏差；未回流补丁不能成为长期分叉或正式发布基线。

不要把整个目录复制回主仓，不搬运另一会话的未提交改动，不直接把总仓提交 cherry-pick 到组件仓。回流只提取对应组件的已审查变更；在源码主仓的独立工作分支重放、验证后形成组件提交。组件仓再通过它自己的合并流程推进。

## 同步指定版本

先运行 `make status`；同步在干净的集成分支或 worktree 中进行。已有工作树含未提交成果时保留现场，先识别和整理归属。只从组件仓取得确定的提交，不以 `main` 的浮动状态代替版本号。

以下以 Weave 为例，`<完整来源SHA>` 必须是已审查的实际提交：

```sh
git fetch https://github.com/jinyitao123/weave-next.git <完整来源SHA>
git subtree merge --prefix=platform/weave <完整来源SHA>
```

Forge 使用 inoForge 来源地址和 `platform/forge` 前缀。保持当前未 squash 的导入历史。随后将对应 SHA 写入 `components.lock.json`，提交版本锁和有关状态记录，再运行 `make check` 与 `make component-check`。subtree 合并和版本锁更新全部完成后的总仓提交才是候选组合版本。

发生冲突时核对主仓改动与总仓回流项，保留需要的实现和证据；不通过整目录覆盖或直接改锁文件掩盖冲突。`make component-check` 会比较来源树与已提交的集成树，同时检查组件目录的未提交改动；两者必须一致。

组件升级若改变契约，先处理调用方兼容性。组件回滚也需要重新核对整个产品组合；不要仅修改锁文件，或直接回退线上镜像后宣称组合仍已验收。

## 检查与交付

- `make check`：仓库结构、版本锁、工程入口链接及工程工具回归。
- `make status`：只读接手盘点；不联网、不同步、不修改文件，不能证明远端最新状态。
- `make component-check`：Weave / Forge 来源一致性检查。桌面产品允许相对 GooeyPi 演进。
- `make desktop-check`、`make weave-check`、`make forge-check`：按改动范围执行组件检查；这些不是跨组件业务验收。
- `make release-check`：检查工程基线、组件一致性及工作树干净程度。它只是版本可追溯性前置检查，不能代替构建、签名、部署或场景验收。

先本地开发和验证，再把通过的确定版本部署至[指定联调环境](../environments/开发联调环境.md)。记录总仓 SHA、组件 SHA、契约版本、产物摘要、部署时间和验收证据；正式业务结果以四类身份的场景读回为准。发布与回滚按一套经过验证的版本组合实施。

根目录 CI 负责本仓工程基线与桌面检查；桌面工作流位于 `.github/workflows/desktop-*.yml`，在 `desktop/` 工作目录运行。公共发布仅手动触发并沿用产物验证门禁。`platform/` 导入目录内的 `.github/workflows` 不会自动成为总仓 CI；组件自身 CI 继续在源码主仓运行。桌面检查不代替跨组件业务验收。

未签名测试组合通过手动[测试发行入口](../../tools/test-release/README.md)直接在GitHub取回并核对官方QA归档，验证准确桌面源码树、服务端固定镜像与启动证明，生成Linux服务端包及三平台桌面附件。逐文件摘要读回后才公开RC预发布；不覆盖已有发行、不设Latest、不部署。正式签名桌面继续沿原桌面发布工作流。
