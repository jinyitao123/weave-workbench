## 用户已经完成什么

销售小王在桌面与 Pi 准备并递交文本合同材料；Pi 找到远端团队并取得真实接单回执。Weave 团队通过 Forge 业务动作形成正式审批，交付负责人小李在自己的桌面看到事项、读取当时可见的正文并退回。独立 Forge 浏览器读回审批为已退回修改。销售随后能够打开退回事项交给 Pi，但补附件的团队运行失败，未完成新版本审批。

    A[销售桌面 Pi 准备材料] --> B[Weave 接单并执行团队]

## 如何查看、运行与验证

1. 查看归档代码时，在新的空目录检出阶段标记；不要覆盖当前未提交工作。总仓源码快照与阶段文档引用已新增，当前开发分支和索引保持原样。
2. 桌面使用阶段标记下的 `desktop/`。开发依赖与入口沿用其 package-lock、package scripts；已有依赖环境下从 desktop 执行 `npm run typecheck`、`npm run dev`。本轮使用 Node `25.6.1`、npm `12.0.2`，npm 报告该 Node 不在其支持范围；检查虽通过，不能将其提升为正式发布工具链推荐。
3. 服务连接按[环境说明](../environments/development.md)使用 124 Forge 和既有 Weave 本机转发。需要重建服务时，分别检出版本清单内两个运行 SHA；不要拿总仓旧副本或候选分支头直接代替。私有配置、模型授权及数据卷由环境维护，不进入 Git。
4. 只核对本阶段成果时，打开已有合同审批、退回意见与运行证据，保留失败现场。要验证后续闭环，应先按问题顺序修复，再从[合同场景](../../scenarios/sales-contract-handoff/README.md)用员工自然表达重新发起；团队配置仍须由开发者在桌面完成。
5. 新场景按两份归档文档逐步验收，分别记录桌面行为、明确版本和另一身份的 Forge 读回；不以合同片段或组件测试代替其通过。

本轮检查：桌面类型检查通过；交接相关 3 个测试文件、37 项通过；文档/版本锁/工程入口检查和组件来源一致性检查通过。后两项只说明**现有锁定副本自身一致**，不表示它们等于线上部署。本轮未运行全量业务回归、Windows 构建或签名安装包流程。

## 已知问题与下一阶段

完整问题、原审计编号和每项验收见[分类与优先级](../plans/mvp1-phase1-priorities.md)。阶段后第一批先解决：

文件级上传幂等、完整字段映射、服务端写入隔离调试、历史版本恢复按下一阶段逐项补齐。合同模板、金额条件、具体岗位、重审范围等可按客户配置；授权、版本、可办理事项和结果留存不能整体后置。
