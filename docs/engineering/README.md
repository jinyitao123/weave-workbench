# 工程管理

用一份当前状态和少量固定入口衔接会话，不另建复杂项目管理系统。

## 开始工作

1. 阅读根 `AGENTS.md`、[项目状态](../project-status.md)和[架构基线](../architecture/product-architecture.md)。确认用户本次目标，不自动恢复旧会话的全部工作。
2. 执行 `make status`，查看分支、HEAD、未提交改动、组件来源与偏差。状态页中的历史快照不能替代本次检查。
3. 从状态表领取一个有完成判据的工作项，标明涉及的仓库和当前负责人（会话或分支）。跨组件工作先读 [contracts](../../contracts/README.md)；组件内部改动再读该组件规则。
4. 有其他会话改动时使用独立分支或 worktree。只有已经提交的成果才能作为跨仓同步基线；文件还在磁盘上不等于已交接。

## 进行与收尾

每个工作项最少有目标、归属、状态、下一步和完成判据。使用 `待开始 / 进行中 / 阻塞 / 待验收 / 完成`；代码实现、组件检查、部署和业务验收分别记录。真实阻塞写清缺失条件，有其他已授权独立工作时继续推进。

收尾更新[项目状态](../project-status.md)，不追加冗长的逐条会话流水。保留下一次可以直接执行的第一步、已改未提交范围、来源提交、验证证据及未验证项。新事实替换当前摘要，历史证据留在 `docs/acceptance/` 和 Git 历史。

会影响职责和状态归属的决定写回架构；接口约定写回契约；主机和部署观察写环境说明。状态页只链接它们，避免多份规则漂移。

## 验证记录

重要验收在 `docs/acceptance/日期-主题.md` 中记录以下内容：

- 范围与工作项；总仓 HEAD / 分支、是否有未提交改动及其范围；需要复现未提交实现时另附差异文件或摘要。
- 来源组件提交、契约版本；涉及线上时附部署产物摘要和观察时间。
- 实际执行的命令或用户路径、结果与证据位置。
- 未通过、未执行、受环境限制的检查，以及下一步。

旧记录不追改成新版本已通过。纯文档和工程工具修改执行 `make check` 及相关工具检查即可；业务修改再执行对应组件检查和真实场景。遵守[场景验收](../../scenarios/sales-contract-handoff/README.md)的证据标准。

## 当前命令与自动检查

命令含义与跨仓同步规则只维护在[开发和发布方式](../architecture/delivery-model.md)。根 CI 执行 `make check`。工程入口或工具改变时应一并修复校验，不留下失效的接手链接。

本地文件与 Git 提交可以衔接本机会话，跨机器共享、PR 和远端 CI 还需要总仓远端。远端配置进度只在[项目状态](../project-status.md)的 ENG-02 维护；CI 文件存在不代表远端已经执行。

## 跨仓补丁

上游仓库暂时无法取得完整工作树时，可以在 `docs/engineering/` 保存可应用的补丁作为交接物。补丁必须写明目标版本、默认行为、测试边界和未完成项，并至少通过源文件应用检查。补丁文件不代表上游已经合入、官方测试已经通过或运行镜像已经发布；取得正式工作树后仍要按上游规则建分支、测试、提交和发布。
