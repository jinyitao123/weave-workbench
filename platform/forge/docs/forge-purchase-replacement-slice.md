# Forge 采购换货补货切片

更新于 2026-09-10。实现位于隔离分支 `codex/otc-purchase-replacement`，验收端口 `4368`，数据库 `.objectstack/otc-purchase-replacement.sqlite`。该库承接已停服的采购退货退款数据，通过非破坏性同步加入换货来源关联、补货进度和兼容的采购到货、检验、入库字段；SQLite 完整性检查为 `ok`。

## 证据边界

RISEMAP 的采购退换货页面证明退货退款和换货补货共享采购订单来源，并记录处理方式、预计补货日期和参考货值；采购退货出库由退换货单驱动。当前没有保存同材料换货补货成功记录，因此 Forge 的状态顺序、独立补货额度和成本恢复规则仍属于待 RISEMAP 复核实现。

## 已实现行为

- 已审核且已有入库数量的采购订单可按原订单明细发起等量换货。系统同时校验已入库、历史退回与补回、未驳回申请占用和仓库可用库存。
- 换货提交后直接进入仓库确认，不走财务审批，也不生成退款或资金流水。仓库确认后按当前库存平均成本退货出库，并保存该批换货的成本基础。
- 供应商补货使用独立额度。每次到货生成到货通知、到货登记和待检记录；检验拒收数量立即释放，可再次登记补货，直至累计合格数量等于原退回数量。
- 入库只接受全部已完成检验的合格总量，按原退货出库成本恢复同一仓库和 SKU 的库存价值，生成采购换货补货入库单、明细和库存流水。
- 采购退换货页面可完成草稿、提交、仓库确认、退货出库、供应商补货登记、补货检验和入库，并分别展示退款或换货进度。

## 验证结果

定向 API 验收共 6 组。API 换货 `0.2` 件，先到货 `0.1`、检验合格 `0.05`，拒收的 `0.05` 释放额度；再到货并检验合格 `0.15` 后完成等量入库。库存经历 `0.4 → 0.2 → 0.4`，最终价值保持 `2720`，采购明细累计已退 `0.8`、换货补回 `0.2`，两类资金账户余额均未变化。匿名、缺少预计补货日、超量、错误状态、超额到货和合格量未齐均被阻断。

浏览器独立办理 `REP-BROWSER-20260910-001` 的 `0.2` 件换货，连续完成七步操作。页面最终显示已完成、仓库已确认、已出库和补货已入库。API 回读确认采购明细累计已退 `1`、换货补回 `0.4`，库存仍为 `0.4 / 2720`；两笔换货共形成 3 张补货到货登记、3 张检验单、2 张入库单、2 条退货出库流水和 2 条补货入库流水，没有采购退货退款流水。

完整停服后从同一 SQLite 文件重启，两笔换货、到货、检验、入库、订单累计、库存余额和流水均按原 ID 回读。元数据门禁通过：100 个对象、1573 个字段、22 个页面、114 个动作；`typecheck`、`validate` 和 `build` 均通过。

## 未证明范围

连续多对象写入仍依赖顺序调用，没有数据库事务包裹；库存、流水、订单累计或状态写入中途失败时仍可能不一致。当前每张换货单只支持一条订单明细，补货必须最终等量且一次完成入库；批次和外部 SN 可以记录，但没有批次库存账或序列号逐件谱系。多明细、让步接收、不合格处置、部分补回、撤销、反入库、角色权限和 RISEMAP 同材料成功记录仍待实现或复核。
