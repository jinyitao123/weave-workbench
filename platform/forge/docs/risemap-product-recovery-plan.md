# RISEMAP 产品结构复刻挽回方案

> 历史阶段方案（2026-09-16 标记）：下文队列、分支、环境、已完成声明和取证方式保留为当时记录，不作为当前执行指令。现行要求以[项目规则](../AGENTS.md)、[交付标准](forge-page-delivery-standard.md)和用户当前目标为准；不得据本方案跳过实时页面对照。保留原路径以维护页面合同及历史证据引用。

更新于 2026-09-12。状态：方案与三方互审完成；依据“完整跟随 RISEMAP 产品结构”的既定方向，R1 委外样板开始实施。

## 要解决的问题

Forge 已经形成若干可运行的业务切片，但产品入口按自定义 OEM 生命周期组织，并把大量底层对象暴露给用户。继续沿这个方向增加页面，会扩大“功能不少、工作难找、流程不连续”的问题。

本轮恢复的目标是先让一个委外业务团队能在与 RISEMAP 一致的产品结构里连续工作，再判断已有能力是否适合迁移到其他域。产品完成度由岗位任务和业务闭环衡量，不再由对象数、页面数或测试数衡量。

## 成功标准

委外样板只有同时满足以下条件才算通过：

1. 用户从“生产 / 委外管理”进入，可见委外看板、订单、发料、回厂、退料、对账、供应商、库存、追溯和三张报表；未实现入口清楚标记状态，不提供假操作。
2. 委外业务员、仓库、质检/收货、财务分别只看到与其岗位相关的待办、记录范围和动作。
3. 一份真实业务材料贯穿供应商准备、订单、发料、签收、回厂验收、良品入库或不良处置、余料退回、赔偿、对账和应付。
4. 每张主单据都能看到来源、当前状态、数量和金额进度、异常、下游结果及下一步；用户无需打开明细或日志对象找答案。
5. 关键阻断在页面中可见，包括供应商能力、供料方式、订单审核、剩余可发、可用库存、剩余可回厂、数量关系、入库完成、赔偿审批和防重复对账。
6. 通过 API 结果核对、同一 SQLite 完整停服重启回读、内置浏览器真实操作、两档视口检查和独立业务验收。
7. 用同一材料与已保存 RISEMAP 证据逐步对照；未在 RISEMAP 成功操作的行为保留“待复核实现”，不改写为已对齐。

## 产品骨架

默认一级区域恢复为 RISEMAP 已观察到的 9 个职能域：工作台、供应链、销售、生产、项目、行政、财务、报表、系统。完整分组、181 个已发现入口及证据位置见 [RISEMAP 产品结构基线](risemap-product-structure.md)。

Forge 的 OEM 项目生命周期保留为“项目全景”跨域视图。它可以把立项、报价、设计、采购、制造、交付、回款和复盘串起来，但不再替代每个岗位的稳定职能导航。

页面采用五层关系：

1. 全局职能域，回答“我在哪个业务部门”。
2. 功能组和岗位可见菜单，回答“我能办理哪些工作”。
3. 看板或列表，回答“今天哪些事需要处理”。
4. 主单据详情，回答“这件事从哪里来、现在怎样、产生了什么”。
5. 上下游和审计页签，承载明细、日志、流水、附件与追溯，不占用日常导航。

### 样板入口

| RISEMAP 入口 | Forge 交付形态 | 首轮状态 |

| 委外管理上手指南 | 岗位切换的流程指南与准备检查 | 必做 |
| 委外看板 | 阶段指标、我的待办、在途订单、快捷入口、最近记录 | 必做 |
| 委外订单 | 独立列表、创建与详情；呈现发料/回厂/对账进度 | 必做，复用现有能力 |
| 委外发料 | 列表、创建、审核、出库、签收 | 必做，复用现有能力 |
| 委外回厂 | 列表、验收、待入库、确认入库、不良去向 | 必做，复用现有能力 |
| 委外退料 | 以供应商侧在外余量为上限，生成待入库并完成入库 | 必做，当前缺失 |
| 委外对账 | 按供应商汇总回厂加工费、赔偿负项并生成应付 | 必做，当前缺失 |
| 委外供应商 | 供应商能力、联系人、结算条件及启用状态 | 必做，改造现有对象页 |
| 委外库存 | 供应商/订单/物料视角的已发、倒冲、退料、在外余额 | 必做，改造现有对象页 |
| 批次追溯 | 材料批次正向到成品、成品批次反向到材料 | 必做，当前缺失 |
| 委外未交 | 剩余交付、交期和超期 | 必做 |
| 委外进货 | 回厂量、良率、加工费和批次 | 必做 |
| 委外对账单 | 加工费、补料、扣款、净应付和关联应付 | 必做 |

NCR 不作为委外第 14 个一级入口。它从回厂详情的“不良处置”进入，并可在“供应链 / 库存管理 / 不合格处理”统一查询。现有退货、特采、报废、返工能力保留；拒收、复检、供应商赔偿及财务扣减补齐后再称为 RISEMAP 处置范围对齐。

### 岗位任务

| 岗位 | 默认看到 | 能执行 | 完成信号 |
| --- | --- | --- | --- |
| 委外业务员 | 进行中、待审核、待发、待回、待对账、逾期 | 准备供应商、建单、提交、协调异常、发起对账 | 订单已对账且异常有明确去向 |
| 仓库 | 待发料、待执行出库、待签收、待退料入库、委外库存异常 | 审核或执行发料、登记签收、确认退料入库 | 双向库存流水与在外余额一致 |
| 质检 / 收货 | 待回厂、待验收、待入库、不良待处置 | 登记回厂、判定良不良、确认入库、发起不良处置 | 良品入库，不良进入受控处置 |
| 财务 | 待赔偿、待对账、待生成应付、差异 | 审批赔偿、核对加减项、审核对账、生成应付 | 对账来源唯一且应付可追溯 |

### 连续旅程与硬门槛

| 阶段 | 页面中的上下文 | 动作 | 阻断与结果 |
| --- | --- | --- | --- |
| 供应商准备 | 能力、联系人、结算条件、启用状态 | 启用委外能力 | 缺能力或结算条件时不得正式下单 |
| 建立订单 | 供应商、来源、甲供/包工包料、交期、验收方式、加工件、BOM/手工发料计划 | 保存草稿、提交、审核/驳回 | 审核锁定关键数据；甲供转待发料，包工包料转待回厂 |
| 发料与签收 | 剩余计划、来源仓可用量、追溯批次 | 建单、审核、执行出库、签收 | 库存不足、计划超量、重复执行均阻断；形成原仓出库和委外仓入库流水 |
| 回厂验收 | 未回数量、验收策略、材料标准/实际耗用 | 登记回厂、提交、确认入库 | 回厂不得超未交；良品形成待入库，不良形成处置任务 |
| 不良处置 | 来源回厂、责任、数量、损失和证据 | 退货、特采、拒收、报废、复检、返工、供应商赔偿 | 物理结果和财务结果分开；所有处置数量必须守恒 |
| 余料退回 | 已发、倒冲、历史退料和在外余量 | 建退料、确认退回、入库 | 退料不得超过在外余量；完成后更新本仓和委外仓流水 |
| 赔偿 | 不良或超耗来源、责任比例、财务方式 | 提交、审批 | 回厂来源需完成入库；审批后作为待对账负项 |
| 对账与应付 | 回厂加工费、补料、赔偿、扣款、已占用来源 | 生成、审核、生成应付 | 来源不得重复；生成应付幂等返回同一记录 |

## 数据和兼容策略

- 现有对象 ID、业务单号和关系不迁移、不重写；新页面先直接读取当前对象。
- 需要新增的退料、赔偿、对账、应付关联和追溯对象使用独立命名空间与稳定来源键，写入动作要求幂等。
- 导航切换使用配置开关。新结构验收前保留旧结构回退，不复制业务数据。
- 原始对象页退出业务导航后仍可由详情页签和维护入口访问；权限默认沿主单据收紧。
- 状态语义不直接强行映射。建立“RISEMAP 已观察状态—Forge 当前状态—迁移规则”表，对无法一一对应的状态保留显式转换或待复核标记。
- 对账、库存和应付不得使用前端汇总作为账。所有数量和金额从持久记录、唯一来源关系和服务端动作计算。

## 视觉与交互基线

- 复制 RISEMAP 的信息层级和任务密度：职能域、侧栏、任务页签、页面标题、主动作、指标、待办、列表/详情。
- 每个列表页保留搜索、范围、状态、业务筛选、刷新、导入导出及分页的固定位置；只实现有真实能力的操作。
- 每个详情页固定呈现单号与状态、责任人、来源、三类进度、金额数量、异常、上下游、操作记录和明确返回路径。
- 主动作与下一步放在当前结果附近。阻断原因保留输入，并直接说明缺什么、去哪处理。
- 统一使用业务名称；技术对象名只在诊断界面出现。
- 颜色和渐变只承担层级与状态，不把视觉相似替代业务可用性。
- 1280×800 和 1440×900 下，主动作、当前状态和下一步无需横向滚动即可看到；宽表只允许卡片内部滚动。

## 分阶段执行

### R0 结构冻结与证据基线

已完成：冻结 `12305fb`，建立当前结构审计、RISEMAP 181 入口产品图和本方案。停止向旧 10 区结构继续添加入口。

### R1 委外产品壳和现有能力重组

重建“生产 / 委外管理”13 入口、岗位指南、看板、独立订单页，并把现有供应商、订单、发料、签收、回厂、入库和 NCR 接入连续详情。隐藏委外内部对象入口。此阶段不补造财务闭环。

完成门槛：四岗位可以从各自入口找到现有任务；已实现流程可在新结构办理；旧数据按原 ID 回读；导航和两档视口通过。

当前状态：结构与既有数据兼容已通过，详见 [R1 验证](forge-product-recovery-r1-verification.md)。四种岗位视图已可切换，真实身份权限仍待 R4 验证；两档视口中的大视口还需在 R2 有真实材料后保存正式证据。

### R2 物料回收与异常责任

实现余料退回、拒收、复检、供应商赔偿、超耗责任与负向对账来源，统一数量守恒和反审核依赖。

完成门槛：正常与异常材料分别跑通；库存双方流水、在外余额、NCR 和赔偿来源一致；重复操作与越级操作被阻断。

### R3 对账、应付与追溯

实现待对账池、对账单、幂等应付、批次双向追溯和三张委外报表。

完成门槛：一份真实材料从订单到应付贯通；加工费、补料、赔偿、扣款和净应付可逐笔追溯；同一来源不能重复对账。

### R4 独立验收与推广决策

由未参与实现的人按岗位剧本执行正常、异常、撤销和重启路径，并与 RISEMAP 证据并排审查。只有通过后，才讨论把同一结构迁移到采购、生产、销售和财务。

## 停止规则

出现以下任一情况，停止扩展并回到证据或设计阶段：

- RISEMAP 对关键状态、数量、金额或角色规则没有证据，且 Forge 推断会造成不可逆账务影响。
- 页面需要用户打开原始明细、日志或流水对象才能判断下一步。
- 业务材料无法在 API、页面和同一 SQLite 重启回读中得到一致结果。
- 为了通过演示而使用前端临时汇总、固定测试数字、默认第一条记录或单进程状态。
- 已实现样板没有独立岗位验收，或测试人员必须依赖开发者口头解释才能完成。
- 委外样板未过门禁，却开始把新结构复制到其他业务域。

## 三方互审

### 产品审查

结论：有条件通过。

- 通过项：一级域恢复为 RISEMAP 职能结构；委外 13 入口完整保留；四岗位任务、当前单据上下文和下一步成为设计中心；OEM 生命周期降为跨域视图。
- 修正项：NCR 不能继续作为委外一级入口；“委外看板与订单”必须拆开；未实现入口必须显示“待实现/待复核”，不能只放空页。
- 方向确认：依据本轮恢复目标，采用“RISEMAP 职能域为默认导航，OEM 生命周期为项目全景”的双视图关系。

### 工程审查

结论：有条件通过。

- 通过项：保留现有对象、动作和数据；通过新页面与导航重组降低迁移风险；旧结构可配置回退。
- 修正项：退料、赔偿、对账和应付必须有唯一来源键和幂等动作；状态映射先落表；原始对象隐藏后要保留受控诊断路径；共享导航只在一个分支修改。
- 待验证：当前动作跨多个对象写入时的原子性、并发重复提交和失败恢复还没有完整证据，R2/R3 必须补齐。

### 质量审查

结论：方案通过，实施验收门禁未满足。

- 通过项：区分了结构、实现、API、持久化、浏览器和独立业务验收；明确正常与异常、四岗位和同材料对照。
- 修正项：验收材料必须包含甲供与包工包料两分支、至少一次不良和一次余料退回；浏览器操作要从登录后的岗位入口开始；重启回读要核对原 ID 和账务总额。
- 阻断项：当前 Forge 缺退料、赔偿、对账、应付和追溯，现状不能宣称委外闭环；现有 NCR 四类中只有让步接收取得 RISEMAP 可操作证据，其余仍待同材料复核。

## 实施方向

默认导航恢复为 RISEMAP 的 9 个职能域，OEM 生命周期改为“项目全景”视图。该方向承接用户要求完整跟随 RISEMAP 产品结构的目标，R1 直接据此编码。后续若收到明确的相反产品决策，再重写产品结构目标。

## 本轮边界

本阶段已交付结构审计、产品地图、恢复方案和三方互审。尚未把委外现状称为闭环。R1 继续在 `codex/risemap-product-recovery` 独立 worktree 完成。
