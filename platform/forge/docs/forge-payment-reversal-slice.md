# Forge 采购付款核销与付款撤销切片

更新于 2026-09-10。实现位于隔离分支 `codex/otc-payment-reversal`，验收端口 `4371`，数据库 `.objectstack/otc-payment-reversal.sqlite`。该库承接已停服的当前主线兼容快照，保留应付 `AP-PIN-RM-20260909-001`；SQLite 完整性检查为 `ok`。

## 证据边界

RISEMAP 已证明付款任务、实际付款流水和付款核销是分开的业务步骤，但本轮仍未取得同材料撤销入口、审批规则和成功撤销记录。因此本切片是 Forge 对错误付款更正的受限实现，不能记作与 RISEMAP 行为一致。

## 已实现行为

- 待审核付款核销可以填写原因后取消，原付款流水继续保持待核销，随后可撤销实际付款。
- 已审核采购付款可以反核销，恢复应付已付金额与余额、付款任务已付金额与待付金额，并把原付款流水恢复为待核销。
- 同一应付存在更晚的已审核核销时，必须按核销时间从后向前撤销，防止跨越后续账务重算。
- 只有核销已取消或已反核销的采购应付付款才能撤销；撤销后按原付款账户加回同额余额，并保存撤销人、时间和原因。
- 取消待核销、反核销和撤销付款均写入独立持久日志。供应商预付款、费用、委外和运输付款被当前撤销动作明确排除。
- 付款管理页提供“取消待核销”“反核销”和“撤销付款”，并显示撤销原因输入及最终“付款已撤销”状态。

## 验证结果

定向 API 验收共 4 组。第一笔 `1200` 在待核销状态取消后撤销；第二笔 `3200` 完成核销后反核销并撤销。测试覆盖匿名取消、空原因、越过待核销或已核销、重复撤销、应付与任务恢复、账户恢复和四条日志。两条链结束后，应付恢复为未付款 `6800`，验收账户恢复为 `9000`。

浏览器办理 `PT-REV-BROWSER-20260910-001 → PAY-REV-BROWSER-20260910-001`，金额 `1800`。页面审批并核销后，应付余额从 `6800` 降为 `5000`，账户从 `9000` 降为 `7200`；反核销和撤销付款后，两者分别恢复为 `6800` 和 `9000`，页面显示“付款已撤销”。

完整停服后从同一 SQLite 文件重启，API 回读 3 张已撤销付款、1 张已取消核销、2 张已反核销和 6 条撤销日志；浏览器重新加载仍显示全部付款已撤销，应付和账户保持原始基线。元数据门禁通过：104 个对象、1642 个字段、23 个页面、122 个动作；`typecheck`、`validate` 和 `build` 均通过。

## 未证明范围

本切片没有撤销付款任务审批，也没有处理供应商预付款、费用、委外、运输、客户退款等其他付款来源。已实现逆序撤销阻断，但本轮未独立构造两笔同时已核销的动态样本。发票红冲、预收预付冲抵撤销、银行对账、总账凭证、关账期间、岗位权限和事务级原子回滚仍待后续阶段。
