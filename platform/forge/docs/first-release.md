# Forge 首个正式版本的交付要求

更新于 2026-09-08。发起人明确要求 Forge 从首版就供真实用户使用，随时可能有客户下单。本文件据此修正此前以展示、走访和试用为终点的交付设想。以下为建设要求，尚无已上线系统或已通过的验收结果。

## 目标与范围

首版应当能够开通客户、接纳真实业务数据，并持续处理已承诺范围内的工作。功能范围可以分期；一旦对客户开放，就应具备正常办理、异常续办、数据恢复和后续维护能力。

当前复刻范围已明确为 RISEMAP 全部能力，详见 [完整复刻与采集标准](risemap-replication-spec.md)。原柜机优先建议不再作为范围依据；一次产品、一次柜机、二次项目用于后续 OEM 适配分析。未完成的路径不得以样例或占位功能交付，也不得为了复用项目管理页面而强迫产品订单立项。

三到四周保留为首版交付的目标窗口，原有按演示安排的周计划需重新估算。范围、人员及首批订单要求确认后，逐项检查交付条件。时间不足时应明确调整范围或交期，不能把数据可靠性和持续运行移到客户使用之后建设。

## 客户下单后怎样交付

客户购买 Forge 的订单，与客户在 Forge 内管理的销售订单分别记录。前者决定客户获得什么服务，后者属于客户自身的业务。

| 环节 | 首版需要交付的结果 |
| --- | --- |
| 接单 | 记录购买主体、交付范围、用户数量、部署方式、服务期限和交付时间，能够查明当前办理人和状态 |
| 开通 | 按购买范围创建企业环境与管理员，通过实际入口登录并邀请成员，重复办理不会创建重复环境或权益 |
| 初始化 | 配置岗位、业务分类和必要基础资料；导入有校验、结果反馈及错误修正方式 |
| 投入使用 | 业务人员能够独立处理约定路径，真实业务记录和附件可持续保存及查询 |
| 持续服务 | 有明确问题反馈入口和处理责任人，可以查明故障、恢复服务及发布修复 |
| 到期与退出 | 服务状态有明确记录，客户能按约定导出业务数据及附件，停用流程保留必要数据 |

首批可以人工办理接单、开通和服务状态变更，但过程须有记录且能重复执行。是否提供自助购买和在线支付尚未确定，本次要求不自动增加支付系统建设范围。

交付方式尚未定案。可评估每客户独立部署，也可评估共享服务中的企业隔离。无论采用哪种方式，都必须验证多个客户的数据和附件互不可见，以及正确身份下的访问与操作。

## 对外开放前必须成立的条件

| 方面 | 可检查的交付证据 |
| --- | --- |
| 业务办理 | 用代表材料完整走完已承诺路径，业务人员能通过页面完成工作，处理驳回、变更、撤销和验收未通过，无需开发者直接修改数据库 |
| 金额与版本 | 报价按确定规则计算；币种、精度、税费和舍入规则明确；已确认版本不被后续编辑覆盖，订单和交付记录能追溯承诺 |
| 重复与并发操作 | 重复交接、重复确认及同时编辑不会重复立项、重复确认或静默覆盖；部分失败有可见结果和续办入口 |
| 客户与岗位隔离 | 使用至少两个客户环境及不同岗位测试页面、接口、导出、附件和 AI 访问；离职或停用账号的访问及时失效 |
| 数据与附件恢复 | 使用持久存储；备份同时覆盖业务记录和附件，并在独立环境实际恢复、核对关联及可读性；恢复时间和可接受数据损失按交付约定验证 |
| 持续运行 | 审批等待时重启可续办，后台任务失败可发现与重试；服务健康、错误及关键业务失败能被负责人员发现和处理 |
| 发布与升级 | 发布对应固定代码及依赖版本，正式环境与测试环境分离；在副本验证迁移与升级失败后的恢复办法，保留发布记录 |
| 容量与操作体验 | 根据首批客户的用户数、记录量、附件量和同时操作量验证响应；以实际约定的容量通过结果判断可交付范围 |
| AI 实际可用 | 已承诺的 AI 功能连接真实模型，结果有来源且可复核；超时或错误可见、可重试，人员可继续办理主要业务 |
| 交付与维护 | 客户开通、数据初始化、操作说明、问题反馈、修复发布和数据导出均有实际办理方式及责任人 |

这些条件是首版产品工作的一部分。精确容量、恢复目标、服务时间和部署方式应在首批交付范围内写明，当前不虚构承诺数字。

## 业务边界怎样落地

采购制造首期若采用状态与证据登记，必须允许责任人真实更新、纠错和追溯，页面明确记录来源与更新时间。外部 ERP、实际生产、财务核算等由哪套系统承担，应在交付范围和操作说明中写清。状态登记不能被宣传为已经自动连接生产系统。

一次柜机的已开放路径要完整处理报价、合同依据、订单转换、项目、配置或设计版本、变更、调试、验收项、整改与客户确认。产品订单的小案例只用于检查模型，产品路径本身通过完整验收后才列入可交付范围。二次项目同理。

历史项目回放用于验证业务规则。上线前还要验证客户开通、权限、恢复及发布；上线后继续记录真实在途业务的使用结果。不能等一个长周期柜机项目实际完工才开始提供服务，也不能将一次历史回放记为真实工程已经交付。

## 框架选择怎样变化

ObjectStack 的两天试验只承担选型初筛，回答关键模型与运行机制能否满足需要。通过后还需完成本文件中的交付验证，才能判断适合承接真实客户。源码中存在实现、模板能启动、样例能演示，均不能替代这些结果。

华炎魔方现成方案也按相同标准评估。除业务操作，还需核实实际交付版本、客户开通、权限、升级、恢复、可扩展范围及维护方式。若现成方案能满足首批真实订单，可以评估采购或配置交付；选择新框架自建时，应把业务开发和持续运行一起估算。

## 下一阶段应形成的结果

首批交付范围、代表单据、账号与企业模型、部署方案、框架初筛结果及重新估算的实施计划，应共同形成可审查的方案。当前已确定真实可用的交付目标；具体行业与路径优先级、客户容量、人员投入和交付方式仍需结合订单信息落实。

后续实施按可交付的业务能力推进，每个已开放功能同时完成界面办理、服务端规则、权限及相关故障处理。避免先铺满页面，再集中补真实行为。
