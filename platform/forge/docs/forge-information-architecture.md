# Forge 信息架构与分组规则

更新于 2026-09-12。本文件先按 RISEMAP 当前可观察的九类一级菜单整理 Forge 导航，再以功能为单位逐步修补页面、动作、状态和验证。菜单归类不代表功能已经复刻或验收通过；实现状态仍以 `docs/forge-verification-matrix.md` 为准。当前注册表已将财务对账归入“业务确认”，并将系统入口整理为“系统设置 / 业务设置”。

## 页面层级约束

1. 一级菜单名称和顺序对齐 RISEMAP 的当前九类入口：工作台、供应链、销售、生产、项目、行政、财务、报表、系统。
2. 一级菜单表达业务责任域，不放单据状态或技术对象。
3. 二级分组表达 RISEMAP 可观察的稳定任务簇，例如“到货检验”“委外管理”“资金管理”。
4. 三级入口优先指向用户可直接办理的列表、看板、工作台或设置页；内部明细、日志和流水不作为常规入口。
5. 联系方式、银行账号、单据明细、BOM 节点等依附对象，正式体验优先以内嵌子表或详情页签出现；当前 ObjectStack 通用列表只承担模型验证，不能据此认定最终交互完成。
6. 配置项靠近其消费业务，同时在“系统”保留统一治理入口；同一配置只有一个权威定义。
7. 菜单按权限隐藏时，接口、搜索、导出与 AI 工具必须使用相同权限边界。
8. 系统二级导航只保留 RISEMAP 的“系统设置”和“业务设置”；后者可以继续使用商品、客户、采购销售、库存和项目等域分组承载现有配置，不把这些配置域误当成系统的一级分组。

## 证据分类

| 分类 | 含义 | 当前处理 |
| --- | --- | --- |
| RISEMAP 已观察事实 | 已保存页面、DOM、深度记录或只读行为证据 | 可用于菜单、字段、状态和交互基线；不可自动升级为成功闭环 |
| Forge 工程推断 | 为让现有代码运行而采用的对象拆分、状态、公式或持久化方案 | 保留在实现和验证材料中，不能写成 RISEMAP 规则 |
| 可复用服务能力 | 已有 API、对象、动作、库存/财务流水或持久化机制 | 先复用，再补用户可见页面和业务语义 |
| 需要重构的产品界面 | 能力存在但入口、上下文、字段组织或下一步不符合 RISEMAP 任务结构 | 逐功能修补，不以对象数计完成 |
| 语义风险 | 状态、金额、责任主体或下游影响尚未被 RISEMAP 或完整业务材料证明 | 保持“待复核”，禁止作为推广依据 |

## 证据和完成声明

每个入口分别记录 `runtime_observed`、`frontend_static`、`published_guide`、`published_example`、`release_note` 和 `forge_verified` 来源。静态前端可支持字段与布局草案，公开说明可支持流程假设，只有运行结果可以证明保存、状态变更、权限和跨单据联动。

当前导航重排只改变页面承载位置，不迁移数据、不删除对象/动作、不修改线上 RISEMAP 数据。后续修补顺序以 `docs/forge-replication-work-order-20260913.md` 为准：先完成每个菜单下的可达入口和页面合同，再按岗位任务补状态动作、上下游跳转、异常阻断、持久化和独立验收。当前下一块是“项目计划与任务”；其中“任务管理”使用独立任务列表入口，任务行回到所属计划上下文办理。委外样板在“订单→发料→签收→回厂→良品/NCR→对账结算”全部门禁通过前，不扩展其他业务域的孤立切片。
