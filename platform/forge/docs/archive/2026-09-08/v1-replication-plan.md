## 我建议怎样起步

以华炎魔方工程项目方案的业务组织方式为参考，建设 Forge 自己的报价与交付管理应用。先形成一条可以销售、开通并持续使用的柜机交付路径，客户拿到账号后能够用它办理日常业务。客户、报价、合同与订单、项目执行、验收和回款台账应彼此关联。

这一范围以首批尚无其他已承诺订单为前提。若客户已经购买产品订单或二次项目能力，实施范围必须覆盖相应承诺。柜机作为默认起点，是因为内部材料已给出其设计、调试与验收过程，能够检验 Forge 的主要价值；它仍是建议，不能代替首批客户需求确认。

现有官方方案展示了项目与销售、合同、采购和资金管理的关联，适合用作业务参照。是否直接使用现成代码或购买完整方案，应依据实际交付包的运行结果决定。[华炎魔方工程项目方案](https://www.steedos.com/resources/solutions/construction)

## 首版用户会看到什么

| 页面 | 必须能完成的工作 | 与后续工作的连接 |
| --- | --- | --- |
| 我的工作 | 查看本人待办、审批、逾期和失败事项，直接进入办理 | 每条待办能找到业务单据、责任人和下一步动作 |
| 客户与需求 | 保存客户、联系人、需求及原始材料，查明待澄清问题 | 需求关联报价，避免成交后重新录入客户和范围 |
| 报价 | 编辑明细、计算金额、修订版本、提交审核、记录客户确认、导出报价单 | 交接时固定采用的版本与明细，保留确认依据 |
| 合同与订单 | 记录合同范围、交期、付款节点、客户订单及交付类别 | 通过明确的转换动作承接交付，失败可继续办理，重复提交复用同一结果 |
| 项目工作页 | 集中查看范围、负责人、里程碑、任务、设计版本、采购制造状态及变更 | 每项变化能追溯输入版本、确认记录及受影响工作 |
| 调试与验收 | 汇集交付物、调试记录、验收项，办理未通过项、整改、复验和最终确认 | 输出验收材料，保留客户确认依据，关联约定的回款节点 |
| 收付款台账 | 记录合同收付款计划、实际金额和凭据，查看到期与逾期 | 显示项目经营进展；实际开票和财务核算由约定的外部流程承担 |
| 企业设置 | 管理成员、岗位、基础字典、业务模板及数据导入导出 | 支撑客户初始化及持续使用，配置调整不覆盖历史单据 |

收付款台账在此前的关联记录建议上有所展开，用来让负责人看到交付与资金的关系。它属于本稿新增建议，需要计入范围与工作量。客户若暂时不需要实际付款记录，可保留合同节点和外部凭据引用，交付范围明确说明即可。

首版可以支持人员导入、登记和上传真实凭据。采购制造状态要标明来源、时间和责任人，提供纠错与历史记录。外部系统尚未自动连接时，不显示自动同步成功。

## 复刻到什么深度

借鉴对象、关联、角色分工和日常操作顺序。逐项观察参考系统的输入、动作、输出和异常，然后形成 Forge 自己的规则。页面上的一个“完成”按钮，要能解释谁有权点击、前提是什么、会修改哪些记录、失败后如何处理。

| 能力 | 处理方式 |
| --- | --- |
| 通用列表、表单、筛选、基础关联 | 优先使用所选框架已经验证的机制，减少基础页面工作 |
| 报价计算、版本固定、订单转换 | 作为 Forge 业务规则实现，明确金额、权限、唯一性和失败处理 |
| 项目、里程碑、任务、问题 | 借鉴现成模型，再按柜机交付关系调整 |
| 范围变更、调试、验收与整改 | 依据内部单据设计，这是首版必须做完整的工作 |
| 岗位权限、附件、通知、备份 | 尽量使用已验证组件，同时完成 Forge 实际身份和数据下的检查 |
| 完整 ERP、生产排程、财务总账、通用流程设计器 | 暂不纳入默认首版范围，已有客户承诺另行评估 |

最重要的关系是报价承诺、交付范围和验收依据。报价 V2 成交后，后续设计和验收应追溯 V2；再编制 V3 不得改写已承诺的历史。范围变更应同时说明价格、交期及交付要求的影响，客户确认后再进入执行依据。

一次产品仍保留独立销售订单模型。用于建模核对的小案例不计为对外可用的产品模块；要销售该能力，就必须完整支持对应的订单、配置、发运与签收。二次项目的现场交付同样单独验收。

## 技术上采用什么形态

我建议首版采用模块化的单体 Web 应用，配关系数据库、附件存储和后台任务。业务模块共用一套对象关系与授权规则。先把跨单据的一致性和人员操作做好，再根据实际负载决定是否拆分服务。

首批建议采用统一代码、每客户独立应用环境、独立数据库及受隔离的附件存储。环境可以由我们集中托管，客户通过浏览器使用，不要求每家一台独立物理服务器。客户开通、初始化和备份做成可重复执行的过程。

这样较容易分别检查客户隔离、恢复和升级，代价是客户数量增加时维护的环境也会增加。因此必须从首版保持统一发布制品及配置方式，客户差异先放入配置和模板，避免每客户维护一套代码。共享服务的多租户架构后续按客户数量和运营成本再评估。

对 ObjectStack，我会保留候选地位，同时把“优先采用”的确定性收窄。当前已经检查了关键源码，尚无本项目的运行证据，不能据此承担正式交付承诺。用两天初筛核对报价强约束、明细锁、受限操作、交接重试及恢复；通过后，用同一版本继续完成首版运行验证。若需要长期修补框架内核才能完成这些要求，及时使用团队具备交付能力的常规应用栈。

ObjectStack 的部署资料将平台运行时与应用版本分开管理，这适合统一制品、分别维护客户环境的方向；实际部署和恢复仍须验证。[官方部署说明](https://objectstack.ai/docs/deployment)

如果能取得华炎魔方完整工程方案，并确认业务办理、客户交付和扩展条件满足首批订单，可以优先比较直接配置交付的成本。当前公开旧应用与新框架之间的迁移工作不放入首版计划。[现成方案核查](steedos-solution-assessment.md)

## AI 放在哪里

先做两个与现有业务页面相连的入口。需求页从上传材料生成可编辑的需求草稿，附材料依据及待确认项。验收页依据已确认范围、设计版本和调试材料起草验收清单，并提示缺失材料。

AI 结果保留草稿状态，人员核对后才进入正式记录。系统记录输入材料版本、处理结果和错误，模型超时可重试，人员也可继续办理。金额、状态转换和客户确认由确定的规则及有权人员控制。

## 开发顺序

1. 核对一个柜机代表项目的实际单据和参考方案操作，把每项工作写成输入、动作、输出、异常及完成依据。同步确定首批交付范围、用户角色及部署容量。
2. 建立可部署的应用、真实账号、客户环境、持久数据库和附件；完成一条实际记录的创建、授权访问、备份与恢复。
3. 完成需求、报价修订、审核、客户确认及订单转换。连同金额校验、权限、重复请求和部分失败一起交付。
4. 接通项目执行、设计版本、范围变更、调试及整改验收，业务人员通过页面完成整个约定流程。
5. 加入台账、导出和两项 AI，按首批使用方式完成容量、升级及恢复验证，再开通正式客户并持续处理使用问题。

前三步形成的阶段结果都应能保存真实数据并持续迭代。正式客户在其购买范围通过交付验收后接入，不把未完成模块先开放给用户。

三到四周只保留目标窗口，现阶段缺少人员投入、首批订单及真实单据，无法给出可靠的固定交期。复刻范围确定后，将业务实现、框架适配和正式运行分别估算，再排成同一份交付计划。

## 最先需要确定的事情

下一步先把首版八个页面及其关键动作细化为可审查的业务规格，再用一份实际柜机项目材料逐项核对。以该规格做技术初筛和排期，能够避免技术试验通过后才发现业务规则遗漏。当前无需先建设完整平台或铺开三类业务的全部页面。
